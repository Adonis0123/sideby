# ADR 0078: Carry folder trust between Claude Accounts, opt-in, by copying one field

Date: 2026-11-18 · Status: accepted

## Context

Claude Code shows "Accessing workspace … Quick safety check: Is this a project you created or one you trust?" the first time an Account opens a folder, and stores the answer per Account in that Account's `.claude.json` as `projects["<path>"].hasTrustDialogAccepted: true`. A user who runs several Claude Accounts has usually answered it in one of them. When sideby starts another Account in the same project (a Pick Command, `sideby run`, an Auto Handoff hop), that Account asks again. The dialog's default is "No, exit": pressing Enter ends the session, and an Auto Handoff stops at the new Account's first screen.

Claude Code 2.1.326 has no launch option, variable or setting that pre-trusts a folder (`claude --trust-workspace` answers "unknown option"). Its documentation (https://code.claude.com/docs/en/permissions) says to trust a folder by hand by setting `projects["<path>"].hasTrustDialogAccepted` to `true` in `~/.claude.json`, where `<path>` is the repository root; "In a worktree, it uses the main checkout's root"; and a parent folder's trust covers its subfolders "apart from a git repository nested inside it". clodex copies trust between accounts by writing only `{ hasTrustDialogAccepted: true }` (https://github.com/avirtual/clodex/blob/35be83499ee74928622acdab67e73532f7e254ba/accounts.js).

Tried with Claude Code 2.1.326 on 2026-11-17, with separate `CLAUDE_CONFIG_DIR`s in a pseudo-terminal: no key asks; a key equal to the folder does not; a key equal to a parent of a plain (not git) folder does not; a key equal to the main checkout's root does not, in a linked worktree of it. While a session ran, a `projects` key added from outside by an atomic rename survived: Claude Code re-reads the file before it writes it and kept the key. Claude Code uses no lock file for `.claude.json`.

Ways to stop the second question:

- Do nothing and document it. Rejected: the default answer ends the session, and Auto Handoff exists to keep going without a person.
- Share `.claude.json` between Accounts (a link). Rejected: it holds the login; Share Mode `json-key` already refuses a linked `.claude.json` because it mixes logins.
- Trust every folder sideby starts in. Rejected: it creates trust the user never gave, which is what the dialog guards against.
- Copy the trust the user already gave in another Account, the same key, only that one field, behind a switch. Chosen: it reuses a decision the user made, writes the least, and is off until the user turns it on.

## Decision

- Config `claude.carryTrust` (boolean, default off). Off: nothing is read or written. On: for every interactive Claude Launch sideby prepares to run a session (`sideby run`, Aliases, Pick Commands, `sideby next`, `sideby resume` routed to a non-main Account, every Auto Handoff hop, AI Tasks, sessions started under Unattended Mode), after Network Guard and every `launch.before` hook let it through and before the Host starts: when the target Account does not trust the launch folder F and another Claude Account of the user (any Claude Account sideby knows, the Main Account and API Accounts included) does, sideby copies that Account's matching key K into the target's `projects` with `hasTrustDialogAccepted: true`. The same key, never widened or narrowed; never trust nobody gave. Not for a headless run (`-p`, `--print`), `sideby login`, `sideby try` or a Quota question (both `-p`). F is sideby's own working folder, which the Host inherits.
- "Trusts F" follows Claude Code's documented rules, read from files only, and anything unclear counts as not trusted:
  - F inside a git checkout: walking up from F, the first `.git` marks the checkout root R. A `.git` folder makes R the main root M. A `.git` file `gitdir: <dir>` is a linked worktree only when `<dir>` is `<common>/worktrees/<name>`, `<dir>/gitdir` points back at `R/.git` (real paths compared), `<dir>/commondir` (or the folder layout) leads to `<common>`, and `<common>` is the `.git` folder of the checkout M above it. A submodule, a separate git folder, a link or a `.git` that cannot be read is unclear. sideby never runs `git` in F: an untrusted repository's config can run programs. Only a key equal to M counts; once a `.git` is found, a parent folder's trust never counts.
  - F outside any git checkout: a key equal to F or any parent of F counts.
  - A key equal to HOME or a filesystem root never counts. F and M are real paths; keys are compared as written (Claude Code writes real paths), so a key that matches only through a link does not count.
  - Among several matches, the narrowest key wins, then the first Account in discovery order.
- Where each Account's `.claude.json` lives comes from the Claude Family (`claudeJsonOf`: `~/.claude.json` for the Main Account, the Account directory otherwise). It is a credential file: only `projects.*.hasTrustDialogAccepted` is read, opened without following a link and at most 64 MB; no other value reaches an output, a log, an error or a record; errors name the path only and never quote the file. The target is read first; the other Accounts only when it lacks trust.
- The write follows Share Mode `json-key`'s protections. It refuses a linked file, a file that is not a JSON object, a `projects` that is not an object, an entry that is not an object, and a field that is neither absent nor `false`, and it never creates the file. It changes only that field: a missing entry becomes `{ "hasTrustDialogAccepted": true }`; an existing one gets the field in place, keeping its other fields. Every other key, their order, the indentation and the final newline are kept. Under sideby's per-file lock (`<state>/settings-locks/`, a 2-second wait), it re-reads the file, compares a hash right before the atomic rename (a temp file in the same folder, mode 600), and skips when the file changed. A failed or skipped carry never stops the Launch.
- Every carry prints one line on stderr at once (not as a launch notice: Auto Handoff may prepare one Launch twice), for example `sideby: claude:work now trusts ~/code/app, as claude:main does (claude.carryTrust; undo: sideby trust undo)`. A skip prints why and that Claude Code will ask. Nothing is printed when no Account trusts the folder or the target already does.
- Each carry is recorded in `<state>/trust/carried/<hash of file and key>.json` (folders 700 through `ownedFolder`, file 600): the Account, its `.claude.json`, the key, what the field was before (`no-entry`, `no-field`, `false`), the time and the source Account. The file is written first and the record after, so a failed write leaves no record. `sideby trust undo` takes back only what sideby added, and only while the field still holds `true`, what sideby wrote: `false` comes back as `false`; an absent field goes again, together with the entry when sideby made it and it holds nothing else (then a canonically formatted file comes back byte for byte); fields Claude Code added to the entry since are kept. A field changed since, or a file that is gone, is left alone and its record dropped; a file that became a link or not a JSON object, or changed during the write, keeps its record for another try. Turning the setting off undoes nothing; the CLI and the Panel say so.
- `sideby trust [--dir <path>]` shows the setting and the records and, only while on, each Claude Account's trust of that folder as booleans (`trusts`, absent with a `problem` that names the path when sideby cannot tell), never another `projects` path. `sideby trust on|off` and `sideby trust undo` show the change and exit 10 until `--yes`. The Panel's Settings get a *Folder trust* section with the switch, the records behind *Review* and their removal, and an "Ask your AI" phrase; its polled state reads only sideby's records, never a `.claude.json`.
- This is the seventh exception to "sideby writes nothing into a Host directory", after `quota setup claude --yes`, `handoff setup grok --yes`, `tune apply` (ADR-0012), `remote-control` (ADR-0017), `messages inbound accept` (ADR-0040) and the Advisor (ADR-0074). With the Main Account as target it is sideby's first write to `~/.claude.json` in HOME.

## Consequences

- A user who turns it on stops seeing the trust question in a second Account for folders they already trusted, and an Auto Handoff no longer stops at it. Folders no Account trusted still ask, as before.
- Sessions started with plain `claude`, and `sideby resume` when it runs the Host unchanged in the Main Account, are not covered: sideby does not prepare those Launches.
- A Launch that runs a Claude subcommand through sideby (`sideby run claude:work -- mcp list`) counts as a Launch too; it only copies trust the user gave.
- A brand-new Account without `.claude.json` asks once, as Claude Code creates the file on its first start; sideby does not create it.
- The rules are the documented ones, checked with Claude Code 2.1.326. If Claude Code changes where it keeps trust or how it finds the key, a carry may write a field nobody reads, or miss a case; it never trusts a folder by itself. Re-check the four cases above with a new Claude Code release.
- Top-level and `projects` keys keep their order, except integer-like keys, which JSON parsing in JavaScript moves first; Claude Code writes none.
