# ADR-0078: A later reply in the session marks a Pending Decision replied

Status: accepted
Date: 2026-11-16

## Context

Unattended Mode (ADR-0058) keeps every question it refused, every permission request nobody answered and every action a session left undone as a Pending Decision, and Answer Wait (ADR-0077) adds the questions nobody answered in time. A Pending Decision goes away only when the user marks it done. After a few nights the Unattended page is a long flat list, and the user cannot tell which items still need them: in practice they come back and answer in the session itself ("go with the recommendation", "ship it"), and never mark anything done.

One real set of data, read on 2026-11-16 from the Hosts' session records whose sessions ran Claude Code 2.1.312 to 2.1.325: 477 Pending Decisions, 96 marked done and 381 not. In 331 of those 381, the user typed in the same session after the decision was kept; 50 had nothing typed after them. The 381 came from 36 working folders; 17 of those folders were gone, 13 of them deleted worktrees under `<repository>/.worktrees/` or `<repository>/.claude/worktrees/`. Read by hand the same day, the 331 the user typed after were not all settled: 206 were finished, 65 partly and 53 not at all: about 37 % were not finished. Typing in the session afterwards shows the user was there, not that the decision was dealt with.

What a Claude Code session record (`projects/<folder>/<session id>.jsonl`) holds after a decision, in that data:

- What the user typed: `type: "user"` with `origin.kind: "human"` (or no `origin` in older records and `claude -p`). Lines with another `origin.kind` (`task-notification`, `peer`) were made by Claude Code or another session.
- sideby's own notes: the `Stop` hook's reason (`decision: "block"`) is a `user` line with `isMeta: true` that starts with "Stop hook feedback:"; every background hook's wake-up (Turn Retry, Answer Wait's `StopWait`, Progress Reminders, Network Guard's `Held`) is a `<task-notification>` line with `origin.kind: "task-notification"`; a refused ask tool or permission request is a `tool_result`.
- Claude Code's own lines: a compaction summary ("This session is being continued from a previous conversation…", `isCompactSummary: true`), skill bodies and image notes (`isMeta`), Messages from another session (`origin.kind: "peer"`, `isMeta`), and slash commands (`<command-name>`).

Session History's reader (ADR-0042, `families/claude/history.ts`, `families/codex/history.ts`) already gives only what a person typed: it drops tool results, `isMeta`, compaction summaries, subagent lines and injected blocks. Of the remaining kinds, slash commands, `!` shell lines and `sideby send`'s Messages are not a reply to a decision.

Options considered:

- Asking a model to read the session and decide whether each decision was handled. Rejected: it reads a credential to call a model (ADR-0001 forbids it), spends Quota, and sends the user's work elsewhere.
- Marking a decision done by itself once the user replied. Rejected: a reply in the session does not always settle the decision (37 % of them in the data above), and done items are deleted after 30 days.
- A one-click "mark the replied ones done" per project. Rejected for the same reason: it would bury the unfinished third with the rest.
- Showing, as a plain fact, that the user wrote in the session afterwards; listing the untouched ones first and folding the others under them, each marked done on its own after a look, with a way to reopen one marked by mistake. Chosen.
- Grouping by session (as before) or by Account. Rejected as the first level: a night spreads over many sessions of the same repository, and the user thinks in projects; sessions stay as the second level, with their way back.

## Decision

- Each Pending Decision belongs to a Project, found from its `cwd` as Session History finds one (spec §3.33, `ProjectResolver`: the repository root, a worktree folded into its main repository, a folder outside any repository on its own), with one addition for Pending Decisions: a folder that is gone counts as the repository of its nearest folder that is still there, when that folder is inside one, so a deleted worktree under the repository folds back into it. Without a `cwd` it belongs to no Project ("Other"). The Project's short name is Session History's (`projectNames`).
- An open Pending Decision with a session id, in a Family whose session records sideby reads (Claude Code, Codex), is **replied** when the session's record holds a message the user typed later than the decision's `at`; `repliedAt` is the first such message's time. The record is found in the decision's Account first, then in the Family's other Accounts (Claude `projects/*/<id>.jsonl`, Codex `sessions/**/rollout-*-<id>.jsonl`), only for a session id of the plain form Session History accepts (`SAFE_ID`). Each Account's records are listed once per listing and the session id is matched against the names listed, so it never goes into a path. The record is read with Session History's reader; a message counts only when Claude Code marks it `origin.kind: "human"` or marks nothing, and not when it starts with `/` or `!` (a slash command or a shell line), holds `sideby message <8 hex>`, starts with `<task-notification>`, "This session is being continued", `sideby: ` (every note of Auto Handoff) or the first prompt of a session a task was handed to ("This task was handed over from <account> by sideby"). When in doubt it is not a reply, so the decision stays with the untouched ones. A record not written after `at` is not opened.
- Three states: `done` (marked done), `replied` (not marked, the user wrote in the session afterwards; that does not tell whether it was finished), `open` (not marked, nothing typed after it: nobody touched it). An open decision whose record cannot be found says so (`replyCheck: "no-record"`), and one whose Family has no reader too (`"unsupported"`); both stay `open`.
- Read only: sideby opens the records read-only, writes nothing into a Host directory, reads no credential and calls no model. Of each record it keeps only the times of the user's messages, per file version, in memory and in `<state>/cache/file-memo.json` (the cache the usage readers already keep); never their text.
- The check runs when the Unattended page or `sideby unattended pending` lists Pending Decisions, not in `/api/state` or `sideby unattended`, which refresh far more often.
- `sideby unattended pending --json` adds `project`, `projectName`, `state`, `repliedAt` and `replyCheck` to each row (`project` and `projectName` are `""` without a Project), and a `projects` summary with each Project's `open`, `replied` and `done` counts; the rows keep their order. Adding fields keeps `schemaVersion` 1. The text output groups by Project, untouched ones first, and its last line says that writing in the session afterwards does not mean it was finished and names `done <id>`, `--ids <a,b>` and `reopen <id>`. `done --ids <a,b>` marks the ones the user checked; `done --replied [--project <name>]` and `done --project <name>` stay for someone who means it. A list of ids marks only the ones still open and returns only those (`done[]`). `sideby unattended pending reopen <id> | --ids <a,b>` opens ones marked done again and returns the ones it opened (`reopened[]`).
- The Panel groups by Project, then by session. In each Project the untouched ones show; the ones written in afterwards are folded under "You wrote afterwards (N)" (「之后说过话（N）」). Opened, the fold says "Some of these may not be finished. Look them over first.", has a button that names the count ("Mark these N done"), and each item keeps its own **Done**. A written-in row has a neutral mark, "You wrote in this session afterwards · 2 h ago". The Project heading carries no bulk button. After the Projects a folded "Done (N)" lists the ones marked in the last 30 days, each with **Reopen**. Every Done has its own toast and Undo, so two marks in a row can both be undone.

## Consequences

- The user sees at once which items nobody touched, project by project. The ones they wrote in afterwards stay one click away, and still need a look: about a third of them were not finished in the data above.
- "Replied" is a sign, not proof, and every surface says so. Marking is per item by default; the counted bulk button sits inside the fold, next to the caution. A wrong mark is undone from the toast, the done list, or `reopen`.
- It depends on the shape of the Hosts' records, through Session History's readers. If a Host version records sideby's notes differently, a note could count as a reply; the extra checks cover the forms seen in Claude Code's records (2026-11-16), and the readers' tests hold fixtures of each.
- Reading the records costs time on the first listing: about 1.8 seconds for 111 session records holding 2.3 GB (Node 22, records in the file cache, 2026-11-16); listing the 16 Accounts' record folders takes about 50 ms of it. The Panel then reuses each record's answer until the file changes (size, times and inode), about 12 ms for the same records, and about 15 ms in a new process that loads the saved answers. Only the Panel saves them: a one-off `sideby unattended pending` loads what the Panel saved, and without that reads the records again (about 2.2 seconds on the data above). `pending done <id>` without `--json` reads no record at all.
- Pending Decisions of Grok, pi, plugin Families and those kept outside a session stay `open`; the first two say why.
- `docs/agents/host-directories.md` lists the new read.
