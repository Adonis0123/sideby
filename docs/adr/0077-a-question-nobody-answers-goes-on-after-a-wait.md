# ADR-0077: A question nobody answers goes on after a wait

Status: accepted
Date: 2026-11-16

## Context

Unattended Mode (ADR-0058) refuses a question or a permission prompt at once, but only in a session that is unattended. An Attended Session (ADR-0075), one a person typed into within the last 30 minutes, asks as usual, and so does every session while the mode is off. A person who types, gets a question and then walks away leaves that session waiting until they come back, however long, also when a Slot begins in the meantime. Users asked for the middle ground: ask me while I am here, and do not get stuck when I am not.

What Claude Code 2.1.325 does (tried on 2026-11-16 with an isolated HOME, `ANTHROPIC_BASE_URL` pointed at a local fake server, interactive sessions in tmux and hooks in the isolated `settings.json` that recorded their input and answered after a delay):

- The `PermissionRequest` hook runs for the ask tool (`tool_name` `AskUserQuestion`) and for a permission prompt. In the main session it runs while the dialog is already on screen; the person can answer it meanwhile. A decision the hook prints later still applies: after 20 seconds, a `deny` with a `message` closed the dialog and the model read the message as the tool's error ("Denied by PermissionRequest hook"); an `allow` with `updatedInput.answers` closed it as "User answered Claude's questions". This held for the question and for a Bash prompt, in the default, auto and bypassPermissions modes, and for a `deny` 660 seconds after the prompt with the hook's `timeout` at 900.
- When the person answers first, their answer applies; the hook is not stopped and its later decision changes nothing (the approved command ran and its file was there).
- Claude Code's documentation says the hooks run alongside the host, "whichever decides first applies", only for a `--permission-prompt-tool` or an Agent SDK `canUseTool` callback (https://code.claude.com/docs/en/hooks#permissionrequest). In a terminal session it is observed behaviour, not a documented promise.
- A background subagent's request is different: the hook runs first and the prompt appears only once every hook has returned without a decision. Holding that hook would hide the prompt from the person.
- In `claude -p` the session waits for the hook (there is no dialog), so a hook that holds would hold the run.
- The session record `<config dir>/sessions/<pid>.json` says `status: "waiting"` (`waitingFor` `input needed` or `permission prompt`) while a question or a prompt is on screen, `idle` while the session waits for a prompt, and `busy` while a turn runs, including in `claude -p` and while a background subagent's hook runs. It is written about 20 to 30 ms before the hook starts. `statusUpdatedAt` changes when the dialog ends or another takes its place (two prompts in a row stayed `waiting` with a new time) and stayed the same for the 11 minutes one prompt waited.
- A `Stop` command hook with `asyncRewake: true` that exits 2 wakes the idle session (also ADR-0076), with no background work too: the wake-up is a `<task-notification>` that holds the hook's stderr, and the turn it starts ends with `stop_hook_active: true`. When the person typed before that, the record left `idle` within a second.
- The `Notification` hook (`permission_prompt`, `idle_prompt`) cannot decide anything (https://code.claude.com/docs/en/hooks#notification), and Claude Code has no setting that answers a question after a while.

Codex (codex-cli 0.169.0, from its documentation only, not tried): its `PermissionRequest` hook "can allow the request, deny the request, or decline to decide and let the normal approval prompt continue" (https://developers.openai.com/codex/hooks), so it runs before the prompt shows, and `request_user_input` has only `PreToolUse`. Nothing reaches a Codex question that is already on screen.

Reference practice: chat tools mark a person away after a stretch without activity (Slack's API docs: "after 10 minutes" without activity, https://docs.slack.dev/apis/web-api/user-presence-and-status), and Unattended Mode itself treats "nobody typed for 30 minutes" as nobody here.

Options considered:

- Simulating keys into the terminal. Rejected: not a supported channel, and it would answer on the person's behalf.
- Answering with the first option or the one marked recommended (`allow` with `updatedInput.answers`). Rejected, as in ADR-0058: the session shows "User answered", the model reads it as the person's choice, and `AskUserQuestion` has no field that says which option is recommended. A denial with Unattended Mode's reason lets the model take the recommended option where the choice can be undone and skip the rest.
- Asking with a deadline up front (a `PreToolUse` hook that holds the question and asks the person elsewhere). Rejected: the question would not be on screen where the person is.
- Watching the dialog from the `PermissionRequest` hook and denying it once it has waited long enough. Chosen, guarded by the session record so that the hook holds only what is on screen.

## Decision

- **Answer Wait**: config `unattended.answerWait`, whole minutes from 1 to 120, or `false` for never; not set means 10. `sideby unattended wait <minutes>|off` and the Panel's Unattended page ("If nobody answers") set it; `sideby unattended --json` shows it as `answerWait` (`null` for never).
- In a Claude session sideby started, `unattended-hook`'s `PermissionRequest` entry, when the request is not refused at once (the session is an Attended Session, or the mode is off), watches what is on screen: only without `agent_id`, only when the record of its parent process (`<CLAUDE_CONFIG_DIR or ~/.claude>/sessions/<ppid>.json`, read without following a link, only `sessionId`, `status` and `statusUpdatedAt`) names its session and shows `waiting` within 2 seconds, put up no later than the hook began. It looks again every 3 seconds and lets the dialog be as soon as the record changes (another `status` or `statusUpdatedAt`), cannot be read, the Host is gone, or the wait is set to never. Once the dialog has waited the Answer Wait and Unattended Mode is on (globally or for this `--unattended` session; an Attended Session counts as on here, since nobody answered), it denies: the question with Unattended Mode's reason, the prompt with its permission reason, each opening with how long it waited, and keeps a Pending Decision of the same kind with `waited` (minutes). While the mode is off it keeps waiting and acts once the mode comes on. It never prints `allow`.
- The entry's `timeout` becomes 43200 seconds (12 hours), so a question shown at 18:00 still goes on when a Slot begins at 23:00. Its quick answers are unchanged.
- A second `Stop` entry, `sideby unattended-hook claude StopWait`, runs in the background (`asyncRewake: true`, `timeout` 43200). When the turn ended on a question (`endingQuestion`, ADR-0058) with `stop_hook_active` exactly `false`, the wait is not never and the session is not unattended right now (the first `Stop` entry already keeps that turn going), it watches the record for `idle` the same way. Once nobody replied for the Answer Wait and the mode is on, it keeps the question as a Pending Decision with `waited` and exits 2 with a note that says nobody replied, that the note is not the user's reply, and Unattended Mode's instructions. A prompt someone typed after this `Stop` (the Attended Session's record noted later than the hook began) also ends the watch, so a hook that first read the record after the reply's turn had already ended does not take that turn's `idle` for its own.
- A permission watch takes a `waiting` record only when its `statusUpdatedAt` is no later than when the hook began: the dialog of this request was on screen before the hook started, so a later one is another dialog (the person answered this one meanwhile) and is never taken for it.
- Both watches look once more just before they keep the Pending Decision and again after, with the wait and the mode read afresh: the same record and the Host there, the wait as set now passed and the mode on. A dialog that ended or a wait set to never lets it be; a wait made longer that has not passed, or the mode off, goes on watching the same dialog. A decision kept before such a change is taken back. What remains is the moment between the last check and the Host reading the answer, where the person's answer applies (see Context).
- Pending Decisions get the optional field `waited`. Deduplication keeps one refused at once apart from one that waited.
- On by default (10 minutes) because it acts only while Unattended Mode is on, which the user turned on or scheduled to mean "do not wait for me", and it only gives a present person a 10-minute window before what the mode already does to every other session at once. 10 minutes is long enough to read and answer a question at the desk and to come back from a short break, and short against a night: the first question of a night costs at most 10 minutes instead of the rest of the night.

## Consequences

- A person who walks away from a question finds the session moved on with the recommended choice and the question listed under "Waiting for you", with how long it waited. A person at the desk sees no change.
- It depends on two observed behaviours of Claude Code: the `PermissionRequest` hook running beside the dialog in a terminal session, and the session record's `status`. If a version runs the hook before the dialog, the record does not say `waiting` when the hook starts and the hook lets the request be at once: the question waits for the person, as before this ADR. If the record changes shape, the same happens. Either failure keeps today's behaviour, never answers early.
- A question that waits holds one small background process (polling two small files every 3 seconds) until it is answered, the session ends, or Claude Code's 12-hour timeout ends it; one per question or prompt on screen, and one per turn that ended on a question.
- A background subagent's prompt in an Attended Session still waits for the person: Claude Code shows it only after the hooks. Codex questions and approval prompts, Grok, pi and sessions started without sideby are not covered.
- Sessions started before this change keep the old entries (no wait, and Claude Code's 10-minute default `timeout`) until they start again.
- `unattended-hook` now reads one Host file, the session's own record, and imports one more leaf module (`core/unattended-wait.ts`); `docs/agents/host-directories.md` and the import walk in `src/unattended/hook.test.ts` say so.
- End to end on 2026-11-16, Claude Code 2.1.325 started by `sideby run` as an API Account whose `proxy.env` pointed at the fake server, Unattended Mode on, `answerWait: 1` and a prompt typed in tmux: a question went on after 1 minute with "No answer after 1 minute", a Bash prompt was refused after 1 minute and its command did not run, a turn that ended on "Should I use React?" was woken after 1 minute, a question answered after 6 seconds kept nothing and its hook ended, and `sideby unattended pending` listed each one with "no answer for 1 min".
