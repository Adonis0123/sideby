# ADR 0081: Share Claude project memory through the Main Account, opt-in, by naming the real path at Launch

Date: 2026-11-20 · Status: accepted

## Context

Claude Code writes auto memory to `<config dir>/projects/<project>/memory/`, where `<project>` comes from the git repository (every worktree and subfolder of one repository shares it; outside a repository, the project root). Each Claude Account has its own config directory, so a user who runs several Accounts keeps one memory per Account for the same Project. When work moves to another Account (a Handoff, a Pick Command, a limit), the new Account does not see what the old one learned. A user with many Accounts typically ends up with the same Project's memory split across several of them, each copy knowing a different part.

Claude Code's documentation (https://code.claude.com/docs/en/memory) says `autoMemoryDirectory` changes where auto memory is written, that it "must be an absolute path or start with `~/`", and that it is read from "user, project, local, policy, or `--settings`". When set, it is one directory for every Project: the Host adds no per-Project subfolder. `CLAUDE_CONFIG_DIR` moves the default location. No lock protects memory files against two sessions writing at once.

Tried with Claude Code 2.1.328 on 2026-11-20, a second Account started directly (no `--dangerously-skip-permissions`, `--setting-sources project`), headless, a negative control write outside the working folder denied:

- The Account's `projects/<project>/memory` as a link to the Main Account's: memory writes **and** the read of `MEMORY.md` were denied, in permission mode `default` and `auto`. Auto memory names the linked path; the permission check resolves it outside the allowed folders. Matches anthropics/claude-code#108770 (open, reported on 2.1.322 for a linked `projects/`).
- `--settings '{"autoMemoryDirectory":"~/.claude/projects/<project>/memory"}'`: writes went to the Main Account's real path, earlier memory there was read, nothing was denied in either mode, and no memory folder appeared in the Account.

Ways to share:

- Link `projects/` or each `projects/<project>/memory` to the Main Account. Rejected: denied writes as above, and a background subagent that cannot show the prompt hangs.
- Set `autoMemoryDirectory` in the shared user `settings.json`. Rejected: one folder for every Project mixes their memory.
- One `extraSharedItems` entry per Project. Rejected: a real folder blocks a `link`, and every new Project needs a hand-written entry.
- Name the Main Account's real per-Project path at Launch, and fold memory written outside sideby into the Main Account with Doctor. Chosen.

## Decision

- Config `claude.shareMemory` (boolean, default off). Off: nothing is read, passed or moved.
- On, for every interactive Claude Launch sideby prepares (the same set as Carried Trust, ADR-0078), sideby derives the Project's memory folder name from its working folder the way Claude Code does, and passes `--settings` with `autoMemoryDirectory` set to that folder under the Main Account. It does not override a value the user already set at a higher-priority scope (policy, or their own `--settings`).
- Memory written by sessions sideby did not start stays in the Account. Doctor reports it, and its Fix folds it into the Main Account: a Project the Main Account lacks moves whole; a file with the same name and other content is kept as `<name>.<account>.md`; `MEMORY.md` indexes are merged without duplicate lines; the emptied Account folder goes to the system trash. A Project with a Live Session of that Account is skipped until it ends.
- This Fix moves real files out of an Account folder. It is the only exception to "a Fix never replaces a real file where a link is expected": nothing is replaced or lost, the trash keeps the original, and the user turned the feature on.
- Doctor warns when the folder name sideby derives for a Project differs from the folder Claude Code created for it, and when a `MEMORY.md` lists a file that is missing or misses a file that exists.
- Like every user-facing feature, it ships in the Panel (Settings switch, with what changes and how to undo), a `sideby` command with `--json`, and the shipped skill.

### Implementation choices (2026-11-20)

- **The folder name.** Read from Claude Code 2.1.328's bundled code: every character that is not an ASCII letter or digit becomes `-`; a name longer than 200 characters is cut at 200 and gets `-` plus the base-36 absolute value of the 32-bit `(h << 5) - h + c` hash of the whole path (UTF-16 units). The Project key is found with Carried Trust's file-only rule (`trustRoot`, ADR-0078: no `git` is run); `unclear` (a submodule, a separate git folder) passes nothing, because a wrong guess would split memory while the Account's own copy is folded later anyway. Session History's transcript path uses the same function.
- **One `--settings` file.** Claude Code takes one `--settings`, and Auto Handoff refuses to start where it sees one the user gave. `autoMemoryDirectory` therefore goes into the file sideby already writes for its session hooks (written even without hooks), kept as the Launch's session settings so Auto Handoff strips it before its eligibility check and carries it into its merged file. The file name holds a hash of the memory path, so two Projects never share a file.
- **Who gets it.** Not the Main Account (that folder is already its own; this also leaves Claude Code's own naming visible for the mismatch check), not a headless run, not `sideby login`. A user `--settings` (from the command line or the Account's configured arguments) gets no second one, and the Launch notice says so once, like Unattended Mode and Progress Reminders. Claude Code reads `autoMemoryDirectory` from policy, then `--settings`, then local, project and user settings, so a user-level value is overridden at these Launches; policy still wins.
- **Doctor findings.** One `warn` `memory.unfolded` per Account (not per Project, which would list dozens of rows), fixable; a linked memory folder is `memory.link`, report-only. The Main Account's checks are general warnings: `memory.index` and `memory.name-mismatch`. None is `fail`, so Doctor's exit code does not change.
- **How a fold moves files.** A Project the Main Account lacks is renamed into place whole (one rename takes whatever the folder holds at that moment). Otherwise every file is read once (bytes, hash, times) and each copy is written from that read into a temp file beside its target, fsynced, its times set (Claude Code shows how old a memory is), then hard-linked to its name, which fails when the name is taken, and the temp file is removed either way: a copy is never half-written under its final name and never written over another file, so a retry after a failed write finds the name free. Every target name is decided before anything is written: a different file of the same name gets the next `<name>.<account>.md`, `-2`, `-3`… that neither folder uses and this fold has not given out, so an Account holding both `a.md` and `a.work.md` cannot chain into `a.work.work.md`. `MEMORY.md` lines the Main Account lacks are appended in order (trailing spaces ignored) through `writeIfUnchanged`, after one pass that resolves each link against the memory folder (`a.md`, `./a.md`, `../memory/a.md`, `a.md#section`) and points the ones to a renamed file at its new name, keeping the `#fragment`; the index check resolves links the same way.
- **Taking files out of the Account, per file.** The Account's folder is never trashed as a whole: a check followed by a move of the folder leaves a moment in which a new file would go to the trash unseen. Each file that was read (`MEMORY.md` included) is renamed on its own into `memory-folded-by-sideby` beside the memory folder, one atomic step after which a write by its name makes a new file in the memory folder, then hashed there: still what was copied or merged, it stays out; changed, it goes back into the memory folder without replacing anything (a hard link, which fails when the name is taken, then the stage name removed), as `<name>.changed.md` (the next free one) when a new file took its name. When a changed file cannot go back at all, nothing goes to the trash, the checked files go back too, and the Fix says where the file is. So the stage holds only files that match their copies when it goes to the trash as one item; the memory folder is then removed with `rmdir`, which fails when anything new appeared, so that memory stays for the next fold and the Fix reports the Project as moved in part (`partial`). A stage left by a fold that stopped halfway is emptied back into the memory folder the same way, never over a file there, before the next fold reads it; one that cannot be emptied stops that Project and the Fix says so. A stage that still holds files counts as memory of the Account even when the memory folder is empty or gone (a fold that stopped right after staging its last file), and the memory folder is created again so the stage can be emptied into it. One limit stays: a process that already holds a file open can still write to it after the hash; only the Live Session check covers that.
- **Live Sessions.** Read inside the Fix from Claude's `sessions/<pid>.json` files and the process list (`ps`); a session's working folder, its real path and its Project count. It fails closed: a record of a running process that cannot be read (Claude Code rewriting it at that moment), lacks its session id, working folder or start time, or a process list that cannot be read means sideby cannot tell which Projects are in use, and nothing of that Account is moved; the Fix says why. Only a record whose process is gone, or whose pid now belongs to a process with another start time, counts as ended.
- **Off reads nothing.** `sideby memory` while off reads only the config and sideby's own records: it does not even list the Accounts, which walks the Host folders.
- **The trash.** The `trash` command on PATH (macOS ships `/usr/bin/trash`; Linux has `trash-cli`), only while HOME is the user's own home by the password database, not `$HOME`, so a demo or test HOME never reaches the real trash. Otherwise the folder moves into `<state>/memory/trash/` and the Fix names it. Nothing is ever deleted.
- **The mismatch heuristic.** A Project folder that holds memory and session files, where no `cwd` in the first or last records of its three newest session files names it by sideby's rule: Claude Code names session folders and memory folders with the same function, so this means its rule changed. Only working folders that still exist count, and both ends of a file are read, because a resumed session keeps the records (and `cwd`) of the folder it came from, and a moved project's folder is often renamed by hand to follow it; tried read-only on 2026-11-20 against 13 Claude Accounts with 66 memory folders, where a first-`cwd` rule flagged such a renamed folder and this rule flags none. Up to 40 folders, the first and last 64 KB of each file, only `cwd` is kept. It does not catch a change in how Claude Code picks the Project root.
- **Records.** Each fold is recorded in `<state>/memory/folded.json` (Account, Project folder name, file count without `MEMORY.md`, time; at most 500), for `sideby memory` and the Panel; never a file's text. The Panel's polled state reads only the config and these records.

## Consequences

- A user who turns it on sees one memory per Project in every Claude Account that sideby starts. Sessions started with plain `claude` or by an app that picks the Account itself write their own copy until the next Doctor Fix.
- Two Accounts writing the same Project at once can overwrite `MEMORY.md`; Doctor's index check finds the damage, it does not prevent it.
- The folder name follows Claude Code's current rule. If Claude Code changes it, the mismatch warning fires and the derivation must follow. Re-check the probe above with new Claude Code releases, together with anthropics/claude-code#108770: if linked memory paths stop being denied, a link would also cover sessions sideby did not start.
- Preferences that apply to every Project still land in one Project's memory. Promoting them into the shared rules file is outside sideby.
