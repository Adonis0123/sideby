# 上下文调优：真实数据验证记录

依据 spec §3.18 和验收第 16 条。只读：对作者本机的真实 HOME 只跑了 `sideby tune` 和面板里的「上下文调优」，没有改任何 Host 配置。下面只记数字，不记路径、邮箱和对话内容。

## 做法

1. 本地构建后 `npm pack` 再 `npm i -g`，让门户（`accounts.localhost:17333`，里面嵌着面板）换上新构建；门户进程没有重启。
2. 在那个地址上点账号菜单的「Context tuning」，看正常、慢加载、出错三种状态。出错状态用页面自己的 `fetch` 在浏览器里临时改成返回 500。
3. 用 `sideby tune --json` 看全部账号，并另写一个只读脚本（读 `projects/**/*.jsonl`，只输出数字）统计自动压缩的触发点和压缩后的额外增长。

## 结果

| 项目 | 结果 |
|---|---|
| 门户页面 | 菜单里出现「Context tuning」；对话框先显示「Replaying your sessions…」，之后显示结果；出错时显示「sideby hit an error: …」和「Retry」 |
| 真实账号的结果（7 天窗口） | 4 个 Claude 模型有足够调用（337–4973 次）：估算最省的阈值 80K–120K，比现在观测到的自动压缩点（中位数 237K–418K）少约 16%–39% 的加权 token。Codex 只观测：15 次压缩，压缩时上下文中位数 235K |
| 自动压缩的触发点 | 本机 31 次自动压缩，压缩前 token：p10 约 204K，中位数约 316K，p90 约 687K，最大约 967K。没有一个固定值，所以「当前阈值」不能由一个数反推 |
| 压缩后重读被丢内容的开销 | 压缩后 8 轮内的额外增长，中位数约为被丢 token 的 1.7%（p25 1.1%，p75 2.8%）。很小，重放里不计这一项 |
| 已修的问题 | ① 候选阈值原来只到窗口的 40%，1M 窗口的账号被截掉最低点，给出的 400K 是搜索边界；现在 4%–95%，并且最低点落在最低候选时不给建议（`no-optimum`）。② `<synthetic>`（Claude Code 的占位行）被当成一个模型，已排除 |

## 未验证（UNVERIFIED）

| 项目 | 为什么 | 怎么验证 |
|---|---|---|
| `autoCompactWindow` 的确切含义 | 没有官方文档；第三方资料说它是压缩所依据的窗口，真实触发点可能略低 | 把某个账号设成推荐值，观察之后几次自动压缩的 `preTokens` 离它多近 |
| 推荐值是否真的省 | 重放只算 token，不算压缩丢掉的上下文带来的质量损失，也没有对照实验 | 设置后比较一周前后同账号的用量 |
| 阈值低到 80K 的实际体验 | 估算不含「丢上下文」的代价 | 先在一个账号上试 |
| 1M 窗口的判断 | 窗口从记录推断（出现过超过 200K 的上下文就当 1M） | 之后若 Host 的记录里有窗口大小，改用它 |
