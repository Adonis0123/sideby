# sideby v0.1 设计

日期：2026-10-05 · 状态：已按 Codex 审核修订（§9） · 术语见 `CONTEXT.md` · 决策见 `docs/adr/`

## 1 目标

让同时持有多个 AI coding 账号的人，在终端里把它们**并排**跑起来，做到四点：不串号；skills、hooks、规则只维护一份；坏了一条命令修好；每个账号的额度和用量一屏看完。

一句话定位：**Run every AI coding account side by side.**

### 1.1 用户与场景

| 用户 | 典型账号组合 | 今天的痛点（证据） |
|---|---|---|
| cc-switch / magpie 用户，想同时开多个账号 | 1 个 Claude 订阅 + DeepSeek/GLM key + 中转 | 切换会改全局配置，同一时间只有一个生效（cc-switch #1105、#1106、#2908） |
| 工作号和个人号分开用 | 2 个 Claude 订阅、2 个 ChatGPT 号 | 手工维护 `CLAUDE_CONFIG_DIR` 和 symlink，时间一长就漂移 |
| 多个 CLI 一起用 | Claude Code + Codex + Grok + pi | 每家的目录约定和坑都不一样 |

### 1.2 体验原则

- **什么都不用额外装。** 只要有 Node 和宿主 CLI 就能用。用量由 sideby 直接读宿主的本地记录。
- **没有数据时要说清楚原因。** 是「还没开过会话」「这个宿主没有公开来源」，还是「格式变了」，每种情况分开提示。
- **每条错误都告诉用户下一步怎么做。** 错误信息里只出现路径和变量名，永不出现凭据的值。

### 1.3 成功标准

- 只装了 `~/.claude` 的新用户，从 `npx sideby` 开始，3 条命令以内让第二个账号并排跑起来。
- 维护者原有的自制多账号脚本，其全部行为在 sideby 里都有对应测试（对照表留在维护者本机，不入库）。
- README 首图是面板截图，显示多个账号的额度。

## 2 范围

### 2.1 v0.1 做

- 四个内置家族：claude、codex、grok、pi，全部以插件形式实现。
- CLI：`list`、`run`、`new`、`login`、`doctor`、`quota`、`ui`、`shell-init`、`plugins`、`quota setup|teardown claude`。
- 本地插件：Family Plugin，以及 `launch.before`、`account.create.before`、`account.created`、`doctor.check` 四类 Hook。
- 面板：账号卡片（额度、用量、健康）、体检加一键修复、新建账号。由 `createPanelHandler` 提供，`sideby ui` 独立运行。
- 额度：Claude 订阅读 statusline 缓存，Codex 读本地 rollout。
- 用量：内置读取 Claude 和 Codex 的本地会话记录，不依赖任何外部工具。
- AI 配套：`AGENTS.md`、`CLAUDE.md` 链接、`--json` 加 JSON Schema、可安装 skill、`llms.txt`。
- 发布：CI 加 tag 触发的 trusted publishing workflow（就绪，但本轮不推送、不发布）。
- 平台：macOS、Linux。

## 3 架构

### 3.1 仓库与构建

```
sideby/
├── AGENTS.md · CLAUDE.md（内容为 `@AGENTS.md`）· CONTEXT.md · README.md · README.zh-CN.md · llms.txt
├── docs/{adr,specs,plans,verification}/
├── schemas/                  # 由 TypeBox 定义生成的 JSON Schema
├── skills/sideby/SKILL.md
├── src/
│   ├── cli/                  # 参数解析和各子命令（只做 I/O）
│   ├── core/                 # 路径、配置、账号发现、Secret File、Share Mode、doctor、launch、原子写入
│   ├── plugins/              # 加载器、信任校验、事件总线
│   ├── families/{claude,codex,grok,pi}/
│   ├── quota/                # Claude statusline 缓存，Codex rollout 读取
│   ├── panel/                # createPanelHandler 和内联页面
│   └── index.ts              # 库入口：createPanelHandler 和插件类型
├── testing/                  # 假 HOME、假宿主 bin、插件测试工具
├── .github/workflows/{ci,release}.yml
└── scripts/leak-check.sh
```

- **构建**：源码是 `.ts`，用 `tsc` 编译到 `dist/`，开启 `rewriteRelativeImportExtensions`。原因是 Node 拒绝对 `node_modules` 里的 `.ts` 做类型剥离（本机 Node 22.22.3 实测报 `ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING`）。用户的插件在 `node_modules` 之外，可以直接写 `.ts`。
- **开发和测试**：直接用 `node --test` 跑 `.ts`，不需要先构建。
- **依赖**：运行时只有 `typebox`；开发时有 `typescript`、`@biomejs/biome`、`@types/node`。
- **启动检查**：Node 低于 22.18 时，打印升级提示并以 1 退出。`--help` 和 `--version` 也走这个检查。`package.json` 的 `engines.node` 只让 npm 打出 `EBADENGINE` 警告，拦人的是这里。`statusline-tap` 除外：Claude Code 每次刷新 status line 都会调用它，版本不够时也必须继续执行原来的命令，不能把这次刷新丢掉。

### 3.2 账号模型

| 家族 | Main Account | 其他 Account | 选择变量 | 宿主命令 |
|---|---|---|---|---|
| claude | `~/.claude` | `~/.claude-<name>` | `CLAUDE_CONFIG_DIR` | `claude` |
| codex | `~/.codex` | `~/.codex-<name>` | `CODEX_HOME` | `codex` |
| grok | `~/.grok` | `~/.grok-<name>` | `GROK_HOME` | `grok` |
| pi | `~/.pi/agent` | `~/.pi-<name>/agent` | `PI_CODING_AGENT_DIR` | `pi` |

- 账号名 `<name>` 必须匹配 `^[a-z0-9][a-z0-9-]{0,31}$`。现有的 `004` 本身就是合法名字。
- 账号靠通配发现。不符合命名规则的目录、config 里 `ignore` 的目录，以及非目录项，都不算账号。
- 名字符合规则的目录，还必须满足以下之一才算账号：有 `proxy.env`；至少有一个该家族的共享项；或者是空目录（刚建好）。这样能排除别的工具的配置目录，例如 claude-code-router 的 `~/.claude-code-router`。名字看起来像备份（含 `bak`、`backup`、`old`、`tmp`）时，doctor 给一条 warn，建议加进 `ignore`。
- Main Account 的名字固定为 `main`，启动时不设选择变量。不做「某个编号就是主目录」这类特殊映射；需要旧习惯的用户用 config 的 `aliases`（例如 `codex001 → codex:main`）。
- **引用账号**：写 `<family>:<name>`。名字在所有家族里唯一时，可以只写 `<name>`；有歧义就报错，并列出候选。

**API 账号**：账号目录里有 `proxy.env`。

- 解析规则是 dotenv 子集：`KEY=VALUE`、可选的 `export ` 前缀、单引号或双引号、`#` 注释。不经过 shell，所以不支持命令替换。`$NAME` 和 `${NAME}`（不加引号或双引号里）只展开同一文件前面已定义的变量，以及 `HOME`、`USER`、`LOGNAME`、`TMPDIR`、`XDG_*_HOME` 这几个不含凭据的位置变量；其他环境变量一律不读，找不到就报错并给出行号。单引号里原样保留。
- 解析出错时报出行号，不报内容。权限不是 600 时拒绝启动，并提示 `chmod 600 <path>`。

### 3.3 Share Mode

| Mode | 健康 | `--fix` | 绝不做 |
|---|---|---|---|
| `link` | 是 symlink，解析后指向主目录对应项 | 缺失时补 link | 位置上是真文件或真目录时，只报告，并给出 `mv <x> <x>.local && ln -s …` |
| `copy` | 是真文件或真目录，内容与主目录一致 | 缺失或过期时复制；是指向主目录的 symlink 时，先删 link 再复制 | 永远不通过 symlink 写到主目录；类型不一致时不动 |
| `link-or-copy` | symlink，或内容一致的副本 | 副本过期时镜像主目录 | 主目录为空或类型不一致时不动 |
| `link-or-local` | symlink，或任意真文件 | 缺失时补 link | 不比较内容，不覆盖 |
| `local` | 是真文件，不比较内容 | 缺失时从主目录复制一份 | 是 symlink 时只报告 |
| `local-if-api` | 订阅账号按 `link-or-copy` 判断；API 账号必须是自己的真文件 | 只修订阅账号 | API 账号的 symlink 或缺失，只报告 |
| `info` | 不计数 | 不处理 | — |
| `json-key` | 账号自己文件里的某个 JSON 键，与主文件一致 | 只替换这一个键；写入前后比较文件 hash，期间文件被改动就放弃 | 会让账号已有条目减少（包括清空）时，没有 `--force` 就拒绝；文件是 symlink、不是 JSON 对象、该键不是对象时，`--force` 也拒绝 |

通用规则（与旧实现一致，逐条有测试）：

- 主目录里没有的项：没什么可共享，不报告、不计入分母、不自动创建（2026-10-05 面板验收后调整：多数用户没有 `commands`、`themes` 这类目录，报 warn 只是噪音）。
- symlink 永不改指向，分三种情况：
  - 悬空链接：报 fail。
  - 指向别处但目标存在：允许链接的项报 warn（用户有意为之）；宿主不允许链接的项（`copy`、`local`、`noSymlink`）报 fail。
  - 相对路径的链接只要解析后等价，就算健康。
- 共享项路径必须是相对路径，不能含 `..`。每次修复在执行的那一刻都会校验写入位置：解析父目录的真实路径后，必须仍在账号目录内，父目录是指向别处的链接时拒绝。
- 复制时递归处理，保留权限位和隐藏文件，目录里的 symlink 原样复制为 symlink。
- 所有写入先写同目录的临时文件（权限 600），再 rename；凭据文件写完后 chmod 600。
- 条件写入（`json-key`、statusline teardown）会在写入前、以及 rename 前各核对一次 hash。普通文件做不到真正的比较并交换，这只是把和宿主同时写同一个文件的冲突窗口缩到最小。
- 已知限制：写入位置的校验和真正写入之间仍有极短的时间窗，期间父目录理论上可能被换成链接。Node 没有按目录句柄写入的 API（如 `openat`），无法彻底消除；能利用这个窗口的进程本身已经能直接改用户 HOME 下的这些文件，所以不构成新的越权。
- 已知取舍：名字符合规则的空目录会被当作刚建好的账号，偶尔会把无关的同名空目录列出来，用户可以把它加进 `ignore`。
- statusline 的 diff 只展示 `statusLine` 这一个对象的前后变化，`settings.json` 其余内容（常含 `env` 里的 API key）永远不进 diff。
- 凭据文件解析失败时，错误信息不引用文件内容（Node 的 `JSON.parse` 报错会带出输入片段）。
- 凭据文件（`proxy.env`、`.claude.json`、`auth.json`）只检查类型和权限是否为 600，`--fix` 会改回 600。内容只读 `json-key` 指定的那一个键。
- 备份残留（深度 1 下的 `*.bak*`、`*backup*`、`*.tmp*`）只计数，不处理。

### 3.4 内置家族

经过测试的版本：Claude Code 2.1.289、codex-cli 0.160.0、grok 1.0.46、pi 1.0.2（2026-10-05 在维护者本机）。

| 家族 | Hijack Variables | 共享项（Mode） | 登录命令 | 登录态判断（不联网、不读凭据值） |
|---|---|---|---|---|
| claude | `ANTHROPIC_{API_KEY,AUTH_TOKEN,BASE_URL,MODEL,SMALL_FAST_MODEL,DEFAULT_HAIKU_MODEL,DEFAULT_SONNET_MODEL,DEFAULT_OPUS_MODEL}` | `settings.json`、`settings.local.json`、`skills`、`commands`、`plugins`、`hooks`、`themes`、`CLAUDE.md`（link）；`.claude.json#mcpServers`（json-key） | `claude auth login`（已核实） | 账号的 `.claude.json` 里有 `oauthAccount` 键 |
| codex | `OPENAI_API_KEY`、`OPENAI_BASE_URL`、`CODEX_API_BASE_URL` | `AGENTS.md`、`hooks.json`、`plugins`、`rules`、`skills`（link）；`config.toml`（local-if-api）；`auth.json`（info） | `codex login`（已核实） | `auth.json` 存在 |
| grok | `XAI_API_KEY`、`GROK_MODELS_BASE_URL` | `skills`、`installed-plugins`（link）；`hooks`、`hooks-paths`（copy）；`trusted_folders.toml`（local）；`config.toml`（local-if-api，订阅账号在 Grok 下按 copy 判断）；`auth.json`（info，但它是 symlink 时 fail） | `grok login`（已核实） | `auth.json` 是真文件 |
| pi | `ANTHROPIC_API_KEY`、`ANTHROPIC_AUTH_TOKEN`、`ANTHROPIC_BASE_URL`、`OPENAI_API_KEY`、`OPENAI_BASE_URL` | `AGENTS.md`（link）；`auth.json`（info） | 进入 pi 后执行 `/login` | `auth.json` 存在 |

其他约束：

- **codex**：非 main 账号默认加 `-c cli_auth_credentials_store="file"`，用户参数里已经有这个键时不加。
- **grok**：hooks 等路径在沙箱里不允许 symlink，doctor 的提示会引用宿主原话。
- **pi**：账号目录多一层 `agent/`；pi 专属的模板复制等工作交给 pi 侧的插件（通过 `account.created`、`doctor.check`）。
- **个人项**：`statusline-command.sh`、`scripts` 这类属于个人的共享项不进内置清单，用户可在 config 的 `extraSharedItems` 里自己加。
- **宿主未安装**：`list` 照常列出账号，只给该家族标「宿主未安装」；`run` 报错，并给出官方安装文档的链接。FamilyDef 可选 `installCommand`：官方的一行安装命令（pi 为 `curl -fsSL https://pi.dev/install.sh | sh`）。有它时，报错、`list`、`families` 和面板都先给这条命令（面板带复制按钮），再给链接；sideby 只显示，从不自己运行它。
- **安装已损坏**：PATH 上找到了 `bin`，但不能执行（多见于升级中断后悬空的链接），家族信息多一个 `brokenBin`（找到的那个路径），`installed` 仍为 false。面板和 CLI 说「安装已损坏，重新安装即可」，不说「没安装」，并给同样的安装命令或链接。只加字段，`schemaVersion` 不变。

### 3.5 启动

```mermaid
sequenceDiagram
  participant U as 用户
  participant S as sideby run
  participant P as 插件 launch.before
  participant H as 宿主 CLI
  U->>S: sideby run work -- --resume
  S->>S: 解析账号；复制当前环境
  S->>S: 删除 Hijack Variables
  S->>S: API 账号：校验 600，解析 proxy.env，合并进 env
  S->>S: 设置选择变量（main 不设）
  S->>P: 依次调用，每个 30 秒超时，可改 env/args，抛错即中止
  S->>H: spawn(bin, familyArgs + accountArgs + aliasArgs + userArgs, stdio inherit)
  H-->>S: 退出
  S-->>U: 退出码
```

- **账号标识**（2026-10-08 补充）：每次 Launch（`run`、`next`、`login`，以及路由到非主账号的 `resume`）都设 `SIDEBY_ACCOUNT=<ref>` 和 `SIDEBY_LABEL`，给宿主的状态栏、提示符或 hook 显示是哪个账号。`SIDEBY_LABEL` 取法：通过短命令启动时就是那个短命令；否则取该账号的短命令（不带宿主参数的优先，再按名字排序）；都没有就是 ref。两者每次都重设，不沿用继承来的值，在 `launch.before` 之前设好（hook 可以改）。`resume` 原样运行宿主时不设，等于没有 sideby。显示时应先核对 `SIDEBY_ACCOUNT` 的家族前缀，因为在一个宿主里再开另一个宿主会继承这两个变量。各宿主怎么显示见 `docs/guide/usage.md` 的「Show which account a session is」一节。
  - **终端标题**：config `accountTitle: true`（默认关）时，Launch 在终端（stdout 是 TTY）上先写 OSC 0，把标题设成 `[<SIDEBY_LABEL>]`，去掉控制字符。家族的可选字段 `keepTitle: { args, key }` 给出让宿主这次不改标题的参数，加在 `defaultArgs` 之后；用户参数里已含 `key` 时不加。Codex 是 `-c tui.terminal_title=[]`（它的状态栏和标题只接受内置项，这是唯一能常驻显示账号的位置）。Claude Code 和 Grok Build 用状态栏显示，不声明 `keepTitle`。
- **参数顺序**：家族默认参数 → config 里该账号的 `args` → 短命令的 `args`（只在用短命令 `run` 时）→ `--` 之后的用户参数。家族的 `defaultArgs` 把短命令参数和用户参数一起当作用户选择看待。
- **父 shell**：环境永不修改。
- **信号**（macOS 和 Linux）：
  - 子进程运行期间，sideby 忽略 `SIGINT`、`SIGQUIT`。终端会把它们直接发给前台进程组，宿主照常能收到。
  - `SIGTSTP`（Ctrl-Z）保持默认动作：sideby 和宿主一起暂停，`fg` 时一起恢复。（OCR 审查发现：如果忽略它，就只有宿主被暂停，shell 会一直等 sideby。）
  - `SIGTERM`、`SIGHUP` 转发给子进程一次，之后等它退出。
  - 窗口大小变化不用处理，宿主共享同一个 TTY。
  - 子进程退出后，sideby 移除所有监听，不再转发。
- **退出码**：子进程正常退出时，原样返回它的退出码；子进程被信号终止时，返回 `128 + 信号编号`。sideby 自身出错返回 1，用法错误返回 2。
- **危险参数**：不再默认带任何危险参数。旧实现硬编码的 `--dangerously-skip-permissions`，改由 config 给单个账号显式配置。
- **登录**：`sideby login <account>` 用同样的环境运行该家族的登录命令。
- **shell-init**：`sideby shell-init zsh|bash` 输出 shell 函数，包括 config 里 `aliases` 定义的短名（例如 `cc004`）。需要指定账号的命令（`run`、`doctor` 等）也接受这些短名；不带冒号时先查 `aliases`。短名的函数调用 `command sideby run '<短名>' -- "$@"`，由 `run` 读取 config，所以改了短名的参数不用重新 source。
- **带参数的短命令**（2026-10-05 补充，ADR-0005）：`aliases` 的值可以是账号 ref 字符串，也可以是 `{ "account": "<ref>", "args": ["--model", "…"] }`。它仍然只启动一个账号，不改登录态和会话（`pi-kimi` 与 `pi001` 共用 `pi:main`）。
  - `args` 只在 `sideby run <短名>` 时插入，位置见「参数顺序」。`login`、`doctor`、`quota` 等命令只把短名解析成账号，忽略 `args`。
  - 短命令不能带环境变量。config 不是 600 文件，env 字段容易装进密钥；要改环境的入口留在用户自己的 shell 里，或写 `launch.before` 插件。
  - `account` 必须是 `<family>:<name>`；短名不能指向另一个短名。
- **`sideby alias add|rm`**（2026-10-05 补充）：给已有账号加、删短命令，供用户和 AI 代替手改 config。
  - `sideby alias add <短名> <账号> [-- host args] [--json]`：账号可以写 ref、唯一名字或已有短名，先解析成磁盘上存在的账号，再保存规范 ref。没有 `--` 参数时写成字符串，与 `new --alias` 一致。已有同名且账号和参数都相同时 `status: exists`；不同时拒绝，提示先 `alias rm`。名字不合法或保留名拒绝。
  - `sideby alias rm <短名> [--json]`：删掉这个键；不存在时 `status: absent`，退出码 0。
  - 写入规则与「短命令随新建账号写入」相同（重新读文件、保留键序、原子写、保持权限、链接写目标、hash 变了拒绝）。写完重写每个 `shellInitFile`，结果记入 `shellInitFiles[]`。
- **短命令随新建账号写入**（2026-10-05 补充）：`sideby new <family> <name> --alias <a>` 和面板 `POST /api/accounts { alias? }` 走同一个 `Runtime.createAccount`。
  - 先校验别名（`ALIAS_NAME`、保留名、config 里已指向别的账号即为占用），不合法时返回 `code: 'alias-invalid'`，什么都不建。
  - 再建账号；之后把 `alias → <family>:<name>` 写进 config 的 `aliases`：重新读文件，保留其他键和顺序（含 `$schema`），2 空格 JSON 加结尾换行，原子写入，保持文件权限（新文件 600），config 是链接时写链接目标。文件不是合法 JSON 或不符合 schema 时拒绝写入，原文件不动。
  - 写别名失败时账号保留，结果里 `alias.added: false`，`message` 写明「账号已建，别名没加上」，`ok` 为 false。
- **shell-init 文件**（2026-10-05 补充）：config 可选 `shellInitFile: { zsh?, bash? }`（绝对路径或 `~/`）。每次 `new`（CLI 或面板）之后，sideby 用 `sideby shell-init <shell>` 的同一份输出原子重写每个配置的文件，保持权限（新文件 644）。已存在且首行不是 shell-init 标题的文件不覆盖，相对路径报错；失败记入 `shellInitFiles[]`，`ok` 为 false。`sideby shell-init [zsh|bash] --write` 按需重写；用 `eval "$(sideby shell-init zsh)"` 的用户不需要配置。
- **面板推断短命令**：只看同一家族已有账号的别名。别名以账号名结尾时，去掉账号名剩下的是前缀（`cc001 → claude:001` 得 `cc`）；不以账号名结尾的（`codex001 → codex:main`）忽略。取出现最多的前缀，建议「前缀 + 新名字」，再按别名规则校验；推断不出时字段留空，不填。

### 3.6 插件

**插件等同于本地任意代码**，拥有 sideby 进程的全部权限。README 和 `sideby plugins` 都要写明这一点。

```
my-plugin/
├── plugin.json      # name、version、description、userConfig（带类型的配置项）
├── index.ts         # export default { name, register(api) {…} } satisfies Plugin
└── index.test.ts    # 用 sideby/testing 测试
```

```ts
import type { Plugin } from 'sideby'   // 只允许 import type（ADR-0002）

export default {
  name: 'litellm-gateway',
  register(api) {
    api.on('launch.before', { family: 'claude' }, async (ctx) => {
      // ctx.account、ctx.env（可改）、ctx.args（可改）、ctx.config
      // 网关没起来时：throw api.abort('网关没起来：…')
    })
  },
} satisfies Plugin
```

| 扩展点 | 时机 | 能做什么 | 超时 |
|---|---|---|---|
| `api.family(def)` | 加载插件时 | 注册家族：目录约定、选择变量、Hijack Variables、默认参数、共享项、登录命令、登录态判断、模型、可选的 `logo`、`readQuota`、`readUsage` | — |
| `launch.before` | 每次 `run`、`login` 之前 | 改 env 和 args，或中止 | 30 秒 |
| `account.create.before` | `new`（CLI 或面板）写入任何文件之前 | 用 `api.abort(msg)` 拒绝新建（例如家族只允许一个非 main 订阅账号）；ctx 为 `{ family, name, api, accounts, config }` | 10 秒 |
| `account.created` | `new` 成功后 | 补文件，打印下一步提示 | 30 秒 |
| `doctor.check` | 检查每个账号时 | 返回 Finding，可附 `fix()` | 10 秒 |

**加载与信任**：

- 加载顺序：内置插件 → `~/.config/sideby/plugins/*` → config 里 `pluginDirs` 列出的路径。`pluginDirs` 只接受绝对路径或以 `~` 开头的路径。
- 加载前校验：插件目录和入口文件必须属于当前用户，且不能被组或其他用户写。不满足就拒绝加载，并说明原因。
- 同名插件，后加载的报冲突，不会覆盖先加载的。
- 插件出错时：错误信息标明插件名。加载失败只影响它自己；`doctor.check` 出错转成该账号的一条 fail Finding；`launch.before` 出错就中止启动；`account.create.before` 出错（含 abort、超时）就中止新建，不写任何文件，CLI 退出码 1，面板返回 400。
- sideby 自己的修复都会校验写入位置必须在账号目录内（§3.3）。插件的 `fix()` 和 `api.fs` 属于插件代码，sideby 管不住它写到哪里（ADR-0002：插件就是本地代码），只保证一个 fix 失败不影响其他 fix。

**内置可选插件 `account-script`**（默认关闭）：

- 账号目录里有 `sideby-before-launch` 文件时，启动前运行它。
- 运行条件：文件属于当前用户、可执行、不能被组或其他用户写。
- 工作目录是账号目录，环境是已准备好的启动环境，超时 25 秒（留在 hook 自身 30 秒上限之内，超时时能给出更具体的报错）。
- 失败就中止启动，错误信息显示它的 stderr 末尾 20 行。

### 3.7 额度与用量

| 家族 | 额度 | 用量（近 7 天 token） |
|---|---|---|

| codex 订阅 | 读 rollout 里的 `token_count.rate_limits` | 每条 `token_count` 事件记它带来的增量：首条是累计值减去继承来的基线（subagent 会话从父线程的累计值开始），累计值回落的事件开始新的一段、记它的全部累计值，其余记增长。只累加事件时间落在 7×24 小时窗口内的增量；文件修改时间只用来跳过不必读的文件，恢复的老会话里窗口外的轮次不计入 |
| grok 订阅 | 问 Grok 自己的 CLI（`_x.ai/billing`，最多每 15 分钟一次），再读本地日志里的额度行，取较新的一份（§3.26） | 显示「这个宿主没有公开来源」 |
| pi | 显示「这个宿主没有公开来源」 | 同左 |
| API 账号 | 不显示 | 同所属家族 |

**按天用量和最近活动**（2026-10-05 面板 v2 补充）：`UsageResult`（`ok`）可选带 `daily` 和 `lastActivityAt`，Claude、Codex 内置读取都给出。

- `daily`：`USAGE_DAYS` 条，以本地日历日 `YYYY-MM-DD` 为键，截止到今天，最早的在前，没有记录的日子为 0。每条记录按自己的时间戳落到本地日期，零点整算新的一天。去重规则与总量相同（Claude 按 `message.id` 取最后一行；Codex 每个事件记它带来的增量，见上表）。总量按 7×24 小时滚动窗口算，最早那天的前半段不在任何一条 `daily` 里，所以各天之和可能小于 `totalTokens`。
- `lastActivityAt`：读取时见到的最新一条记录的时间（ISO），晚于当前时间的记录不算。只读窗口内修改过的文件，所以更早的活动不会出现。

**上下文调优**（2026-10-13 补充）：用同一批本地记录估算 Compaction Threshold，见 §3.18。

**Claude statusline 缓存**：

- **setup**：先展示 diff，用户确认后，把主 `settings.json` 的 `statusLine.command` 包成 `sideby statusline-tap --orig-b64 <base64(原命令)>`（base64 保证原命令的引号和空格不被 shell 二次拆分）。同时在 state 目录记录三样东西：原始字节、原始 hash、包装后的 hash。重复 setup 时检测到已包装，直接提示已开启。
- **teardown**：只有当前文件的 hash 仍等于包装后的 hash 时，才把原始字节原样写回。否则拒绝，给出 diff，并说明「文件在开启后被改过，请手动把 `statusLine.command` 改回原命令」。
- **statusline-tap**：
  - 读 stdin 的 JSON，取 `rate_limits`，写入 `${XDG_STATE_HOME:-~/.local/state}/sideby/quota/claude/<name>.json`。账号由 `CLAUDE_CONFIG_DIR` 反推，没有这个变量就是 `main`。
  - 不让旧数字盖掉新数字（2026-10-14 补充，2026-10-17 改为按会话判断）：同一账号开着几个会话时，每个会话的状态栏报的是它自己上一次请求时的额度，闲着的会话会一直重复旧数字。状态栏 JSON 带 `session_id`，缓存文件按会话记 `sessions: { <session_id>: { hash, seenAt } }`：`hash` 是这个会话上次报的各窗口（用量和重置时间）的摘要，`seenAt` 是它变化的时间；最多记 32 个会话，超过 8 天没变化的删掉，会话的其他信息一概不存。一份读数的摘要和同一会话上次报的相同，说明这个会话之后没有新请求，忽略它，什么也不写，`observedAt` 保持原来的时间。摘要变了，或这个会话第一次出现，就是一次新请求的结果：它带的每个窗口都采用（最后一份新读数为准，和 Orca 一样），供应商把重置时间提前或推后都跟着变；它没带的窗口保留旧的。没有 `session_id` 的读数按旧办法：两份的重置时间相差不到窗口长度的四分之一算同一个窗口，取用量高的那份；否则采用新数据。旧版本写的、没有 `sessions` 的缓存照常读取。
  - 再把原始 stdin 交给原命令，透传它的 stdout 和退出码。原来没有 statusline 时，输出一行默认内容。
  - 任何解析错误都不能影响透传。
  - 用一个单独的小入口，只 import 最少的模块。
- **自己有一份 `settings.json` 的账号**（不是 link）：面板提示「这个账号的 settings.json 不共享，额度需要单独开启」。

**Codex rollout 读取**：

- 按文件修改时间从新到旧扫描，最多看 20 个文件。
- 每个文件逐行解析，坏行跳过。
- 只接受结构完整的 `rate_limits`：`used_percent` 是数字，`window_minutes` 是正数，`resets_at` 是秒。
- 按事件里的 `timestamp` 取最新的一条。窗口按 `window_minutes` 归类：300 是 5h，10080 是 7d，其他值原样显示。
- 结果里记录来源文件和事件时间。

**显示规则**：

- 每个额度都标注数据时间，例如「5h 已用 42%，14:30 重置，12 分钟前的数据」。
- 已过 `resets_at` 的窗口，显示「已重置，等下次会话更新」。
- 没有数据时，区分三种原因：未开启（Claude）、还没有会话、格式无法识别。

**读取缓存**（2026-10-05 补充）：内置用量和额度读取器按文件记住解析结果（`core/file-memo.ts`），文件的大小、mtime、ctime、inode 都没变就复用，聚合仍按当前时间重算，所以结果与完整重读一致。实测真实 HOME（18 个账号）：`/api/state` 原来每次约 1.56 秒；现在服务启动后第一次约 1.77 秒，之后每次 0.08–0.10 秒。

**读取缓存存盘**（2026-10-08 补充）：门户的面板 worker 在 skm-web 重启、sideby 重装或切换语言后都是新进程，每次都要重新解析日志（实测 343 个文件约 2.6 秒）。带 `persist` 的缓存（Claude 用量、Codex 用量、Codex 额度；身份不存）写到状态目录的 `cache/file-memo.json`（约 6 MB，读回约 10 毫秒）。第一次读取前加载一次；每次读取后在最后一次读取 2 秒后写回，两次写入至少隔 60 秒，定时器不拖住 CLI 进程。文件格式号或某个缓存的版本号对不上、JSON 坏了，都整份忽略、照常解析。缓存值的形状或含义变了就把那个缓存的 `version` 加一。文件只有 token 数、会话 id 和日志路径，不含凭据，原子写、权限 600。

**账号身份**（2026-10-05 补充，ADR-0003 修订）：`FamilyDef.identity` 返回 `{ email?, org? }`，只读登录文件里的身份字段，失败时返回空，不记为账号问题，同样按文件签名缓存。

### 3.8 面板

- **库入口**：`createPanelHandler({ basePath, allowedHosts, readOnly?, runtime?, theme?, lang? })` 返回 `(req, res) => Promise<boolean>`。
  - `allowedHosts` 是 Host 头允许的取值，例如 `['127.0.0.1:17420', 'localhost:17420']`；嵌入门户时由门户传入自己的主机名。
  - 每个 handler 实例在内存里生成自己的随机 token，注入到它返回的页面中。
  - 写请求的 `Origin` 必须等于 `http://<请求的 Host>`，并且这个 Host 在 `allowedHosts` 里。
  - 独立运行和嵌入门户共用同一套规则，各有一个集成测试。
- **独立运行**：`sideby ui [--port]` 只监听 `127.0.0.1`，默认端口 17420。
  - 端口被另一个 sideby 面板占着：直接打开那个面板。
  - 被别的程序占用：顺延到下一个空闲端口，并打印最终地址。
  - 启动后自动打开浏览器；打不开就只打印地址。
- **后台运行**（ADR-0004）：`sideby ui --background` 把面板交给一个脱离终端的子进程（`sideby ui --serve-detached`，内部选项），命令本身打开浏览器后退出。
  - 状态目录里的 `panel.json` 记录 pid、端口、地址、随机实例 id 和进程启动时间（`ps -o lstart=`），日志写到 `panel.log`（超过 1MB 轮转一份）。后台面板的 `/api/health` 额外返回实例 id 和 pid。
  - 已有后台面板，或默认端口上已有同一用户的 sideby 面板：直接复用，不再起第二个。并发启动用 `panel.lock` 串行。
  - **只复用自己的**（2026-10-18 补充）：独立服务器的 `/api/health` 带 `owner`，是系统用户 id 和 HOME 的 SHA-256 前 16 位，不含路径。端口上的 sideby 面板报出别的 `owner`，说明是同一台电脑上另一个用户的，当作端口被占，换下一个端口；没有 `owner` 的旧版面板仍当作自己的。以前只看 `app: "sideby"`，第二个系统用户执行 `sideby ui` 会打开第一个用户的面板，自己的却没启动。
  - **换新代码**（2026-10-05 补充）：`pnpm build` 写 `dist/build.json`（随机构建 id），`buildId()` 是「版本 + 构建 id」，同版本重装也不同；从源码运行是 `<版本>+source`。`/api/health` 和 `/api/state` 都带 `build`，页面启动数据也带。
    - `ui --background` 复用前比对：pid 文件指向的后台面板确认是自己的、但 `build` 不同（或没有这个字段，说明更旧）时，先按 `--stop` 的规则停掉它，再启动新的，输出注明替换了旧面板。别的进程在端口上起的面板不碰。
    - 页面每次读到 state 时比对 `build`：和页面加载时不同，说明服务端换了代码，页面在用户不忙时（没有打开的菜单、对话框、输入焦点、选中文字，也没在体检或修复）自动刷新；忙时先提示「sideby 已更新，你操作完后页面会自动刷新」。
    - 嵌入方（门户）在进程里加载了 sideby，要自己发现包变了并重启进程；页面会随后自动刷新。
  - 后台进程的 Runtime 用登录 shell 的 PATH：`$SHELL -ilc` 在标记之间打印 PATH，5 秒超时，合并到当前 PATH 前面；拿不到就用当前 PATH。这样从 Finder 启动时，`~/.local/bin` 等目录里的宿主不会显示「未安装」。
  - `sideby ui --stop`：只在 pid 仍存活、启动时间与 pid 文件一致、命令行带 `ui --serve-detached`，且记录端口上的面板返回同一实例 id 和 pid 时才发 SIGTERM；任何一项对不上就只删掉过期的 pid 文件。进程看起来对但端口不应答时不发信号、退出 1，提示用 `kill <pid>`。
- **桌面入口**（ADR-0004）：`sideby app install [--url <url>]` / `sideby app uninstall`。
  - macOS 写 `~/Applications/sideby.app`（`CFBundleIdentifier` 为 `dev.sideby.panel`，`Contents/MacOS/sideby` 是 shell 启动脚本，`AppIcon.icns` 由纯 Node 绘制的 PNG 经 `iconutil` 生成，失败时自己写 ICNS）。
  - Linux 写 `~/.local/share/applications/sideby.desktop`、`~/.local/share/sideby/sideby-launcher` 和 hicolor 下的 SVG、256px PNG 图标（遵守 `XDG_DATA_HOME`）。
  - 启动脚本记录安装时的 `process.execPath` 和 sideby 入口的绝对路径，执行 `ui --background`；路径失效时退回登录 shell 里的 `sideby`，再失败就弹窗提示重新安装。安装时设置了 `XDG_CONFIG_HOME`、`XDG_STATE_HOME` 就一并写进脚本。
  - `--url` 时只打开这个地址（嵌入面板的门户），不启动面板。
  - 每个生成的文件都带 `sideby-app-install` 标记（Info.plist 的 `SidebyInstalledBy`、脚本注释、PNG 的 tEXt、SVG 注释、`.desktop` 的 `X-Sideby-Installed-By`）。重装就地更新；安装和卸载都拒绝碰没有标记的同名文件。
  - 重装不带 `--url` 时，沿用已有启动脚本里记录的 `URL='…'`（只认带标记的脚本、不跟随链接、必须是 http(s) 地址），并提示「沿用了上次的地址」；要改回启动面板，先 `sideby app uninstall` 再 `sideby app install`（2026-10-16 补充）。
  - Update 成功后，装了应用（主文件带标记）就由新代码按名字跑一次 `sideby app install --json`，应用记录的 Node、入口和图标随之更新；`sideby update` 之外升级 Node 或换了安装方式时仍要自己重跑（2026-10-16 补充，§3.23）。
- **页面实现**：原生 HTML、CSS、JS，全部内联，跟随系统切换深色和浅色。

**安全**：面板是「本机受信应用」，不防本机上的恶意进程，只防网页发起的请求。

- 只监听 `127.0.0.1`。每个请求校验 `Host` 必须在 `allowedHosts` 里，用来防 DNS rebinding。
- 写接口必须带 `x-sideby-token`（handler 实例的随机 token，只存在内存里），`Origin` 必须存在且与请求的 Host 同源。
- 请求体上限 64KB。写操作全局串行，同一时间只执行一个。
- 新建订阅账号后，面板只给出 `sideby login <account>` 的复制按钮。
- `POST /api/quota/teardown { family }` 撤销额度开启，返回 `{ family, result: { ok, message, diff? } }`。它是写接口：校验同上，只读面板拒绝（403），进同一个串行队列。
- `/api/state` 的账号带可选 `aliases`：config 里指向这个账号的短名，排好序；指不到任何账号的短名不出现。带参数的短名另记在可选 `aliasArgs`（短名 → 参数数组），页面在短名标签的悬停提示里显示参数，搜索也匹配参数。state 还带可选 `configAliases`（短名 → 账号 ref，带参数的短名也只给 ref），页面用来判断短命令是否已占用；别名规则（`aliasPattern`、`reservedAliases`）随页面的 boot 数据下发。

**嵌入其他本地页面**：别的本地 Node 网页可以用约 10 行调用 `createPanelHandler`，把面板挂在自己的路径下。嵌入方传入自己的 `allowedHosts`，handler 负责 token 和 Origin 校验。

**嵌入方主题**（2026-10-05 门户嵌入后补充）：嵌入方用 `theme` 让面板和自己的页面一致。

- 形状：`{ colorScheme?: 'auto' | 'light' | 'dark', header?: 'plain' | 'bar', light?: PanelThemeTokens, dark?: PanelThemeTokens }`。token 是一组有类型的名字（字体、字号、字重、颜色、圆角、控件高度、内容宽度、页边距），清单与含义在 `src/panel/theme.ts`；页面所有组件只读这些 CSS 变量，不传 `theme` 时外观与 `sideby ui` 相同。
- 写入位置：在页面自带的 nonce `<style>` 里，按「默认浅色 → 嵌入方浅色 → 默认深色 → 嵌入方深色」的顺序写成 `:root` 上的自定义属性。CSP 不变。默认深色会重设所有颜色 token，所以嵌入方的浅色不会漏进深色；字体、尺寸、布局 token 两种模式共用。
- 校验：创建 handler 时检查。未知 token、非字符串、空值、超过 200 字符、含字母数字空格和 `# % ( ) , . + - / ' " _` 以外的字符（即不允许 `;` `{` `}` `<` `\` `*` `:`）、含 `url(`、括号或引号不成对，一律抛出写明 token 名的 `TypeError`。这样值无法结束声明、跳出 `<style>` 或加载外部资源。

**嵌入方语言**（2026-10-08 补充，ADR-0006 修订）：嵌入方用 `lang: 'auto' | 'en' | 'zh'` 让面板语言和自己一致，默认 `auto`。

- 规则同 `theme.colorScheme`：`en` 或 `zh` 优先于用户在面板里保存的选择，并隐藏面板自己的语言切换按钮；用户保存的选择不被改写，回到 `auto` 时照常生效。`auto` 保持原顺序：本地保存的选择 → 浏览器语言（`zh` 开头为中文，其余为英文）。
- 值随页面的 boot 数据下发；`<html lang>` 首屏就按它写（`zh` 为 `zh-CN`，其余为 `en`），切换按钮在 `en` / `zh` 时首屏即带 `hidden`。
- 校验：创建 handler 时检查，其他值抛出列出可选值的 `TypeError`。
- 只是创建时的选项。Portal 运行中切语言就重建 handler；不提供按请求的选项，也不读查询参数。

**家族标志**：`FamilyDef.logo = { path, color?, title?, fillRule? }`，24×24 视图框里的一条 SVG path。内置家族的标志在 `src/families/logos.ts`，由各自的 `FamilyDef` 引用；面板只读 `/api/state` 里家族携带的 `logo`，`list --json` 不输出它。插件注册家族时校验：`path` 只能含 SVG path 命令字母、数字、空格、逗号、点、`+`、`-`（最多 20000 字符），`color` 为十六进制颜色，`title` 最多 80 字符，`fillRule` 为 `nonzero` 或 `evenodd`。不合法时丢弃 logo、记一条插件错误，家族照常注册，面板显示首字母。面板用 DOM API（`setAttribute('d', …)`）绘制，不拼接标记。

**只走运行时**：面板和 CLI 只通过 `src/runtime.ts` 调用。体检记录由运行时 `doctor()` 写（只读面板传 `persist: false`）；额度开启通过 `quotaSetups()` / `quotaSetup(family)`；用户造成的错误统一是 `UserError`，面板映射为 400，CLI 映射为退出码 1（2026-10-05 架构加固第 1 轮）。

- **出错时的 `--json`**（2026-10-05 补充）：带 `--json` 的命令出错时，stdout 输出 `{ schemaVersion: 1, error: "<说明和下一步>", code: "<原因>" }`。`code` 取 `UserError.code`（如 `alias-invalid`、`no-quota-source`），用法错误为 `usage`，其他为 `error`。`error` 保持字符串，只新增 `code`，所以 `schemaVersion` 不变。
- 除 `run`、`resume`、`login`、`ui`、`shell-init` 外，所有命令（包括 `app`、`families`）都支持 `--json`，输出带 `schemaVersion: 1`。 只有 `--` 之前的 `--json` 才算 sideby 的选项。`plugins --json` 只给出插件配置的键名（`configKeys`），不输出值。
- 版本规则：只新增字段时 `schemaVersion` 不变；删除字段、改名或改语义时加 1。
- 所有输出、日志、错误信息里都没有凭据值（key、token、密码）。模型名不算凭据：API 账号的 `ANTHROPIC_MODEL` 这类非密钥变量可以显示。

### 3.10 配置与状态

- **配置**：`${XDG_CONFIG_HOME:-~/.config}/sideby/config.json`，可以不存在，schema 在 `schemas/config.json`。字段：`accounts.<ref>.args`、`aliases`、`ignore`、`pluginDirs`、`plugins.<name>`（含 `enabled` 和 userConfig）、`extraSharedItems`、`shellInitFile`、`resumeRouting`（§3.15）、`accountTitle`（§3.5）、`handoff`（§3.17）、`update`（§3.23）、`display`（§3.25）、`quota.check`（§3.26）、`terminal`、`ask`（§3.28）。sideby 对 config 只写十二个键：`aliases`（新建账号时追加，以及 `sideby alias add|rm`，§3.5）、`handoff`（`sideby handoff enable|disable`，§3.17，2026-10-09 补充）、`accounts.<ref>.args` 里的模型、effort 参数（`sideby model`，§3.19，2026-10-14 补充）、`update.auto`（面板的自动更新开关，§3.23，2026-10-16 补充）、`browser.signIns`（`sideby browser --enable|--disable`，§3.24）、`display`（面板拖拽排序，§3.25）、`quota.check.<family>`（面板的额度查询开关，§3.26）（2026-10-17 补充）、`terminal.preferred`、`terminal.custom`、`ask.account`（首选终端、自定义终端命令和 AI Task 用的账号，§3.28）、`panel.theme` 和 `panel.language`（主题和语言，§3.29）；`sideby config set|unset`（§3.29）是例外，可以改 schema 里除插件配置外的任意键。这些写入用同一套写法：保留其他键和顺序，原子写，文件在读写之间被改过就拒绝。
- **状态**：`${XDG_STATE_HOME:-~/.local/state}/sideby/`，存放额度缓存（含联网查到的额度 `quota/<family>/<name>.fetched.json`，§3.26）、日志解析缓存（`cache/file-memo.json`，§3.7 读取缓存存盘）、上次体检结果、statusline 原始备份，以及后台面板的 `panel.json`、`panel.log`、`launcher.log`，检查更新的 `update.json`、`update.lock` 、运行中会话的 `running/<pid>`（§3.23），以及 AI Task 的任务文件 `ask/<task-id>.json` 和工作目录 `ai/`（§3.28）。
- **不写宿主目录**：sideby 不往宿主账号目录写自己的文件。唯一例外是 `quota setup claude` 在用户确认后修改主 `settings.json`。

### 3.11 AI 配套

- **AGENTS.md**：写明命令、目录地图、不变量。不变量包括：§3.3 每种 Mode 的「绝不做」、不泄露凭据、不写宿主目录、插件即本地代码。
- **`pnpm check`**：依次跑 `tsc --noEmit`、biome、`node --test`、`leak-check`。任何一项失败都输出文件和修法。
- **测试隔离**：测试一律用 `testing/` 提供的假 HOME 和假宿主 bin。检测到真实 HOME 就失败。
- **测试文件**：每种 Mode、每个家族一个测试文件。
- **skill 与 llms.txt**：
  - `skills/sideby/SKILL.md` 教 agent 用 `list --json`、`doctor --json` 诊断，以及何时该让用户自己去登录。安装方式：`npx skills add Adonis0123/sideby -g`。
  - **只有一个 skill**（2026-10-05 补充）：sideby 的命令少，不学飞书拆成「shared 底座 + 多个域 skill」。`SKILL.md` 是路由页：硬规则、退出码与确认规则、「想做什么 → 跑哪条命令 → 读哪个 reference」的表；只在某类任务里才需要的细节放 `skills/sideby/references/*.md`（安装与首次配置、共享什么、账号标识、诊断信号表、建号与短命令、Claude 额度、Handoff），只往下一层，不互相引用。description 写明中英文触发说法（「配置一个新账号」「cc002」「这些账号共享了什么」）；frontmatter 的 `metadata` 另有 `requires.bins: [sideby]` 和 `cliHelp: sideby --help`（2026-10-08 补充，§3.16）。
  - **版本**：frontmatter 的 `metadata.version` 等于 `package.json` 的 `version`。`npm version` 的 `version` 脚本同步它，测试校验两者一致。
  - **Doctor 检查已装 skill**：对本次检查的每个家族（指定单个账号时就是它的家族），读这个宿主会读的位置：主账号的 `skills/sideby/SKILL.md`；Codex 另读 `~/.agents/skills/sideby/SKILL.md`（`npx skills add -g` 的安装位置，也是 Codex 读用户 skill 的位置）。同一家族里同一个真实路径只看一次；一个文件被两个宿主读，就各报一条，结果不随本次检查了哪些家族而变。版本和当前 CLI 不同（含没有版本）时给一条 general warn，`code: skill.outdated`，记在该家族主账号名下，hint 是重新安装的命令；没装不报。只读，不修。
  - `llms.txt` 是命令、JSON 契约和插件 API 的索引。

### 3.12 分发与发布

- 包名 `sideby`，命令 `sideby`，`engines.node >=22.18`。`files` 只包含 `dist`、`schemas`、`skills`、README、LICENSE。
- **`ci.yml`**：触发条件是 `push` 和 `pull_request`，权限 `contents: read`。跑 `pnpm check` 和 build，并用 `npm pack --dry-run` 检查发布内容。
- **`release.yml`**：只在推送 `v*` tag 时触发。
  - `publish` job：使用 environment `npm`，权限 `contents: read` 加 `id-token: write`。不用任何 cache。action 全部固定到 commit SHA，checkout 设 `persist-credentials: false`。安装用 `pnpm install --frozen-lockfile --ignore-scripts`。先校验 tag 等于 `v<version>`，再跑测试、构建，然后 `npm publish`（npm ≥11.5.1，provenance 自动生成）。
  - `github-release` job：权限 `contents: write`，用 changelogithub 生成发布说明。它能解析 emoji 前缀的 commit。
- **首发**：npm 要求包已存在才能配置 trusted publisher，所以 0.1.0 必须在本机手动发布一次。之后按 `docs/release.md` 的清单配置 trusted publisher、关闭 token、加 tag 保护。**这一步等作者确认后再做。**
- **日常发版**：`npm version <x> -m "🔖 chore(release): v%s"`，然后 `git push --follow-tags`。

### 3.13 Handoff（2026-10-05 补充）

一个账号的额度快用完时，`sideby next` 推荐同一家族里 Quota Pressure 最低的账号，由人启动。它不轮换、不代理、不读凭据（ADR-0001），只用已有的本地额度数据（ADR-0003）。

- **命令**：`sideby next <family> [--dry-run] [--include-api] [--json] [-- host args]`。
  - 默认打印每个账号的状态和推荐理由，然后像 `sideby run <推荐账号>` 一样启动；`--` 之后的参数交给宿主，不带短命令的参数。
  - `--dry-run`、`--json` 只给推荐，不启动。agent 用这两种模式，把启动命令交给用户。
- **Quota Pressure**：`core/quota-levels.ts` 的 `quotaPressure(quota, now)`。额度可用时，取还没过 `resetsAt` 的窗口里最大的 `usedPercent`，窗口全部已重置为 0；不可用或没有窗口为 `null`。面板按额度压力排序用同一规则：`page-logic.ts` 的函数要保持自包含（由 `toString()` 嵌入页面），由测试保证两者结果一致。
- **每个账号的状态**，按表中顺序排序：

| state | 条件 | 能否被选 |
|---|---|---|
| `ready` | 订阅账号，不是 `logged-out`，压力低于 `QUOTA_FAIL_PERCENT`（85） | 能；压力升序，相同时主账号在前，再按名字 |
| `unknown` | 订阅账号，不是 `logged-out`，没有额度数据 | 能；排在 `ready` 之后 |
| `api` | API 账号 | 只在 `--include-api` 时能，排在 `unknown` 之后；否则只列出 |
| `full` | 订阅账号，不是 `logged-out`，有未重置的窗口达到 85% | 不能；`resetsAt` 取这些窗口里最晚的重置时间；按它升序，没有可读时间的排最后 |
| `logged-out` | `loginState` 为 `logged-out` | 不能 |

  判定顺序（`core/handoff.ts`）：`api` → `logged-out` → `unknown` → `ready` → `full`，先命中的为准；所以已退出登录、额度也满的账号是 `logged-out`。登录态为 `unknown` 的订阅账号照常参与。
- **没有任何额度数据**：所有账号都是 `unknown`（或 API、未登录）时，推荐只是猜测，而且常常就是刚用完的主账号，所以 `next` 不启动，退出码 1，提示开启额度（家族有可用的 `quota setup` 时）或自己用 `sideby run` 选一个。`--json` 照常给出 `pick`，并带 `hasQuota: false`。有账号已满、另一个账号没有数据时照常推荐那个没有数据的账号。
- **没有可选账号**：不启动，退出码 1。全满时说明哪个账号最早恢复、在什么时候；有未登录账号时提示 `sideby login <ref>`。
- **家族没有额度来源**（pi，或既没有 `readQuota` 也没有 `fetchQuota` 的插件家族；Grok 2026-10-17 起有，§3.26）：`UserError`（`code: no-quota-source`），列出这个家族的账号，让人用 `sideby run` 自己选。家族下没有账号：`code: no-accounts`，提示 `sideby new`。
- **会话**：不复制会话。新账号开新会话；输出提示用户先让原会话写一份交接说明。要复制会话并 `--resume`，先单独验证宿主是否接受、Usage 和 Codex 额度会不会被重复计入，再另写 ADR。
- **`--json`**：`{ schemaVersion: 1, family, pick: <ref> | null, accounts: [{ ref, kind, state, pressure: number | null, resetsAt?, observedAt? }], hasQuota, earliestReset?: { ref, at } }`，退出码同上（`hasQuota` 为 false 时也是 1）。`observedAt` 是该账号额度的记录时间。
- **`--dry-run` 给出的命令**带上用户写在 `--` 之后的宿主参数（需要时加引号）。漏写 `--` 时的未知选项错误提示把宿主参数放到 `--` 之后。
- **面板**：`/api/state` 增加可选 `handoff: { <family>: <ref> }`，只含有额度来源、至少两个订阅账号、有额度数据（`hasQuota`）并且有推荐的家族；规则与 `next` 相同，不含 API 账号。被推荐的账号在列表和卡片里显示「下一个 / Next」标记；标记可以点击，复制 `sideby next <family>`，悬停时说明推荐理由。
- **同一登录**（2026-10-14 补充，§3.21）：额度按同一登录共享；从 sideby 启动的会话里运行时（`SIDEBY_ACCOUNT`），和当前账号同一登录的账号带 `sameLoginAs`，不会被选。
- **不做**：主动提醒（Claude Code 撞限额时自己会提示；`statusline-tap` 不能改原命令的输出）、自动切换、复制会话。自动交接后来由 §3.17 Auto Handoff 补上（默认关闭，ADR-0010）；`sideby next` 本身仍只推荐和启动。

### 3.14 参考 Tool 与 Portal（2026-10-06 补充）

作者本机还有几个本地工具（skills 管理、todo、blog 阅读、项目面板），以后可能开源。它们要照 sideby 的样子做，sideby 因此成为「参考 Tool」；把这些页面放在一起展示的本地网关叫 Portal。决定与理由见 ADR-0006，这里只记对 sideby 的约束和待办。

- **契约**：`PanelHandlerOptions` 的全部字段（`runtime` 可以是实例或按请求调用的工厂、`basePath`、`allowedHosts`、`readOnly`、`version`、`theme`、`lang`），handler 返回 `Promise<boolean>`（不在 `basePath` 下返回 `false`，交给 Portal 的后续处理），`token` 属性，`PanelTheme` 的全部字段（`colorScheme`、`header`、`light`、`dark`）与 `PanelThemeTokens` 的键名（背后的 CSS 变量名属于内部实现），`/api/health` 的 `app` 与 `version`。按 `--json` 的规则演进：只加；删除、改名或改变含义都要另写 ADR。
- **挂载**：Portal 在自己的服务进程里把 handler 挂到一个路径（如 `/panel`），再在**同一 host:port** 的页面里用 iframe 显示这个路径，两者同源；放在别的 host 上的顶栏框不住面板。面板的 CSP（含 `frame-ancestors 'self'`）不放宽；不支持跨 origin 嵌入独立运行的 `sideby ui`。Portal 不往面板里注入标记；Portal 自己的顶栏、「在其他应用中打开」不属于契约。
- **Portal 要满足**：用 plain `http`，`allowedHosts` 写上它服务的 `Host`。所有 `POST` 都要求 `Origin` 为 `http://<Host>`，用 https 或会改写 `Host` 的反向代理时，面板能读到状态，但所有操作都会被拒，包括运行 Doctor 和预览 quota setup。
- **信任边界是 origin**：同源的任何页面（包括 Portal 自己的页面）都能取到 token 并做修改。Portal 若还托管不受信的代码，应给面板单独一个 host。
- **CLI 优先**：新功能先有 CLI 命令和 `--json`；面板只展示或调用同一份 core 函数，不加 CLI 没有的写操作。
- **skill 粒度**：保持一个 skill（§3.11），不拆 shared skill。
- **共享库（Kit）**：第二个 Tool 需要时，从 sideby 复制加载器、主题 token、i18n、handler 检查，沿用 sideby 的 token 名；sideby 暂不依赖它，等第二个 Tool 不改接口地用稳后再迁。
- **已实现**：`createPanelHandler` 的 `lang`（2026-10-08），规则见 §3.8「嵌入方语言」。Portal 运行中切语言靠重建 handler，不加按请求的选项或查询参数。
- **待办（未实现）**：
  1. `--json` 输出加可选 `_notice`，只用于提示已装 skill 的版本和 CLI 不同（与 Doctor `skill.outdated` 同一检查，按相等比较），让 agent 不跑 `doctor` 也能看到。只读已装 `SKILL.md` 的 front matter；错误信封是否也带，实现时再定。加字段不升 `schemaVersion`，需同步 `schemas/` 与 `llms.txt`。
- **不做**：`doctor --fix` 和 `new` 不加 `--dry-run`。`doctor` 不带 `--fix` 本身就是预览。`new` 会写东西（Shared Item 的链接和复制、`json-key` 条目、API 账号的 `proxy.env`、短命令和 shell-init 文件），但它拒绝已存在的目录，插件能在 `account.create.before` 里在写任何东西之前拒绝，`--json` 列出每一步，撤销就是删掉新目录，有短命令就 `sideby alias rm <短命令>`，没有就 `sideby shell-init --write`（插件 `account.created` hook 做的事由插件负责）。

### 3.15 会话路由（2026-10-08 补充）

终端管理器（例如 Orca）会记下宿主会话的 id，重开时在 shell 里敲裸命令恢复：`claude --resume <id>`、`codex resume <id>`、`grok --resume <id>`。命令不带账号目录，宿主只在主账号里找，于是报 `No conversation found`。会话路由让这条裸命令落到存有该会话的账号。决定与理由见 ADR-0007。

- **命令**：`sideby resume <family> [-- host args]`。
  - 家族的 `resumedSession(args)` 从宿主参数里取出按 id 恢复的会话；取不到（新会话、按标题或 `--last` 恢复）时原样运行宿主。
  - 取到 id 时，对家族的每个账号调用 `sessionWrittenAt(account, id)`；存有该会话的账号里，取最近写过的那个。
  - 落在非主账号：与 `sideby run <ref> -- <args>` 完全相同地启动（账号的 config `args` 照加），启动前在 stderr 打一行 `sideby: session <id> is in <ref>; starting it there`。
  - 哪个账号都没有会话文件，但有账号起过这个会话（`sessionStartedAt` 返回时间，取最近的那个）：会话启动后没发过消息，宿主从没保存它，按 id 恢复注定失败。这时用家族的 `withoutResume(args)` 去掉按 id 恢复的参数，在起过它的账号开一个新会话：非主账号同 `run` 启动，主账号原样运行宿主、只去掉这几个参数。启动前在 stderr 打一行 `sideby: session <id> was never saved; starting a new session in <ref>`。决定与理由见 ADR-0009。
  - 其他情况（落在主账号、哪个账号都没有也没起过、环境里已设了家族的选择变量）：原样运行宿主，环境和参数都不改，等于没有 sideby。宿主自己报找不到会话。
  - 退出码同 `run`。家族不存在或不支持路由为 1，缺家族为 2。不支持 `--json`。
- **家族接口**（`FamilyDef`，都可选，只读本地文件，不读凭据）：`resumedSession(args): string | undefined` 只认 UUID 形式的 id；`sessionWrittenAt(account, id): Promise<number | undefined>` 返回会话文件的修改时间（毫秒）。
  - Claude：`--resume <id>`、`--resume=<id>`、`-r <id>`；会话在 `projects/*/<id>.jsonl`。
  - Codex：第一个 `resume` 之后的第一个 UUID；会话在 `sessions/**/rollout-*-<id>.jsonl`（不含归档）。
  - Grok：同 Claude 的写法；会话是目录 `sessions/*/<id>/`。
  - 三家都只看 `--` 之前的参数。pi 不支持。
  - 没保存的会话（可选，只 Claude 提供）：`sessionStartedAt(account, id): Promise<number | undefined>` 返回账号起过这个会话的时间；`withoutResume(args): string[]` 返回去掉按 id 恢复参数后的宿主参数，其余参数和顺序不变。Claude 的启动痕迹是 `session-env/<id>/` 目录：Claude Code 在会话启动、跑 SessionStart hook 时建它，会话没发消息也会建（2.1.292 实测）。这是 Claude Code 的内部布局，没有这个目录时按“哪个账号都没有”处理。Codex 和 Grok 没找到同样的痕迹，不提供。
- **shell 函数**：config `resumeRouting: true`（默认关）时，`shell-init` 为每个支持路由、并且至少有一个非主账号的家族，额外生成一个与宿主同名的函数：

  ```sh
  function claude { local a; if [ -z "${CLAUDE_CONFIG_DIR-}" ]; then for a in "$@"; do case $a in ????????-????-????-????-????????????|--resume=????????-????-????-????-????????????) command sideby resume 'claude' -- "$@"; return;; esac; done; fi; command claude "$@"; }
  ```

  - 用 `function name {` 写法，因为 zsh 在 `name() {` 的定义处会展开同名 alias（许多人有 `alias claude='claude --dangerously-skip-permissions'`）。alias 仍然生效：先展开，再进函数。
  - 只有选择变量没设、并且某个参数长得像会话 id（36 个字符、连字符在 UUID 的位置，或 `--resume=` 加这样的 id）时才调 `sideby resume`；其他情况直接调宿主。所以平时敲裸宿主命令不多花时间，`sideby run` 启动的宿主、以及宿主里再开的子 shell 也不会被二次路由。
  - 宿主名或选择变量名不是合法的 shell 名字时不生成；与某个 Alias 同名时也不生成，Alias 优先。
  - 代价：按 id 恢复时多起一次 sideby，实测约 140 ms（`dist`，21 次中位数，含加载全部家族和发现账号）。
- **不做**：复制或移动会话；按标题、`--continue`、`--last` 路由（宿主按当前目录挑，sideby 不猜）；改 Orca 等终端管理器的配置；为了找起过会话的账号去读 `.claude.json` 等凭据文件。

### 3.16 交给 AI 安装和配置（2026-10-08 补充）

多数用户不读文档，而是对自己的 AI agent 说「帮我装 sideby」「帮我配置一个 cc00x」。目标：agent 能做的都由 agent 做；只有必须由用户本人做的步骤（在浏览器里登录、往 `proxy.env` 填密钥）交给用户，并且只给一行命令。sideby 负责两件事：给 agent 确定的命令输出，给 agent 写好引导文字。决定见 ADR-0008。

- **入口**：
  - README 的「Set up with your AI agent」放一句可复制的提示词，指向 `llms.txt`。
  - `llms.txt` 的「Set up sideby for a user」和 skill 的 `references/setup.md` 写同一份步骤，见下面的流程图。
  - `sideby --help` 末尾的「For AI agents」段指向 skill 和 `llms.txt`。

```mermaid
flowchart TD
  A[检查 node --version ≥ 22.18<br>sideby --version] -->|没装| B[npm i -g sideby<br>npx skills add Adonis0123/sideby -g]
  A -->|已装| C
  B --> C[sideby list --json<br>看 families 的 installed 和已有账号]
  C -->|宿主没装| X[告诉用户安装命令 installCommand 或链接 installUrl，停下]
  C --> D[sideby families 家族 --json<br>告诉用户会共享什么]
  D --> E[sideby new 家族 --next --json<br>或用户给的名字和短名]
  E -->|订阅账号| F[交给用户一行 sideby login 账号]
  E -->|API 账号| G[告诉用户 proxy.env 路径，由用户填]
  F --> H[短命令生效：shell 里没有 sideby shell-init 时<br>说明后在 rc 文件末尾加 eval 一行]
  G --> H
  H --> I[sideby doctor 账号 --json 确认]
  I -->|claude 且用户要看额度| J[sideby quota setup claude，退出码 10 后经用户同意加 --yes]
```

- **`sideby families [family] [--json]`**：从 FamilyDef 和 config 的 `extraSharedItems` 输出每个已加载家族（含插件家族）的事实，文档里的共享项表照它核对。字段：`FamilyInfo` 的全部字段（`id`、`title`、`bin`、`installUrl`、`installCommand?`、`installed`、`brokenBin?`、`plugin`），加上：
  - `layout`：`{ main, account }`，相对 HOME，例如 `.claude`、`.claude-<name>`。
  - `selectVar`：选择账号目录的环境变量。
  - `login`：`{ args, hint }`，`args` 为 null 表示在宿主里登录（pi）。
  - `quota`、`usage`、`quotaSetup`：有没有对应的读取器或一次性配置。
  - `shared[]`：`path`、`mode`，可选 `key`、`mainPath`、`credential`、`noSymlink`，`source`（`family` 或 `config`），`meaning`（一句固定英文，说明这一项在账号里是什么样，由 Share Mode 和标记决定）。
  - 人读输出在共享项表之后加一句：账号目录里其他内容（登录、会话、历史）都是账号自己的。
- **`sideby new <family> --next`**：不写名字，由 sideby 选。
  - 名字用面板的 `suggestName`：已有纯数字名字时，接着最大的编号、保持位数（`001`…`007` → `008`）；否则 `work`、`work2`……
  - 没给 `--alias` 时，用面板的 `suggestAlias` 按已有短名的规律给出短名（`cc001` 对 `claude:001` → `cc008`）；看不出规律就不加。建议的短名不能用（被占用、保留字）时不加，原因写在结果里，账号照建。给了 `--alias` 就用给的。
  - `--json` 多一个可选字段 `suggestion: { name, alias?, aliasProblem? }`，只在 `--next` 时出现。
  - `--next` 和名字同时给是用法错误（退出码 2）。
- **面板体检交给 AI**（2026-10-17 补充）：体检里有不能自动修复的发现时，体检区在「全部修复」旁边多一个「复制给 AI 修复」按钮（只读面板也有，它不写任何东西）。点了把这些发现拼成一段提示词复制到剪贴板，用户粘贴给自己的 AI agent。
  - 提示词用面板当前语言，内容只有：一句说明（逐条按提示修好，会删改文件前先问用户，用法看 `sideby` skill 或 `llms.txt`）、当前列出的不能自动修复的发现（账号、项、级别、说明、提示）、还有能自动修复的发现时加一句先运行 `sideby doctor --fix`，最后让 agent 运行 `sideby doctor` 确认。
  - 发现本身不含凭据值（见 Invariants），提示词也就不含；只按某个账号筛选时，只带这个账号的发现。
  - 面板自己能修的发现不进提示词，直接给按钮：sideby skill 版本落后（`skill.outdated`）且更新计划说 sideby 可以更新它（§3.23 `skillUpdate.canRun`）时，这条发现旁边有「更新 skill」，打开更新对话框，看过要做什么后一键更新；更新成功后体检自动重跑。只剩这类发现时，「全部修复」不可用的说明改成「点每条旁边的按钮修复」。
  - 拼装在 `page-logic.ts` 的 `fixPrompt`，哪些发现由面板直接修在 `panelFixes`，测试覆盖。
- **分命令帮助**：`new`、`alias`、`login`、`doctor`、`families` 的 `--help`（也可以 `sideby help <command>`）打印该命令自己的帮助：用法、2–3 个示例、会写哪些文件、哪一步需要用户本人。其他命令仍打印总帮助。
- **不做**：
  - 一条命令装好一切的引导命令（例如 `npx sideby setup` 去装 skill）。它要让 sideby 调 npm、访问网络，违背「sideby 不调用远程服务」。
  - 替用户登录。像飞书 CLI 那样由 agent 在后台跑登录、取出授权链接发给用户，留作后续调研：各宿主在非终端环境下会不会打印链接，还没逐个验证。

### 3.17 Auto Handoff（2026-10-09 补充，ADR-0010 待实测后生效）

一个正在跑的会话额度快用完时，由它自己写好 Handoff Brief，sideby 结束它，在同一个终端里按 Handoff Order 启动下一个账号，开一个新会话接着做。默认关闭。术语见 `CONTEXT.md`「Limits」，取舍见 ADR-0010（部分推翻 ADR-0001）。

**边界**：不读凭据、不代理请求、不合并登录、不改全局生效的账号、不调私有额度接口（ADR-0001、ADR-0003）；不复制会话。只对 sideby 启动的交互会话生效（`sideby run`、短命令、`sideby next`）：直接敲 `claude` 不触发，headless 运行（`claude -p`、`codex exec`、`grok -p`）也不触发。

#### 配置

`config.json` 新增 `handoff`，全部可选：

```json
{
  "handoff": {
    "auto": false,
    "sameFamily": false,
    "prepareAt": 80,
    "threshold": 95,
    "waitIfResetWithinMinutes": 30,
    "countdownSeconds": 10,
    "crossOrganization": ["claude:003"],
    "families": {
      "claude": { "policy": "order", "order": ["cc002", "cc003", "codex001"] }
    }
  }
}
```

- `auto`：打开 Auto Handoff。只开它时，会交给 API 账号（任何家族，按次付费，不绕过哪一家的限额，所以不受 `sameFamily` 限制），以及写进 `order` 的其他家族账号。
- `sameFamily`：另外允许交给同家族账号（例如 cc001 → cc002）。封号风险最高的一种，README 和 guide 写明。
- `prepareAt`、`threshold`：Quota Pressure 的预备档和 Handoff Threshold，整数百分比，`prepareAt < threshold ≤ 100`。
- `waitIfResetWithinMinutes`：满了的窗口在这么多分钟内重置时，留在原账号等，不交接。`0` 表示从不等。
- `countdownSeconds`：交接前的倒计时；`0` 表示不倒计时。
- `crossOrganization`：可以从不同组织的账号接手的账号（ref 或短命令）。组织是否相同按三级判断，用 Identity（ADR-0003）：两边都有 organization 时比 organization；否则两边都有 email 时比 email 域名（`work.dev` 与 `gmail.com` 不同）；都没有时视为相同。不同就跳过，除非接手方列在这里。
- `families.<family>`：`policy` 为 `pressure`（默认，规则同 §3.13）或 `order`。`order` 列出账号（ref 或短命令），可以包含其他家族的账号；没列出的账号不参与。没有这一项时用 `pressure`，只在本家族内选，再按 `auto` 的规则补上 API 账号。
- 写错（阈值越界、`prepareAt` 不低于 `threshold`、未知的键或 `policy`）时 config 校验报错，指出键名和修法。账号是从磁盘发现的，加载 config 时还不知道有哪些，所以 `order` 里找不到的账号或短命令由 Doctor 报 `handoff.order-unknown`，交接时跳过；不能接手的家族（没有 `handoff` 成员）在选号时跳过。

#### 流程

1. `sideby run` 在 `handoff.auto` 为 true、家族能发起、会话是交互式时，给宿主进程设 `SIDEBY_HANDOFF_RUN=<run id>`、`SIDEBY_HANDOFF_FAMILY=<family>`、`SIDEBY_HANDOFF_DIR=<链目录>`，并按上表注入 hook。sideby 加的参数（hook、链目录、`eligibility.args`）插在用户参数里第一个 `--` 之前，否则用户自己写的 `--` 会让它们变成 prompt 文字。启用前先确认 `PATH` 上的 `sideby` 能用：不在 PATH、来自 npx 缓存，或 `sideby handoff-hook --check` 不回答 `ok`（旧版本没有这个入口，每次 hook 都会失败），就关闭这次运行的 Auto Handoff 并说明。注入的 hook 都是同步的 command hook，命令是固定文本 `sideby handoff-hook <family> <event>`，变化的值都放在环境变量里：Codex 的信任按 hook 来源和内容记录，命令一变就要重新信任。父进程一直等到宿主退出（`spawn`，`stdio: inherit`，已有行为）。
2. `sideby handoff-hook <family> <event>` 由宿主在 `PostToolUse`、`Stop`、`StopFailure` 时调用；Claude 还在 `SessionStart` 调用（2026-10-15 补充）：返回 `additionalContext`，告诉 agent 它在哪个账号、用户要把任务换到别的账号时先写 Brief、再运行 `sideby handoff ready --to <account>` 并结束这一轮，不要让用户自己去启动。没有这句，agent 只会把启动命令交给用户。Codex、Grok 只从第二跳的首条 prompt 得到这句。没有 `SIDEBY_HANDOFF_RUN`，或 `SIDEBY_HANDOFF_FAMILY` 不等于命令里的 `<family>` 时，立即退出 0、不输出。前者让写进主账号的 hook 不影响 sideby 之外的会话；后者防止串家族：Grok 默认（`compat.claude.hooks`）也执行 `~/.claude/settings.json`、`~/.claude/settings.local.json` 和项目 `.claude/settings.json`、`.claude/settings.local.json` 里的 hooks（项目级的要文件夹被信任后才执行）。它和 `statusline-tap` 一样只能 import Node 内置模块和叶子模块，不 import `runtime.ts`、家族 index 或 `core/accounts.ts`。
3. **预备档**（压力 ≥ `prepareAt`，每个会话一次）：`PostToolUse` 返回 `{"hookSpecificOutput": {"hookEventName": "PostToolUse", "additionalContext": "…"}}`，要求 agent 按 Brief 模板写到 `<链目录>/<n>-<ref>.md`，之后每完成一步就更新它。
4. **交接档**（压力 ≥ `threshold`）：先看选号结果（下一节）。结果是「等」或「没有可接的账号」时，只在终端说明，不打断会话。否则 `PostToolUse` 要求 agent 做完当前一步、最后更新 Brief、结束这一轮。`Stop` 再查一次额度（一轮里没有工具调用时只有这一次）：Brief 已更新就通知父进程；没更新就返回 `{"decision": "block", "reason": "…"}` 再要求一次，每个会话最多一次（Codex 还要看输入里的 `stop_hook_active`，避免循环），之后改由 sideby 拼 Brief。
5. **撞墙兜底**（只有 Claude 和 Grok）：只认额度用完，不认临时限流：Grok 文档写明 `rate_limit` 也包括 503/529 过载，重试耗尽的 429 大概也在其中（推断，Claude 同理）。
   - Claude：`StopFailure` 的 `rate_limit`，并且 tap 缓存里的压力 ≥ `threshold`，或者报错文字说的是用量上限。
   - Grok：`StopFailure` 不按 `error` 过滤（它只有 `rate_limit`、`authentication_failed`、`invalid_request`、`server_error`、`max_output_tokens`、`unknown` 六类，额度用完没有单独一类）。只在 `errorDetails` 或 `lastAssistantMessage` 含下列子串之一时才算：`You hit your weekly limit`、`You hit your free usage limit`、`reached your free Grok Build usage limit`、`usage limit reached`、`out of credits`、`usage balance exhausted`、`spending cap`、`credit limit for your plan`、`free-usage-exhausted`、`status 402`；`status 403` 只在和其中一条同时出现时才算（单独的 403 可能是拒绝访问）；只出现 `rate limit` 不算，包括带「try again later」的 `You’ve hit the rate limit for your plan` 和 `You’ve hit your team’s API rate limit. Ask a team admin to purchase more credits…`；「try again later」只排除这两句，`You’ve reached your free Grok Build usage limit for now…try again later` 含名单子串，仍算额度用完。名单取自 1.0.50 二进制，放在 Grok 家族代码里，宿主升级后复核。带 `subagentType` 的是子 agent 的失败，忽略。
   - 命中后 sideby 从会话记录拼 Brief，然后通知父进程。`StopFailure` 的输出会被宿主忽略，所以通知只能写文件。
6. **通知**：hook 在链目录写 `ready.json`（mode 600），父进程监听这个文件。
7. **父进程交接**：
   0. 先选号。结果不是 `pick`（没有可接的账号，或该等待）时不结束宿主：删掉 `ready.json`，会话照常进行，结束后在终端说明原因。手动入口和撞墙兜底不经过 `plan.json`，所以这一步不能省。结果是「等」时（2026-10-16 补充）父进程写 `waiting.json`（`runId`、`until`），并继续监听 `ready.json`：等待期间用户的手动入口照样交接。
   1. 给宿主发 SIGTERM，最多等 10 秒让它退出（留出 `SessionEnd` hook 的时间）。10 秒内没退出就放弃这次交接，在终端说明，不发 SIGKILL。
   2. 宿主退出、终端交还给 sideby 后，终端有人值守（stdin 是 TTY）时显示倒计时，`Enter` 取消。先结束再倒计时，避免两个进程同时读键盘。
   3. 取消时，sideby 在原账号里续接刚才那个会话（用家族的续接参数，如 `claude --resume <id>`），这条链本次不再自动交接。
   4. 不取消就像 `sideby run <下一个账号>` 一样启动，首条 prompt 见下文。
8. 下一个账号也在同一条链里，带同一个 chain id，到阈值时继续往下交。

**手动入口**：`sideby handoff ready [--to <account>] [--brief <file>] [--json]`。只能在 sideby 启动的会话里运行（有 `SIDEBY_HANDOFF_RUN`），作用是写 `ready.json`，父进程在这一轮结束后按第 7 步交接。父进程在 `plan.json` 里写 `acceptsTo: true`；带 `--to` 而本次运行的 `plan.json` 没有它时（父进程是 0.9.3 之前的版本，会忽略 `--to` 另选账号），报 `parent-too-old`，不写 `request.json`。成功时说出接手的账号（`--json` 里是 `next`），agent 照这个告诉用户，不要拿 `sideby next` 的结果代替：后者不知道这条链用过哪些账号。`--to`（2026-10-15 补充）指定接手的账号（账号或短命令），可以是本链已经用过的账号，比如交回额度已恢复的原账号；只放开「本链已经用过」这一条，选号的其他条件照旧，不能接时报 `no-pick` 并说明原因，不改成选别的账号。自动交接（阈值、撞墙）仍不回到用过的账号，避免两个账号来回切。`--brief` 可以指向用户自己的 `/handoff` 等工具写的文件，sideby 把它复制进链目录。不在 sideby 启动的会话里时报错，提示用 `sideby next`。手动入口也需要 `handoff.auto`：只有这时 sideby 才注入 hook、设环境变量（否则每次启动都要多一层 hook，Codex 还会对所有人要求信任）；仍受 `sameFamily` 限制。

#### 等待要看得见、能跳过（2026-10-16 补充，ADR-0018）

用户反馈：cc008 撞到上限后没有换号，看起来像坏了。实际是按第 1 条选了「等」：额度 26 分钟后恢复，Claude 自己续上了。问题是等待时用户看不到 sideby 的决定，也没有办法改成立刻换号。

1. **提前说**：压力 ≥ `threshold` 且 `plan.json` 的决定是 `wait` 时，`PostToolUse` 或 `Stop` 在输出里带 `systemMessage`（显示给用户，不给模型），每次运行一次（run 状态记 `waitNoticeSentAt`）：哪个账号、额度几点恢复、到时原地等着自己续上、要现在换号就在会话里输入 `! sideby handoff ready`。`plan.json` 的 `wait` 带 `until`（恢复时间）供 hook 使用。
2. **撞墙时再提醒**：`StopFailure` 只认 `terminalSequence`（Claude Code 只放行 OSC 0/1/2/9/99/777 和 BEL），所以 `plan.json` 是 `wait` 时，hook 返回一条桌面通知（OSC 9 和 OSC 777 各一份，覆盖 iTerm2、WezTerm、Ghostty 等），内容同上。终端不支持时什么也不显示，第 1 条仍在。
3. **不用模型也能换号**：额度用完后模型不能回话，在会话里说「换号」没用。Claude 的 `!` 前缀直接在会话的 shell 里运行命令，不经过模型，并继承 `SIDEBY_HANDOFF_*` 环境变量。`sideby handoff ready` 在本次运行有 `waiting.json` 且现在早于 `until` 时，直接写 `ready.json`（`trigger: manual`，带 run 状态里的会话 id），不写 `request.json`：等待中不会再有 `Stop`，request 永远不会被处理。父进程照第 7 步交接，输出写「现在交给 X」。过了 `until` 视为会话已续上，回到 request 流程。
4. **只在能续上时才等**：见「选号」第 1 条。

#### 选号

在 §3.13 的状态和排序之上，按顺序判断：

1. 原账号满了（或将满）的窗口在 `waitIfResetWithinMinutes` 内重置：等。Claude 交给官方的 `autoContinueAtUsageLimit`；sideby 不自己轮询重启。
   - 只在会话能自己续上时才等（2026-10-16 补充，ADR-0018）：家族的 `handoff.resumesAtReset(account)` 返回 true。Claude 读账号 `settings.json` 顶层的 `autoContinueAtUsageLimit`，没写按官方默认 `true`，只有写成 `false` 才不等（只读这一个键；托管设置、项目设置和 `--settings` 里的同名键读不到，guide 写明这个缺口）。Codex、Grok 和插件家族没有这个能力：等于 `waitIfResetWithinMinutes: 0`，一满就交接，否则「等」就是停在那里没人续。
   - 手动入口（`sideby handoff ready`，不带 `--to` 时）不等：用户已经说了要换，选号跳过这一条。
   - 「满了」：用量已到 `threshold` 的窗口。真正交接时（`ready.json` 之后）只看这些。
   - 「将满」（2026-10-14 补充）：提前算好的结果，也就是每 60 秒刷新的 `plan.json` 和面板「接下来会交给谁」，回答的是「最满的窗口到了 `threshold` 时会怎样」。所以这两处把最满的那个窗口也算进去，前提是它已到 `prepareAt`。否则额度刚过 `threshold` 时，钩子读到的还是不到 `threshold` 时算的「交接」，会先要求 agent 收尾，而真正选号时却是「等」。
2. 候选：`policy: order` 时取 `order`；否则取本家族账号（按压力），再补其他家族的 API 账号。
3. 去掉（手动入口带 `--to` 时候选只有那一个账号，且不按「本链已经用过」去掉）：与原账号同一登录的账号（§3.21，`order` 里写了也跳过，结果的 `skipped` 和终端写明原因）、本链已经用过的账号、`full`（压力已到用户的 `threshold` 也算，否则它第一次工具调用就又要交接）、`logged-out`、组织不同（见 `crossOrganization`）且没列出的账号、`sameFamily` 为 false 时的同家族订阅账号（API 账号不受影响）、宿主没装的账号。
4. 取第一个 `ready` 或 `unknown`；没有就取第一个 `api`。都没有时：不交接，旧会话照常结束，终端打印最早恢复的账号和时间（同 §3.13 的 `earliestReset`）。

#### Handoff Brief

- 位置：链目录 `${XDG_STATE_HOME}/sideby/handoffs/<chain>/`，Brief 为 `<n>-<ref>.md`，目录 mode 700、文件 mode 600，不写进项目仓库。链目录另有 `chain.json`：每一跳的账号、时间、触发方式（`prepare`、`threshold`、`limit`、`manual`）、Brief 来源（`agent`、`sideby`、`user`）。
- 模板（hook 注入时完整给出，不依赖任何 skill）：任务目标；已完成；剩下的步骤；关键决定和原因；相关文件。已经写进 spec、ADR、commit、diff 的内容只给路径不复述；列出建议下一个 agent 使用的 skill；不写 key、密码、个人信息。
- sideby 补的部分（不调模型）：工作目录、当前 git 分支、未提交的文件列表、`git diff --stat`。不 commit、不 stash。不是 git 仓库时省略。
- sideby 拼的 Brief（兜底）：从旧会话记录里取第一条用户消息、最后几轮对话的文字部分和改过的文件路径，再加上面的 git 部分，开头注明「由 sideby 机械生成，可能不完整」。会话记录不是凭据文件；只取文字，不取工具输出的大段内容。
- **首条 prompt 只传路径**：一句「这是从 <账号> 交接来的任务（写明原因：额度快满、额度用完或用户要求交接），先读 `<Brief 路径>` 再继续」，再加一句：用户要把任务换到别的账号时，运行 `sideby handoff ready --to <account>` 并结束这一轮。正文不进启动参数：同机其他用户能用 `ps` 看到参数，兜底 Brief 可能带进聊天里贴过的内容，长正文也会刷满终端。发起方和接手方都要能用链目录：发起方要写 Brief，接手方要读。Claude 和 Codex 启动时加 `--add-dir <链目录>`：只在 `handoff.auto` 打开时加，不是危险参数。sandbox 模式和 approval 策略照用户的设置；Codex 的 `--add-dir` 是额外可写目录，`workspace-write` 下只把本链目录加进可写范围。Codex 用 `read-only` 沙箱时（来自 `-s`/`--sandbox`、`-c sandbox_mode=…` 或账号 `config.toml` 的 `sandbox_mode`；profile 里的设置不读）agent 写不了 Brief，跳过预备档，到阈值时由 sideby 拼 Brief。Grok 的 hook 是 grok 的子进程，继承它的 sandbox：默认 `off` 和 `devbox` 能读能写链目录，可以发起，也可以接手；`workspace`（只能写当前目录、`~/.grok/` 和临时目录）和 `read-only` 能读不能写，hook 写不了 `ready.json`，只能接手。sideby 按 Grok 的配置层算出生效的 profile：`requirements.toml`（`$GROK_HOME/` 和 `/etc/grok/`，`sandbox.profile` 是 pin，压过其他一切）、命令行 `--sandbox`、`GROK_SANDBOX`、账号 `config.toml`、`managed_config.toml`（`/etc/grok/` 和 `$GROK_HOME/`）。同一层有两份时：`requirements.toml` 以 `/etc/grok/` 为准，`managed_config.toml` 以 `$GROK_HOME/` 为准。算出 `off`、`devbox`：可发起可接手；`workspace`、`read-only`：只能接手；其他值、文件读不了或无法判断：两边都不做，启动时说明原因。macOS MDM（`ai.x.grok`）下发的值 sideby 读不到，guide 写明这个缺口。`cli.use_leader` 用同一套生效值，启动参数 `--leader`、`--no-leader` 优先；`allow_managed_hooks_only` 为 true 时 sideby 的 hook 不会运行，Grok 不能发起。正文任何时候都不进启动参数。

#### 启动参数

同家族接手时沿用用户这次写在 `--` 之后的宿主参数和短命令参数，由家族去掉续接和旧会话的参数；其他家族只带该账号在 config 里的 `args`。每个家族要去掉的：

| 家族 | 去掉 | 保留 |
|---|---|---|
| Claude | `--resume`/`-r` 及其值、`--continue`/`-c`、`--fork-session`、`--session-id` 及其值、旧的首条 prompt | 其他参数 |
| Codex | `resume`、`fork` 子命令及其会话 id 或名字、`--last`、`--all`、`--include-non-interactive`、旧的首条 prompt | `-c` 配置覆盖（Codex 里 `-c` 不是续接）、profile、工作目录等 |
| Grok | `--continue`/`-c`、`--resume`/`-r` 及其值（会话 id 或标题，可以省略）、`--session-id`/`-s` 及其值、`--fork-session`、`--restore-code`、旧的首条 prompt | 其他参数 |

sideby 自己不加任何危险参数，包括 Codex 的 `--dangerously-bypass-hook-trust`。Codex 的信任记在每个账号自己的 `config.toml`（`hooks.state`，key 含来源路径），`hooks.json` 是软链也不共享信任，所以每个 Codex 账号第一次带 hook 启动时都要在 `/hooks` 里信任一次；sideby 在该账号第一次带 hook 启动前打印一行说明。

#### 命令与输出

- `sideby handoff setup <family> [--yes] [--json]` / `teardown`：只用于没有启动参数能注入 hook 的家族（这一期是 Grok；Claude、Codex 只在实测不通过时启用）。规则同 `quota setup`：不带 `--yes` 只展示变更、退出码 10；写入走原子写；teardown 只在文件 hash 等于 setup 写入时还原，否则报错并说明手动删哪一项；`sideby` 不在 PATH 或来自 npx 缓存时拒绝。
- `sideby handoff ready`：`--json` 输出 `requested: true`、`next`、`brief`，等待中直接交接时加 `now: true`（2026-10-16 补充）。退出码 0；不在 sideby 会话里（`code: not-in-handoff-run`）、读不了 `--brief`（`brief-unreadable`）、现在没有可接的账号或 `--to` 指定的账号不能接（`no-pick`，先选号，不写 `request.json`）为 1。
- `--json` 输出都带 `schemaVersion: 1`；新 schema 进 `schemas/`。
- Doctor：`handoff.auto` 为 true 而 Claude 没开额度 tap 时，给一条 warn（`handoff.no-quota-tap`），hint 是 `sideby quota setup claude`；主账号的 `hooks/` 里还没有 sideby 的文件时，给一条 warn（`handoff.setup-missing`），hint 是 setup 和 `sideby doctor grok --fix`；其他 Grok 账号缺文件由已有的 `copy.stale` 报。`order` 为空（`handoff.order-empty`）或有找不到的账号（`handoff.order-unknown`）时各给一条 warn。

#### 交给 AI 开启（2026-10-09 补充）

多数用户会让 agent 去开启（§3.16、ADR-0008），所以 CLI 给出确定的命令和输出，skill 只负责编排：

- **`sideby handoff status [--json]`**（只读）：一次给出就绪情况。`auto`、`sameFamily`、`prepareAt`、`threshold`；`sideby`：`PATH` 上的 `sideby` 能否响应 hook（同启用前的检查）；`families[]`：每个有账号的家族的 `family`、`starts`（`quota`、`limit`，空表示只能接手）、`ready`（这个家族能否发起）、`problems[]`、`notes[]`（例如 Codex 每个账号要在 `/hooks` 里信任一次，sideby 读不到信任状态）、`order`（`policy`、`order`、`unknown`）。`nextSteps[]`：按顺序列出还要跑的命令（`sideby handoff enable`、`sideby quota setup claude`、`sideby handoff setup grok`、`sideby doctor grok --fix`）。退出码 0。
- **`sideby handoff enable [--same-family] [--order <family>=<acct,acct…>] [--yes] [--json]`**：把 `handoff.auto` 设为 true，`--same-family` 设 `sameFamily: true`，`--order` 设该家族 `{ policy: "order", order }`；其他已有设置不动。`order` 里的账号或短命令必须能解析，否则报错并列出可用账号。不带 `--yes` 只展示 config 改动，退出码 10；已经是要求的状态时退出码 0、不写。带 `--yes` 写入后，输出同 `status` 的 `nextSteps`。
- **`sideby handoff disable [--yes] [--json]`**：把 `auto` 设为 false，其余设置保留，方便再开；规则同上。
- `--json`：`enable`/`disable` 输出 `{ schemaVersion, applied, file, diff, settings, nextSteps }`。
- **开启提示**：`handoff.auto` 为 false 时，`sideby run` 的交互会话结束后，如果这个账号的 Quota Pressure 已到 `threshold`、家族能发起交接，stderr 打一行指向 `sideby handoff status` 的提示，每天最多一次（时间记在 `<状态目录>/handoff/hint.json`）。`sideby next` 的输出末尾也加一行同样的指引。
- **面板**：顶栏「设置」菜单里有「自动交接 / Auto Handoff」一行，显示开关状态（2026-10-16 起，原来是顶栏单独的按钮）。`/api/state` 带 `autoHandoff: { settings, starters }`（只读 config，不起子进程）。功能关闭、某个能发起交接的订阅账号压力到阈值时，显示一条横幅，带「去设置」和「暂不」（暂不：本浏览器 24 小时内不再显示）。对话框里可以改总开关、`sameFamily`（附风险说明）、四个数值和每个能发起交接的家族的顺序（按剩余额度，或按自己的顺序：上移、下移、移除、添加），下方是 `/api/handoff/status` 的就绪情况和可复制的下一步命令。「查看改动」调 `/api/handoff/configure`（不带 `confirm`，只返回 diff），「应用」带 `confirm: true` 才写；只读面板拒绝写入。两个接口都调用 CLI 用的同一份 core 函数（§3.14「CLI 优先」），`configure` 只接受白名单里的字段。
- **skill**：用户要开启时，agent 先跑 `status --json`，说明风险（同家族接力），跑 `enable` 拿到退出码 10，问过用户再加 `--yes`，然后按 `nextSteps` 逐条做，其中会改宿主文件的 setup 同样遵守退出码 10 的确认规则。`--same-family` 只在用户明确要求时才加。

#### 页面与一键开启（2026-10-14 补充，ADR-0013）

对象是不懂这个功能的新用户：第一屏只有一句话和一个按钮，开启要做的事全由 sideby 做完，先预览、再确认、可关闭；数字、顺序这些放在点开之后。

- **页面**：顶栏页签「账号 / 自动交接」（有上下文调优时三个，地址 `#handoff` 直达）。「设置」菜单里的「自动交接」打开这个页面；原对话框保留，入口是页面里的「高级设置」。
- **关闭时**：一句话说明（额度快用完时，自动换到下一个账号接着做），一个「一键开启」按钮，一个单独的勾选「也在同一工具的多个账号之间切换」（默认不勾，旁边写明供应商条款风险）。没有任何可发起交接的账号时说明原因，不给按钮。
- **开启预览**：点按钮只调 `/api/handoff/enable`（不带 `confirm`），页面列出会做的每一步：`config.json` 里的 `handoff`；Claude 的额度显示（`quota setup`，已开则不列）；Grok 的钩子文件（`handoff setup`），以及把这一个文件复制到其他 Grok 账号自己的 `hooks/` 里（只写这个文件，账号里的其他文件不动；已有同名文件的账号不覆盖；链接或共用同一目录的账号跳过；只写预览里列出的账号；没有 Grok 则不列。teardown 只删主账号的文件，副本留着，在没有 sideby 交接时什么都不做，要删自己删）。每一步默认只显示一句话，点开看 diff。无法替用户做的事（Codex 每个账号在 `/hooks` 里信任一次，`PATH` 上的 `sideby` 不可用）单独说明；`sideby` 不可用时整体阻止，并给出 `npm i -g sideby` 这一条命令。「确认开启」带 `confirm: true`，按顺序执行，每一步报告成功或原因；中途失败就停，已完成的保留，页面显示还差什么。已经全部就绪时直接返回 `alreadyOn`，不写。确认时带上预览的 `key`（`expect`）：执行前重新生成的计划和预览不一样（预览之后有别的地方改了文件或设置）时一项都不写，返回新计划和 `changed: true`，页面说明「设置在这期间变了」，让用户再看一遍、再确认。复制钩子文件后仍有账号缺文件时，报告哪些账号缺，并说可以重试。
- **开启后**：状态条「已开启」和「关闭」按钮（只把 `auto` 设为 false，其他设置保留；额度显示、钩子文件留着，各有自己的 teardown）。下面每个能发起交接的订阅账号一行：当前已用百分比，以及「到 {threshold}% 会交给 X」（只在撞到用量上限才发起的家族，如 Grok，写「撞到用量上限时交给 X」）「会等到 hh:mm 重置，不交接」「现在没有可接的账号」，数据来自 `rt.handoffDecision`（与真正交接同一套选号，按「将满」算，见「选号」第 1 条）。状态条的说明写明等待规则：到 {threshold}% 时离额度恢复不到 `waitIfResetWithinMinutes` 分钟，就原地等，不换号；关闭时的三步说明里也写这一句。「最近交接」最多 5 条：`旧账号 → 新账号`、时间、原因（额度到达交接线 / 撞到用量上限 / 手动）。就绪检查有缺口（`problems`）时显示「还差一步」和「补全」按钮，走同一个开启流程。固定一句说明：只有用 sideby 启动的会话（短命令、`sideby run`）才会交接，直接敲 `claude` 不会。
- **只读面板**：能看，按钮都不可用，说明用 CLI。
- **接口**：`/api/handoff/overview`（只读，不起子进程：`settings`、`takeover[]`、`recent[]`）；`/api/handoff/enable`（`sameFamily?`、`confirm?`；`sameFamily` 不写就保持现有设置，写 true 或 false 就设成那个值；不带 `confirm` 只返回计划 `{ alreadyOn, blocked?, steps[], manual[], sameFamily, key }`，`sameFamily` 是应用后的值，`key` 标识这份计划，带 `confirm` 时可附 `expect: key`；带 `confirm` 才写，返回 `{ plan, results[], changed? }`）。已开启时「补全设置」不带 `sameFamily`。把同工具交接从关改成开，需要在页面上单独确认一次（风险说明加一个确认按钮）；从开改成关直接生效。`recent` 来自 `<状态目录>/handoffs/*/chain.json` 最近的 40 个目录，只取每一跳的 `ref`、`startedAt`、`trigger`、`briefSource`，不读 Brief，也不返回 Brief 路径。
- **提示文字**：预备档（80%）的消息不再说「另一个账号可能很快接手」，改为只要求写 Brief 并继续任务、不要向用户宣布切换；交接档（95%）的消息不变。切换时由 sideby 自己的倒计时行告诉用户（`sideby: starting cc002 in 10s; press Enter to stay in cc001`）。
- **不做**：自动安装或升级 `sideby`、替用户在 Codex 里信任钩子、检测用户是否直接敲了 `claude`、默认勾选同家族交接。

#### 插件契约

`FamilyDef` 新增可选成员 `handoff`，包含：怎样注入 hook（启动参数或 setup 写入的文件）、怎样从 hook 输入读出事件和额度用完、怎样从会话记录拼 Brief、续接时去掉哪些参数、怎样带首条 prompt 启动、怎样让 Brief 目录可读。没有这个成员的家族不能发起，也不能接手。这是公开契约的新增，只加不改。插件家族这一期只能接手：hook 入口和 `statusline-tap` 一样只能引入叶子模块，只加载内置家族的读取器（`src/families/<id>/handoff-hook.ts`）。`eligibility` 还可以返回 `args`（这次运行需要的宿主参数，例如 Grok 每个账号自己的 leader socket）和 `agentBrief: false`（会话写不了 Brief，例如 Codex `read-only` 沙箱：没有预备档，到阈值时只要求结束这一轮，Brief 由 sideby 拼）。

### 3.18 上下文调优（2026-10-13 补充，ADR-0011）

用账号自己最近的会话记录，估算每个模型的 Compaction Threshold（Host 在上下文涨到多大时自动压缩）设成多少最省 token，给出 Tuning Suggestion。分析本身只读；用户点「使用」才写入 Host 的设置，写什么先展示、写完可撤销（ADR-0012）。

**范围**

| 家族 | 第一版 |
|---|---|
| claude（订阅和 API 账号） | 观测 + 推荐值 |
| codex（订阅和 API 账号） | 只观测，不给推荐值：默认阈值和 scope 没有一手来源，推荐会建立在未证实的前提上。等有来源再加 |
| grok、pi | 「这个宿主没有公开来源」，和额度、用量一致（ADR-0003） |

时间窗固定 `USAGE_DAYS`（7 天），按账号、按模型分别算，不同账号的会话不合并（账号是身份边界）。

**数据来源**（全部本地，不联网，不读凭据值）

| | Claude | Codex |
|---|---|---|
| 逐轮上下文大小 | assistant 行的 `message.usage`：`input_tokens + cache_read_input_tokens + cache_creation_input_tokens`；按 `message.id` 去重（同 §3.7）；`isSidechain` 的行不进重放，subagent 有自己的上下文 | `token_count.info.last_token_usage.input_tokens` |
| 模型 | `message.model` | `turn_context.model` |
| 窗口大小 | 从记录推断（见下） | `token_count.info.model_context_window` |
| 压缩事件 | `type:"system", subtype:"compact_boundary"` 的 `compactMetadata`：`trigger`（`auto`/`manual`）、`preTokens`、`postTokens` | 顶层 `type:"compacted"`；压缩前取之前最近一条 `token_count` 的 `last_token_usage.input_tokens`，压缩后取之后第一条 |
| 当前配置值 | 该账号 `settings.json` 的 `autoCompactWindow`（tokens） | 该账号 `config.toml` 的 `model_auto_compact_token_limit` |

- **读 Host 配置的边界**：这是 sideby 第一次为用量类功能读账号 Host 配置里的值（此前只有 statusline setup 读写主 `settings.json` 的 `statusLine.command`，Doctor 读 `json-key` 指定的那一个键）。读的只有「自动压缩大小」这一项设置：Claude 是 `settings.json` 顶层的 `autoCompactWindow`，加上 `modelSettings` 下各模型自己保存的 `autoCompactWindow` 数字（官方的 `/autocompact` 把大小存在这里，对那个模型优先于顶层键）；Codex 是 `config.toml` 顶层的 `model_auto_compact_token_limit`。文件里其他值一概不读、不返回、不进缓存；文件缺失、不可解析或没有这项设置，当前值就是「默认」。环境变量（`CLAUDE_CODE_AUTO_COMPACT_WINDOW` 优先于一切，sideby 看不到你 shell 里设了什么）和 `proxy.env` 不读。Codex 的键名取自 DeepWiki 对 codex 的描述，没有官方文档原文，所以 Codex 只观测。
- **`autoCompactWindow` 的含义（官方文档，2026-10-13 核对）**：它是「上下文涨到多满才压缩」，也就是压缩阈值本身，文档没有提缓冲或余量（https://code.claude.com/docs/en/model-config#set-the-auto-compact-window）。取值 100K 到 1M token，不会超过模型的上下文窗口；没设时 Claude Code 在模型窗口处压缩，但原生 1M 窗口的模型（Fable 系列、Sonnet 5 及以后、Haiku 5.5、Opus 4.7 及以后）默认在约 967K 压缩，Sonnet 4.6 和 Opus 4.6 没开扩展上下文时在 200K。优先级：环境变量 `CLAUDE_CODE_AUTO_COMPACT_WINDOW` 高于 `--autocompact`，高于 `/autocompact` 存的 `modelSettings`，高于顶层 `autoCompactWindow`。所以 sideby 写顶层键，对「自己保存了大小的模型」和「设了环境变量的会话」不生效，确认页对前者会列出来。
- **模型窗口和阈值的关系**：Claude 的有效阈值是设置值与模型窗口取较小者（从二进制字符串推断，未读源码）；界面据此显示「你设置的是 500K，但模型的 200K 优先」，推断不成立时这句话不显示。
- **模型的局限**：重放只给 token 算成本，不给压缩丢掉的上下文定价，也不含压缩后重读被丢内容的开销（在作者本机日志里实测约为被丢 token 的 2%，所以忽略）。`<synthetic>`（Claude Code 自己写的占位行）不是模型，不计入。
- **空闲压缩（作者本机日志和 Claude Code 2.1.296 的代码核对，2026-10-13）**：Claude Code 除了到阈值才压缩，还会在会话空闲时**提前压缩**：缓存期是 1 小时，空闲到约 90%（54 分钟）、上下文不小于 200K 时就压缩，不管当时多大；是否启用由服务端实验开关决定（`mode` 为 `off`/`log`/`compact`，默认 `off`），用户设置里还有一个 `idleCompaction`（默认开）。作者本机 31 次自动压缩里 30 次都是在安静 54–55 分钟之后发生的，压缩前最小 202K，只有一次（967K，等于原生 1M 模型的默认阈值）是阈值触发。`autoCompactWindow` 管不到空闲压缩。所以：
  - 解析时记下每次压缩前的静默时长，静默 ≥ 50 分钟的自动压缩记为 `idle`；`compactions.idle` 是它们的个数。
  - 只要记录里出现过 `idle` 的压缩，重放就也模拟它：相邻两轮间隔 ≥ 54 分钟、且上下文 ≥ 200K 时压缩一次，对基线和每个候选阈值一视同仁。这样「调阈值能省多少」只算阈值真正能改变的那部分。
  - 基线（「现在」在起作用的阈值）依次取：配置值、官方默认触发点（原生 1M 约 967K，其余等于窗口）、观测到的非空闲自动压缩中位数。不再用「所有自动压缩的中位数」，因为它几乎全是空闲压缩，不是阈值。
  - 界面在建议旁说明「这几次压缩是 Claude Code 在会话空闲约一小时后自己做的，这个设置改不了」。
- **窗口和已知模型**：记录里没有窗口大小，所以从记录推断：模型在窗口内出现过超过 200K 的上下文（或压缩前超过 200K），按 1M 窗口算，否则按 200K。一个实际是 1M 窗口、却从没用到 200K 以上的模型，会被当成 200K 窗口，推荐值因此偏低；界面不隐藏这一点，只写「估算」。「已知模型」目前是模型 ID 以 `claude-` 开头；其他模型（例如经网关的第三方模型）不给推荐值，因为成本倍率只对 Anthropic 的计价成立。倍率常量带取值日期（2026-10）写在 `core/tuning.ts`。

**重放口径**（估算，界面和 JSON 都标 `estimate`）

1. 每个会话取有序的轮次：上下文大小 `c`、本轮输出、cache 写入（5m、1h 分开）。
2. 候选阈值：模型窗口的 4%、5%、6%、7%、8%、9%、10%、12%、15%、20%、25%、30%、35%、40%、50%、60%、70%、80%、90%、95%（常量 `CANDIDATE_PERCENTS`），再加上 Claude Code 允许的最小值 100K，只保留 100K 到 min(窗口, 1M) 之间的。低于 100K 的值 Claude Code 不接受，所以最省点落在 100K 时，推荐的就是 100K，意思是「Claude Code 允许的最低值」。作者本机 1M 窗口的账号里，估算的最省点在 80K–120K，范围只到 40% 时会把它整个截掉。
3. 对每个候选阈值 `T` 逐轮重放：上下文按历史增量增长；增长到 `T` 时压缩一次，压缩后回落到该模型历史 `postTokens` 的中位数，下一轮按 cache 重建计价。
4. 成本是相对权重：input 为 1，cache read 0.1，cache write 5m 1.25、1h 2，output 5（Anthropic 公开的倍率；表里只存倍率，不存美元，因为价格会变而 sideby 不联网取价）。压缩那次调用按「压缩时的上下文按输入权重 + 摘要长度按输出权重」估，摘要长度取历史 `postTokens` 中位数。
5. 取成本最小的 `T` 为推荐值。相对当前有效阈值（见下面「基线」）节省不足 1%，给「已是最省」，不推荐改。基线依次取：配置值（不超过窗口，且在 100K–1M 内）、官方的默认触发点（原生 1M 模型约 967K，其余等于窗口）、观测到的非空闲自动压缩点中位数；三者都没有时没有基线：仍给推荐值，但 `savedPercent`、`savedWeighted` 为 null，界面不写节省，`reason` 仍是 `suggested`。
6. `reason` 的取值：`suggested`（有推荐值）；不给推荐值时：`insufficient-calls`（该模型窗口内调用不足 200 次）、`no-compactions`（窗口内没有任何压缩记录，压缩后剩多少无从估）、`no-optimum`（模型窗口低于 100K，Claude Code 允许的值一个也放不下）、`unknown-model`（不是 `claude-` 开头的模型，成本倍率不适用）、`already-best`、`observe-only`（Codex）。

**为什么只能是估算**：换阈值后摘要内容和 `postTokens` 无法重现，只能用历史分布；压缩那次调用的真实花费记录里没有；不同阈值对 cache TTL 命中的影响只能建模；没有对照实验，不能说因果。界面写「估算」，不说「会省」。

**公开契约**

- `FamilyDef.readTuning?(account, ctx): Promise<TuningResult>`，可选成员，只增不改。`TuningResult` 是 `ok`（`days`、`estimate: true`、`models[]`；`estimate` 恒为 true，表示整份结果是估算，供 JSON 消费者区分）或 `unavailable`（`reason`: `no-source` / `no-session` / `unrecognized`）。每个模型项带 `model`、`calls`、`contextWindow`、`configured`（number 或 null）、`compactions`（`total`、`auto`、`manual`、`idle`、`preTokensP50`、`preTokensMax`；`total` 含 Host 不记录触发方式的压缩，Codex 的 `auto`、`manual` 恒为 0）、`effective`（生效的阈值或 null）、`suggestion`（`{ threshold, savedPercent, savedWeighted }` 或 null）和 `reason`。`reason` 每个模型项都有：有推荐值时是 `suggested`（`suggestion` 非 null），其余取值时 `suggestion` 为 null。
- `Runtime.tuning(account)`：无 `readTuning` 的家族返回 `unavailable/no-source`；读取异常转 `unavailable/unrecognized`（带 `detail`）。出错只有这一个去向：调优不走 `/api/state`，错误不写进 `AccountStatus.problems`，也不中断其他账号。
- `sideby tune [acct\|family]`：不带参数时列出全部账号（和 `quota` 一致），带参数时只列那个账号或家族。不带 `--json` 时打印表；`--json` 输出 `{ schemaVersion: 1, accounts: [{ ref, family, tuning }] }`。账号或家族不存在为 1，多给参数或未知选项为 2，其余为 0。家族存在但没有账号时，列表为空、退出码 0，文字输出说明怎么新建。`json-schemas.ts` 加 `tune`，`llms.txt` 加一行。
- 面板：`POST /api/tuning` 是只读路由（`writes: () => false`，只读面板也可用），但和其他 POST 一样校验 Host、Origin 和 token，进同一个串行队列。返回 `{ minCalls, accounts: [{ ref, family, tuning }], groups: [{ id, file, members, target, current, pick, undo }] }`：`groups` 按真实设置文件分组（Claude；符号链接指向同一个文件的账号在一组），`file` 用 `~` 缩写，`current` 直接读设置文件里那一个键（没有会话数据时也准确），`pick` 是这组里用得最多、且有建议的模型 `{ ref, model, threshold, savedPercent, calls }`，`target` 是发起写入和撤销时用的账号（`pick` 来自的那个，没有就是第一个成员），`undo` 同下。带 `{ account }` 时返回这个账号、与它共用文件的账号，和它所在的那一组。CLI 的 `sideby tune apply` 缺省值用同一个 `pick`。重放比 `/api/state` 重，所以只在打开页面或对话框时请求，不进自动刷新。`FamilyInfo` 新增 `tuning: boolean`，`list --json` 和 `families --json` 的家族条目都带它。
- 页面和对话框共用同一段渲染：每组设置一张卡（当前值、建议值及依据、预计省多少、「使用 80K」按钮、大小菜单、撤销，以及确认时的说明），各账号各模型自己的数字收进「各账号的详情」折叠区，只是信息。不再给任何可复制的配置片段，用户不必知道文件在哪。带 `{ account }` 时 `accounts` 也包含和它共用文件的账号，所以从没有会话的账号打开，也看得到所在组的卡片和依据。空数据、出错（带重试）、慢加载各有显示。中英文案进 `i18n.ts`，颜色走主题 token。页面的页签是 `role="tablist"`，当前页用 `aria-selected` 标出。

**应用与撤销**（2026-10-13 补充，ADR-0012）

- 推荐值旁有「使用 80K」按钮（只有 Claude；Codex 没有推荐值，所以没有）。点了先展示：要改的文件、改前和改后的值、共用这个文件的其他账号；用户确认才写。写完说明「新开的会话生效」，并给「撤销」。用户不必知道设置文件长什么样，也不必自己复制任何内容。
- 除了推荐值的按钮，每个 Claude 账号下还有一个「自动压缩大小」设置：下拉菜单（默认 / 几个常用值 / 当前值 / 建议值，建议值标「建议」）加「使用这个」按钮，走同一套「先展示、确认、可撤销」。选「默认」就是把这个键删掉。用户不用复制任何内容，也不用知道文件在哪。
- 只写一个键：账号 `settings.json` 的 `autoCompactWindow`（整数 token，100000 至 1000000，与官方一致）。其他键原样保留，缩进沿用文件原来的，保留末尾换行。
  - 文件不存在：新建，权限 600，只含这一个键。
  - 文件是软链（和主账号共用设置的常见情形）：写它指向的真实文件，确认页写明「会同时影响：账号列表」。绝不创建、替换或改变任何软链。
  - 不可解析、不是 JSON 对象、指向不存在的文件：不写，说明原因和下一步；错误里不含文件内容。
  - 用 `writeIfUnchanged` 写：读和写之间文件被改过就放弃并说明；写完文件权限不变。
  - `env` 等其他键的值不进任何输出、错误或状态记录。
- 撤销：写之前把「这个键改之前的值（没有记为无）」和写入的值，连同文件路径和时间，记在状态目录 `tune/<文件路径的 hash>.json`。撤销只在这个键仍等于当初写入的值时才改回去（改回旧值，或原来没有就删掉这个键）；用户之后自己改过就不动，说明原因。
- CLI：`sideby tune apply <acct> [tokens|default] [--yes] [--json]`：不带 `--yes` 只展示改动并退出 10；`tokens` 缺省取推荐值，写 `default` 就是恢复默认（删掉这个键）；`tokens` 可写 `160000`、`160k`、`1m`。`sideby tune undo <acct> [--yes] [--json]` 同理。成功为 0；不是 Claude 账号、没有推荐值又没给 `tokens`、被拒绝为 1；用法错误为 2。
- 面板：`POST /api/tuning/apply { account, value, confirm }`（`value` 是整数 token，或 `null` 表示恢复默认），不带 `confirm` 只返回计划（只读面板也可用），带 `confirm: true` 才写（只读面板 403）；`POST /api/tuning/undo { account }` 总是写。`/api/tuning` 的 `groups[].undo` 是 `{ value, previous } | null`（`value` 为 `null` 表示当时是恢复默认），让页面知道要不要显示「撤销」。
- 界面措辞按「把用户当小白」写：不出现 token 加权、Host 这类词，只说会发生什么、能得到什么。

**读取缓存**：每个文件的逐轮摘要放进单独的、带 `persist` 的缓存（`claude-tuning`、`codex-tuning`；摘要的形状或含义变了就把版本加一，`claude-tuning` 因压缩补记模型已是 2），按文件签名复用，聚合和重放按当前时间在缓存之外重算。摘要只含 token 数、模型名、时间和会话 id，不含对话内容和凭据。只留 `USAGE_DAYS` 内的轮次，大日志流式读，坏行跳过。Claude 用量缓存的 `Entry` 不动，避免已有缓存失效。

**不做**：Codex 推荐值（也就没有 Codex 的「使用」）、应用后自动追踪效果、提示缓存的调优、模型间的比较、跨账号合并、联网取价或取默认阈值。

**文档同步**：两份 README（一句话）、`docs/guide/usage*.md` 和 `commands*.md`（中英成对）、`skills/sideby/` 的相关 reference、`llms.txt`、`schemas/`、`CONTEXT.md`（Compaction Threshold、Tuning Suggestion）、AGENTS.md 的 Invariants（读 Host 配置只取一个键；`tune` 只读）。

### 3.19 模型与 effort（2026-10-14 补充，ADR-0014）

账号行显示这个账号现在用的模型和 effort，点开可以按账号改。改动写进 sideby 自己的配置（这个账号的启动参数），不碰宿主的设置文件，所以共用同一个 `settings.json` 的账号可以各用各的。

**显示**（面板账号行、`sideby model <账号>`）：
- 模型和 effort 各自按这个顺序取第一个有的：sideby 为这个账号设的（`accounts.<ref>.args` 里的模型、effort 参数）→ 最近一次会话实际用的（Claude：最后一条 assistant 记录的 `message.model` 和 `effort`；Codex：最后一个 `turn_context` 的 `model`、`effort`）→ 宿主配置（Claude：`settings.json` 的 `model`；effort 取 `modelSettings.<模型>.effortLevel`，没有再取顶层 `effortLevel`。Codex：`config.toml` 顶层的 `model`、`model_reasoning_effort`）。都没有就不显示。最近会话排在宿主配置前面（2026-10-15 调整）：订阅账号常共用同一个 `settings.json`，按它显示会让每个账号都一样，看不出各自实际在用什么。
- 鼠标悬停说明来源：「sideby 为这个账号设置」「来自 Claude 设置」「最近一次会话」。显示的是最近会话、而宿主配置的值不同时，同一行再写「新会话默认是 …（来自 Claude 设置）」。
- 只读 `model`、`effortLevel`、`modelSettings.*.effortLevel`（Claude）和 `model`、`model_reasoning_effort`（Codex）这几个键；文件里的其他值不进入任何输出。API 账号照旧显示 `ANTHROPIC_MODEL`，不提供修改（模型由 `proxy.env` 决定）。
- 看不到的覆盖：shell 里的 `ANTHROPIC_MODEL`、`CLAUDE_CODE_EFFORT_LEVEL`（后者优先于 `--effort`），以及组织下发的设置。界面和 guide 写明。

**修改**：
- 选项：模型（「默认」、宿主别名 Claude `fable`/`opus`/`sonnet`/`haiku`，加上最近用过的模型，也可以手填；名字只允许字母、数字和 `._:/[]-`）；effort（「默认」，Claude `low`/`medium`/`high`/`xhigh`/`max`，Codex `minimal`/`low`/`medium`/`high`/`xhigh`/`max`/`ultra`，按 Codex 文档可用档位随模型变化）。「默认」表示 sideby 不加这个参数。
- 写入：只改 config 的 `accounts.<ref>.args`，去掉原有的模型、effort 参数（Claude `--model`/`--effort`，含 `=` 写法；Codex `-m`/`--model`、`-c model_reasoning_effort=…`），保留其他参数，再按选择追加（Claude `--model <m> --effort <e>`；Codex `-m <m> -c model_reasoning_effort="<e>"`）。参数变空就删掉这个账号的条目。写法同 §3.10 的 config 写入（原子写、读写之间被改过就拒绝）。
- 生效：只影响之后用 sideby 启动的会话（`sideby run`、短命令、`sideby next`、自动交接接手方）；正在跑的会话不变，直接敲 `claude` 不受影响。账号参数在短命令参数和用户参数之前，后两者里再写 `--model` 时以宿主的解析为准（后写的生效）。
- 面板：账号菜单「模型和 effort…」，也可以点账号行里的模型文字打开。对话框先显示改动（config 的 diff），确认才写；「恢复默认」清掉 sideby 设的两项。只读面板不能改。
- CLI：`sideby model <账号> [--json]` 只读，列出三个来源和生效值；`sideby model <账号> [<模型>|default] [--effort <级别>|default] [--yes] [--json]` 不带 `--yes` 只展示改动、退出码 10。
- 插件契约：`FamilyDef` 新增可选 `modelChoice`（可选 effort、建议模型、读宿主配置、选择 ↔ 参数互转）；`UsageResult` 新增可选 `lastModel`、`lastEffort`。只加不改。

### 3.20 桌面应用（2026-10-14 补充，ADR-0015；Grok Bot 见下文「Grok Bot 窗口」，ADR-0019）

有些家族还有桌面应用（Desktop App）：Claude Desktop、Codex 应用。sideby 能为一个账号单独打开它，多个账号的窗口同时开着、互不影响。sideby 只用启动参数打开应用，不复制、不修改、不重新签名 `.app`（ADR-0015）。

**范围**：只支持 macOS，只给内置的 claude、codex 家族；其他平台、其他家族说清楚「还不支持」。桌面应用的定义留在内部（`src/families/<id>/desktop.ts`），不进 `FamilyDef` 公开契约。只有订阅账号能打开；API 账号拒绝并说明原因（桌面应用只认订阅登录）。

**找应用**：在 `/Applications`、`~/Applications` 里按 bundle id 找（Claude `com.anthropic.claudefordesktop`，常见名 `Claude.app`；Codex `com.openai.codex`，常见名 `ChatGPT.app`、`Codex.app`），读 `Contents/Info.plist`（二进制 plist 用 `plutil` 读）；按名字找不到再用 `mdfind` 按 bundle id 找。都没有就报错，给下载地址。

**App Data**：主账号用应用默认的数据目录，不加数据目录参数，但也用 `open -n`：不带 `-n` 时 `open` 只会把已经在跑的实例（常常是别的账号的窗口）提到前台。前面已经确认主账号没在跑，所以不会开出第二个主账号实例。其他账号用 `~/Library/Application Support/sideby/<家族>/<账号名>/`，第一次打开时建（权限 700）。它不在宿主账号目录里，sideby 照旧不往宿主账号目录写任何东西。

**启动**：`/usr/bin/open`。启动 `open` 的环境照 §3.5 清掉 Hijack Variables、选择变量和 `SIDEBY_*`，另外清掉调用方所在 agent 会话给子进程设的变量（`CLAUDE_CODE_SESSION_ID`、`CLAUDE_CODE_MESSAGING_TOKEN`、`CLAUDE_CODE_ENTRYPOINT`、`CLAUDE_CODE_CHILD_SESSION`、`CLAUDECODE`、`CLAUDE_PID`、`CLAUDE_PLUGIN_DATA`、`CODEX_COMPANION_*`、`CODEX_THREAD_ID`、`CODEX_SANDBOX*`），免得从 Claude Code 或 Codex 会话里打开的应用继承那个会话；从 Dock 打开的应用本来也拿不到它们。`sideby run` 不变。再按账号加：

| 家族 | 主账号 | 其他账号 |
|---|---|---|
| claude | `open -n -a <Claude.app>` | `open -n -a <Claude.app> --env CLAUDE_CONFIG_DIR=<账号目录> --args --user-data-dir=<App Data>` |
| codex | `open -n -a <ChatGPT.app>` | `open -n --env CODEX_HOME=<账号目录> --env CODEX_ELECTRON_USER_DATA_PATH=<App Data> <ChatGPT.app> --args --user-data-dir=<App Data>` |

- Claude 的 Code 标签页认 `CLAUDE_CONFIG_DIR`，所以用的是这个账号自己的 Claude Code 配置；签名版忽略 `CLAUDE_USER_DATA_DIR`，不用它。
- Codex 用 `CODEX_HOME`，和终端里的这个账号共用 `auth.json` 登录；只给 `--user-data-dir` 会被应用自己的 JS 覆盖，所以照应用自带的「Codex Demo」做法同时设 `CODEX_ELECTRON_USER_DATA_PATH`。这些是应用内部变量，可能随版本变，文档写明。

**已经开着**：先用 `ps -axo pid=,command=` 找这个账号的实例（应用主进程 `<名字>.app/Contents/MacOS/<可执行文件>`；其他账号看参数里有没有 `--user-data-dir=<App Data>`，主账号看主进程有没有 `--user-data-dir`）。找到了就不再启动，用 `osascript -l JavaScript` 像点 Dock 图标那样把它提到前台：先给这一个进程发「重新打开」事件（`aevt/rapp`），窗口都被关掉时应用会重新开一个窗口，再用 `NSRunningApplication.activateWithOptions` 激活（都不需要「自动化」权限；2026-10-14 实测只激活时，关掉了窗口的 Codex 应用会变成前台却什么都不显示）；提不到前台就只说「已经开着」。`ps` 失败时看不出主账号是否在跑，主账号就退回不带 `-n` 的 `open -a`，免得开出第二个主账号实例。sideby 从不结束任何进程。

**第一次登录**：Claude 账号的 App Data 是新的（刚建或只有 sideby 放的链接）、同时还有别的 Claude Desktop 在运行时，提示：登录时先关掉其他 Claude 窗口，因为浏览器回跳的 `claude://` 链接可能被另一个实例接走。只提示，不关任何窗口。Codex 一般不用在应用里登录；账号没登录时提示先 `sideby login`。实测（2026-10-14）：新账号的 Codex 登录页会显示「Welcome back」和主账号的邮箱（这个状态存在 App Data 之外，可能来自系统或浏览器的登录记录），点了就把这个账号登成主账号；提示和文档都要求选「使用其他账号」，或先 `sideby login`。Claude 的登录提示同样写明用这个账号自己的身份登录，不要点它推荐的其他账号。

**共享 `claude_desktop_config.json`**：它是 Claude Desktop 的 MCP 配置，放在 App Data 里。新 App Data 第一次打开时，如果主账号默认 App Data（`~/Library/Application Support/Claude/claude_desktop_config.json`）有这个文件，就建一个指向它的链接；那里已经有东西就不动。Doctor 对已经存在的 App Data 按 §3.3 的 `link` 规则检查它（真文件只报告，从不替换；缺了可以 `--fix` 补链接，只写 App Data），Finding 的 item 是 `app-data/claude_desktop_config.json`，不计入 `shared.total`。这类额外检查自己出错时只给本账号一条 `warn`（`extra-check.error`），不中断整次 Doctor。例外：那里是真文件时不算问题，改按 §3.3 的 `json-key` 规则只核对 `mcpServers` 这一个键（Finding 的 item 是 `app-data/claude_desktop_config.json#mcpServers`）：和主账号一致就没有 Finding；不一致时 `--fix` 只把这个键同步进 App Data 里的这份文件，其他键（Claude Desktop 自己的 `preferences` 等）原样保留，会删掉账号已有条目时同样要 `--force`。原因：主账号第一次打开时还没有这个文件，Claude Desktop 会自己建一份；它保存偏好设置时也会把链接换成真文件（2026-10-16 实测），重新建链接还会被换掉。这不是用户做错了什么，用户真正要共享的是 MCP 设置。`sharedFiles` 里没有 `key` 的文件，真文件仍只给 `warn`（`link.real-file`），并给出改成共享主账号那份的命令。

**入口**：
- CLI：`sideby desktop <账号|短命令> [--json]`。退出码：0 已启动或已在前台；1 不是 macOS、家族没有桌面应用、API 账号、应用没装、`open` 失败（`code` 分别为 `not-macos`、`no-desktop-app`、`api-account`、`app-not-installed`、`open-failed`）；2 缺参数。`sideby app` 已经是面板启动器，所以用 `desktop`。
- 面板：订阅账号所在家族有桌面应用、而且装了时，账号的 ⋯ 菜单里有「打开桌面应用」（正在运行时是「切到桌面应用」）；账号行不放按钮，免得挤掉邮箱和模型。只读面板不显示也拒绝。`/api/account/desktop` 带 `account`。
- `sideby list --json` 和面板状态里每个可用账号多一个 `desktopApp: { app, installed, running }`（只在 macOS、只给有桌面应用的家族的订阅账号；只加字段，`schemaVersion` 不变）。

**已知问题**（文档写明）：Dock 里几个实例图标一样；主账号没开、别的账号开着时，点 Dock 图标切到的是那个账号的窗口，主账号要从 sideby 打开；应用自动更新后重启的那个窗口回到主账号，需要从 sideby 再开一次；Claude 非默认数据目录下 Claude in Chrome 的本地配对不可用；登录回跳可能被其他实例接走（见上）。

**不做（v1）**：自动更新后的看门狗、每个账号一个带颜色图标的启动器 `.app`、公开插件接口、和 Handoff / Auto Handoff 联动。

#### Grok Bot 窗口（2026-10-16 补充，ADR-0019）

Grok Bot（`Grok Bot.app`，bundle id `com.anysphere.sand`）是 xAI 的桌面应用，用 Cursor 账号登录（官方：https://docs.x.ai/grok-bot/get-started ），和 grok 家族（Grok Build，`grok login`）的登录、目录、额度都无关。它的账号菜单能保存几个账号，但同一时间只登录一个。用户要的是几个 Grok Bot 同时开着、各登录一个账号，所以 sideby 把每个 Grok Bot 窗口当成独立的 App Profile（应用配置），不挂在任何 Account 下。

**App Profile**：
- ref 是 `grok-bot:<名字>`，名字规则同账号名（`ACCOUNT_NAME`）。`grok-bot` 和 `grok-bot:main` 是 Main Profile，用应用默认的数据（`~/.grokbot`、`~/Library/Application Support/Grok Bot/`），sideby 不建、不删。
- 其他 Profile 的数据目录是 `~/Library/Application Support/sideby/grok-bot/<名字>/`（权限 700），这里的目录就是 Profile。它不在任何宿主账号目录里。
- 启动：Main 是 `open -n -a <Grok Bot.app>`，其他是 `open -n -a <Grok Bot.app> --args --user-data-dir=<数据目录>`。0.71.2 的代码里这是应用自己的「隔离数据目录」模式：userData 放到那里，数据根目录（会话、本地执行进程、`host.lock`）放到 `<数据目录>/sand-data`，跳过从 `~/.grokbot` 的旧数据迁移。`SAND_DATA_ROOT`、`SAND_USER_DATA_DIR` 会压过这个参数，所以 `open` 前清掉它们，并照 §3.20 清掉 `SIDEBY_*` 和 agent 会话变量。这些是应用内部行为，可能随版本变，文档写明。
- 找应用、已经开着时切到前台、`ps` 失败时 Main 退回不带 `-n` 的 `open -a`、从不结束进程、从不改 `.app`，都和 §3.20 相同。
- 登录状态：读应用自己写的 `desktop-status.json` 的 `signedIn`（其他 Profile 在数据目录里，Main 在 `~/Library/Application Support/Grok Bot/`）。这个文件只有版本、pid、启动时间和这个布尔值，不是凭据；应用关掉后它停在最后的状态。读不了或格式不对就是未知（字段不出现）。登录的是哪个 Cursor 账号本地读不到，不显示；用户靠 Profile 名字区分。

**入口**：
- `sideby desktop grok-bot[:<名字>] [--json]`：Profile 不存在就建数据目录再打开（`createdAppData: true`），开着就切到前台。输出和退出码同 §3.20 的 `desktop`（`ref` 是 Profile 的 ref，`family` 是 `grok-bot`）；名字不合法 `code: invalid-name`。新建的 Profile 给登录提示：用这个窗口要用的账号登录；同时还有别的 Grok Bot 在运行时，先关掉它们再登录（浏览器回跳可能被别的窗口接走）。
- `sideby desktop grok-bot:<名字> --remove [--yes] [--json]`：删掉这个 Profile 的数据目录，也就是退出这个窗口的登录、删掉它的本地数据。不带 `--yes` 只说明会删什么，退出码 10（`--json` 输出 `{ ref, appData, removed: false }`）；带 `--yes` 删除后 `removed: true`。Main 不能删（`code: main-profile`）；窗口开着时拒绝（`code: app-running`）；目录不存在（`code: no-profile`）；数据目录是链接或不是目录时拒绝（`code: app-data-invalid`），不跟进链接。不是 macOS 同样 `not-macos`。删除只发生在 `~/Library/Application Support/sideby/grok-bot/` 之内。
- `sideby list`：表格下方多一段 Grok Bot，每行 ref、开着、已登录；`--json` 顶层多一个 `appProfiles: [{ ref, app, name, isMain, appData?, installed, running, signedIn? }]`，Main 在前，其他按名字排。只在 macOS，且装了 Grok Bot 或已有 Profile 时有内容；只加字段，`schemaVersion` 不变。
- 面板：账号分组后面一组「Grok Bot」，每行名字、开着 / 已登录状态和「打开」（开着时「切到窗口」），非 Main 行有「删除」（确认框写明会退出这个窗口的登录、删掉它的本地数据；开着时不能删）。组底部「再开一个 Grok Bot」：名字预填下一个空闲的三位数（`001`、`002`…），可改，建好立刻打开。只读面板只显示状态。没装 Grok Bot、也没有 Profile 时这一组不出现；家族筛选选了某个家族或只看需要处理时也不出现；搜索按名字和「Grok Bot」匹配。接口 `/api/app-profile/open`（`ref`）、`/api/app-profile/remove`（`ref`，删除即确认过）。
- grok 账号没有桌面应用：`sideby desktop grok:<名字>` 报 `no-desktop-app`，提示改用 `sideby desktop grok-bot:<名字>`。

**不做**：读出 Grok Bot 登录的邮箱（要读凭据）、把 Profile 和 grok 账号关联、迁移 Grok Bot 账号菜单里保存的账号、改 Profile 名字（删了再建）。

**测试**：`open`、`ps`、`osascript`、`plutil`、`mdfind` 都经过一个可注入的执行函数，测试从不启动真实应用。断言每个家族主账号和其他账号的 `open` 参数与环境、已在运行时只激活不启动、API 账号和非 macOS 拒绝、没装应用的报错、链接从不覆盖真文件、宿主账号目录快照无差异。

### 3.21 同一登录（2026-10-14 补充，ADR-0016）

同一家族的两个以上订阅账号，用同一个身份登录（例如 `~/.claude` 和 `~/.claude-001` 都登录了同一个 claude.ai 账号和组织），是 Same Login（同一登录）。目录、会话、Usage 各自独立，但供应商只算一份 Quota。sideby 自己认出来，不迁移、不删除、不合并目录，Doctor 不报。

**判定**（`core/same-login.ts`）：
- 同一家族、两边都是订阅账号、两边都有 email 且相同（不分大小写）。
- 组织：两边都有且相同（不分大小写），或两边都没有。一边有、一边没有不算同一登录。
- Codex（2026-10-18 补充，ADR-0028）：email 相同之外，两边的 Login Key 也要相同。Login Key 是 `auth.json` 里 `tokens.id_token` 的 auth claim 中 `chatgpt_account_id`（工作区）和 `chatgpt_user_id` 合起来的 SHA-256，取前 16 位十六进制，只在分组时比较，不进入任何输出、错误、日志、缓存或面板；token 和其余 claim 读完即丢。任一边没有 Login Key 就不算同一登录。Claude 仍按 email 加组织判定。
- 没有 email 的账号（API 账号、已退出登录）不参与。
- v1 只对 claude 家族开启。Codex 的身份只有 email，同一个 email 可以属于几个 ChatGPT 工作区、各有额度，等 ADR-0003 能区分工作区再说。开关在内部，不进 `FamilyDef`。
- 身份只来自已有的身份读取器（§3.7「账号身份」），不读任何凭据。

**额度**：组里每个账号显示组内最新的一份额度（`observedAt` 最晚；相同时用自己的）。借来的结果带 `from: <ref>`，表示读自哪个账号，`observedAt` 是那份数据的时间。组里没有任何一份可用额度时，各自显示自己的原因。Usage 不共享，仍按目录统计。`rt.quota()` 统一做这一步，所以 `sideby quota`、面板、`sideby next`、Auto Handoff 看到的是同一份。

**输出**：
- `sideby list --json` 和面板状态的账号带 `sameLogin: string[]`（同组其他账号的 ref，只在有时出现）。`sideby list` 文本在账号名后面加 `= main` 这样的标记，表格下方说明一次「= 表示同一登录，共用一份额度」。
- `sideby quota --json` 的 `quota` 带 `from`；文本在数据时间后加「read from claude:001」。
- 只加字段，`schemaVersion` 仍为 1。

**Handoff**：
- 排序用共享后的额度，所以同一登录的账号压力相同，满了一起满。
- `sideby next` 从 sideby 启动的会话里运行时（环境里有 `SIDEBY_ACCOUNT`，且是这个家族的账号），这个账号就是当前账号：`--json` 带 `from`；和它同一登录的账号带 `sameLoginAs: <当前账号>`，照常列出、不会被选，文本里注明「same login as …」。
- Auto Handoff（§3.17「选号」）去掉与原账号同一登录的账号。`policy: order` 里写了这样的账号时同样跳过，选号结果带 `skipped: [{ ref, reason }]`，终端说明原因；`sideby handoff status` 在 `notes` 里说明哪些账号是同一登录。
- 面板「下一个」标记用共享后的额度排序（面板没有当前账号）。

**面板**（2026-10-17 再改，ADR-0026）：列表视图里，同组且都在当前筛选结果里的账号合成**一行**，放在组里排序最靠前的成员的位置。
- 这一行的名字是组里排序第一的成员（主账号在前，再按名字），后面跟它的短命令，再跟一个灰色小标签「2 个目录 · 共用额度」（悬停写「这几个目录登录的是同一个账号，额度一起算」）。邮箱、「用浏览器打开」、额度（组内最新的一份）都只显示一次。「最近使用」取成员里最新的一次。
- 「下一个」：任何成员是 `sideby next` 的选择时，标在这一行上。
- 展开后，先写一句「这几个目录登录的是同一个账号，额度一起算」，下面每个目录一行：名字、短命令、各自的「最近使用」、近 7 天 token、健康、按钮「复制启动命令」（`sideby run <ref>`）和它自己的「…」菜单。
- 这一行的「…」菜单：最上面是「置顶 / 取消置顶」（§3.25，对整组生效），然后每个目录一段，段首是目录名和短命令，段内是只属于这个目录的操作（复制启动命令、短命令、桌面版、目录、模型、上下文调优、体检）；最后是共用的操作（用浏览器打开、复制登录命令、复制邮箱、新建同类账号）。
- 额度提醒（名字后的圆点、关注计数、家族标题的关注标记）每组只出现一次，在这一行上；关注计数仍只算额度读自自己的那个成员。成员自己的问题（体检、未登录）在展开后的目录行上标圆点。
- 筛选后只剩一个成员时照常显示单行，展开后写「与 main 同一登录」。卡片视图每个目录仍是一张卡片，带「与 main 同一登录」标记。
- 额度的悬停说明在借来时写「与 001 同一登录；额度读自 001，X 分钟前」。额度数据过时（§3.6）时不另起一行，在百分比后放一个时钟图标，悬停写「截至 X 前」；进度条保持该级别的颜色、变淡，和数字颜色一致。显示组织名时去掉末尾多余的逗号、句号。

- 显示哪个目录的名字（2026-10-17 补充）：用「我的顺序」里排在最前的那个目录；都没排过时用主账号，再按名字。展开后每个目录一行，当前显示的那个标「显示名」，其余有「设为显示名」，点了把它在 `display.accounts.<family>` 里挪到当前显示名前面（不新增配置项）。CLI 同样做：`sideby order claude 001`。「恢复默认顺序」后回到主账号。

（2026-10-17 上午的版本是每个目录一行、左边竖线连成一组、其余行写「与 main 共用额度」。读起来像两个账号，额度画两次也让人以为有两份；改成一行，见 ADR-0026。）

### 3.22 Remote Control 默认关闭（2026-10-15 补充，ADR-0017）

Claude Code 的 Remote Control 把本机会话连到 claude.ai/code 和 Claude 手机 App，登录同一个 claude.ai 账号的设备都能看到并继续这些对话。`/config` 里的「Enable Remote Control for all sessions」把它存成用户 `settings.json` 的 `remoteControlAtStartup`：`true` 每个交互会话都自动连接，`false` 不自动连接，没有这个键时跟随组织或 Claude Code 的默认值（可能是开）。来源：https://code.claude.com/docs/en/remote-control 。

sideby 帮用户一键把所有 Claude 账号改成不自动连接，会话里仍可手动 `/remote-control`。

**读**（`core/remote-control.ts`）：每个 Claude 账号的 `settings.json` 按真实文件分组（链接到主账号的共用一组，同 §3.18 的做法），每组只读 `remoteControlAtStartup` 一个键：
- `on`：值为 `true`。
- `default`：没有这个键（跟随默认值，可能自动连接）。
- `off`：值为 `false`。
- `missing`：账号没有 `settings.json`。
- `blocked`：文件不是普通文件、不是 JSON 对象、太大，或是指向不存在文件的链接；附原因。

**关闭**：`on` 和 `default` 的组写成 `false`，经 `writeIfUnchanged`，其他键、缩进、文件权限原样；链接写到真实文件，说明还影响哪些账号，不新建、替换或改指链接。`missing` 不新建文件（`settings.json` 是 link 类共享项，新建真实文件会造成 Drift），提示先运行 `sideby doctor --fix`。`blocked` 跳过。每组在状态目录 `remote-control/<文件哈希>.json` 记原值，撤销只在键仍是 sideby 写的值时还原（原来没有就删掉键）；记录里 `wrote` 存写入的值，旧记录没有这个字段时按 `false`。已经开着的会话不受影响，要重开；输出这么说。

**命令**：
- `sideby remote-control [--json]`：每组的文件、账号、状态。
- `sideby remote-control off [--yes] [--json]`：不带 `--yes` 只显示计划，退出码 10；带 `--yes` 写。
- `sideby remote-control on [--yes] [--json]`（2026-10-16 补充）：把 `off` 和 `default` 的组写成 `true`，规则同「关闭」；预览里写明打开后登录这个账号的设备都能看到新会话。sideby 只在用户要求时打开，从不自己打开。
- `sideby remote-control undo [--yes] [--json]`：同样先预览。

**面板**：有 `on` 的组时，顶部出提示条「Remote Control 会自动开：claude.ai 和 Claude 手机 App 能看到这些账号的对话」，按钮「全部关闭」打开确认框，列出要改的文件、从什么改成什么、涉及哪些账号；确认后 toast 带「撤销」。「不再提示」只记在本浏览器。只读面板不显示按钮。顶栏「设置」菜单里常驻一行「Remote Control」（有 Claude 账号就显示），写当前状态：有订阅账号的组是 `on` 为「开」，否则有 `default` 为「默认」，否则「关」（只含 API 账号的组不算，它们连不上 claude.ai）。点开对话框列出每组的文件、状态和账号；对话框里有一个开关「新会话自动打开：开 / 关」（按钮状态就是汇总状态，`default` 时两边都不按下）；切到另一边后，列出会变的每个文件（从什么改成 `true` 或 `false`），切到「开」时加一条警示（其他设备上登录这个账号的人都能看到并继续对话），点「确认打开」或「确认关闭」才写，「取消」退回；sideby 改过的组给「撤销上次更改」。状态是「开」时，「设置」按钮带一个橙色圆点。关掉提示条或点过「保持开启」后，仍从这里看状态、关闭。（2026-10-16 修订：原来面板只能关，要开得去会话里的 `/config`，新手找不到。）

**不做**：不写 `disableRemoteControl`（会连手动开启也禁掉，用户选了只关自动）；不改 sideby 启动参数（没有关闭用的参数，见 ADR-0017）；不碰 `~/.claude.json`；不结束正在运行的会话。

### 3.23 检查更新与更新（2026-10-16 补充，ADR-0021）

- **CLI 补充**：`sideby update --auto on|off [--json]` 直接保存 Auto Update 开关，保留其他 update 配置；本次不查更新、不安装。JSON 带 `auto`、`changed`，成功退出 0。

**检查**（`core/update.ts`）：每 24 小时最多一次，`GET <registry>/-/package/sideby/dist-tags`（默认 `https://registry.npmjs.org`，`SIDEBY_UPDATE_REGISTRY` 可换镜像），5 秒超时，只取 `latest`。不带账号、路径、身份。结果写 `$XDG_STATE_HOME/sideby/update.json`（`checkedAt`、`triedAt`、`latest`、`notified`、`auto`、`autoTriedAt`），CLI 和所有 Panel 共用。失败不提示；`triedAt` 让下一次尝试至少隔一小时，离线时 CLI 和面板都不会每次刷新都起请求。`SIDEBY_UPDATE_REGISTRY` 只接受 http/https；消息里显示时去掉 URL 里的用户名和密码。

关闭：`NO_UPDATE_NOTIFIER` 或 `SIDEBY_NO_UPDATE_NOTIFIER` 有值、config `update.check: false`、CI（`CI`、`CONTINUOUS_INTEGRATION`、`BUILD_NUMBER`）、本地构建（`dist/build.json` 有 `local: true`，见下文「本地构建」）。关闭后不发请求、不提示；用户自己运行 `sideby update` 仍会查。

**CLI 提示**：命令结束后在 stderr 打一行 `sideby 0.12.0 is available (you have 0.11.0) · sideby update`，同一版本每天最多一次。条件：stderr 是终端、没有 `--json`、命令不是 `statusline-tap`、`handoff-hook`、`shell-init`、`update`、`ui --serve-detached`、`update-check`，也不是 `handoff ready`。`run`、`next`、`resume` 在 Host 退出后才打印。缓存超过 24 小时，同样条件下另起分离的 `sideby update-check` 进程去查，本次不等。

**JSON 提示**（2026-10-17 补充，参照 lark-cli 的 `_notice`）：agent 经 skill 调用时用 `--json`，又不是终端，看不到上面那行。所以带 `--json` 的命令（`update`、`update-check`、`shell-init`、`ui --serve-detached`、`handoff ready` 除外）在输出里多一个 `_notice`，成功和出错的输出都带：
- `_notice.update`：缓存里的最新版本比当前新，`{ current, latest, command: "sideby update", message }`。
- `_notice.skill`：`~/.agents/skills/sideby/SKILL.md` 或 `~/.claude/skills/sideby/SKILL.md`（同一真实文件只算一次）的 `metadata.version` 和当前版本不同，`{ installed（没有版本时为 null）, current, command: "sideby update", message }`（2026-10-17 修订：和 CLI 同一个更新入口）。
- 只读缓存和这两个文件，不联网；检查关闭（变量、config、CI、本地构建）时不带。缓存超过 24 小时，同样另起分离的 `sideby update-check`，只靠 agent 用的机器也能拿到新版本。每次都带（不按天去重），由 skill 规定每次对话只提一次。
- skill（`references/update.md`）：先做完用户的事，最后用一句话提有更新并主动问要不要帮忙；同意后 `sideby update --json`（退出码 10）→ 用户确认 → `--yes`；不能自己更新的安装方式把命令交给用户；`_notice.skill` 在时，用户同意后同样走 `sideby update --json` → `--yes`。

**安装方式**（Install Method），按本包所在真实路径判断：

| 路径 | 方式 | Update 执行 |
|---|---|---|
| `dist/build.json` 有 `local: true` | `local` | 只给 `pnpm local --off`（在 sideby 仓库里运行，回到 npm 版） |
| 含 `/_npx/` | `npx` | 只给 `npx sideby@latest` |
| 含 `/.volta/` | `volta` | 只给 `volta install sideby@<v>`（Volta 自己管理全局包，绕开它会破坏它的记录） |
| `<prefix>/lib/node_modules/sideby` | `npm` | `npm install -g --prefix <prefix> sideby@<v>` |
| 含 `/pnpm/global/` 或在 `PNPM_HOME` 下 | `pnpm` | `pnpm add -g sideby@<v>` |
| 含 `/.bun/install/global/` | `bun` | `bun add -g sideby@<v>` |
| 其他 `node_modules/sideby` | `project` | 只给 `npm install sideby@<v>` |
| 不在 `node_modules` 下 | `source` | 只给 `git pull` |

**本地构建**（Local Build，2026-10-16 补充，ADR-0024）：维护者在仓库里运行 `pnpm local`，让全局 `sideby` 和 Portal 里的面板马上用上工作树的代码。
1. 把工作树编译到 `$XDG_DATA_HOME/sideby-dev`（默认 `~/.local/share/sideby-dev`）下的新目录，带 `package.json`、`schemas`、`skills`、README、`LICENSE` 和指向仓库 `node_modules` 的链接；`dist/build.json` 写 `{ id, local: true, commit, dirty, builtAt }`。
2. `tsc` 成功、`node dist/src/cli/main.js --version` 输出包版本，才切换；否则旧版本不动，退出 1。
3. 切换是两次改名：`pkg` 移到 `old/<id>`，新目录改名为 `pkg`。全局 `sideby` 解析到的目录一直是 `pkg`，Portal 读到新的 `build.json` 就换新代码；`old/` 留最新 3 个。
4. 第一次运行把 npm 全局包 `<prefix>/lib/node_modules/sideby` 换成指向 `pkg` 的链接（原包移到 `sideby-dev/npm`），并保证 `<prefix>/bin/sideby` 指进去。只支持 npm 全局安装；pnpm、bun、Volta 时停下说明。
5. 有后台 Panel 在跑就从新代码重启；打开的页面和 Portal 照常自己重新加载。
- `pnpm local --back`：和最新的 `old/` 互换。`pnpm local --off`：删链接，放回原 npm 包（没有就 `npm install -g sideby`）。
- 本地构建不检查更新、不提示、不自动更新；面板版本胶囊显示 `v<版本>-dev · <commit>`，工作树有未提交改动时后面加 `+`，弹层里写构建时间。
- **在面板和 CLI 里切换**（2026-10-17 补充，ADR-0024 修订）：维护者不用回到仓库敲命令，就能在本地构建和 npm 正式版之间来回切。
  - `sideby local [on|off] [--yes] [--json]`：不带参数只看状态：全局 `sideby` 现在跑的是本地构建还是 npm 包（`running`）、留着的本地构建（`local`：commit、是否有未提交改动、构建时间）、放在一边的 npm 包版本（`kept`）。`on` 切回 `sideby-dev/pkg` 里最近一次 `pnpm local` 的构建，不重新编译；`off` 做 `pnpm local --off` 的切换部分（留着的 npm 包不比 `latest` 旧就放回，否则 `npm install -g sideby@<latest>`）。先预览、退出 10，`--yes` 才执行。只支持 npm 全局安装；没有本地构建时 `on` 退出 1，提示先在仓库运行 `pnpm local`。
  - 执行时和 Update 共用 `update-install.lock`；安装失败就把链接接回本地构建，全局 `sideby` 不会没有。切完有后台 Panel 就由新代码按名字重启。`off` 切到 npm 后由 npm 的代码按名字跑一次 `sideby update --yes`，skill 落后就一起补上（结果 `skillSynced`，失败不影响切换）；`pnpm local --off` 也走这一步。面板里不等它：skill 要联网拉取，可能要几分钟，比 Portal 等回应的时间长，所以 `/api/local` 切完就返回，同步在后台单独跑（`skillSyncStarted`），它自己拿安装锁，跑完前再切换会提示稍候。页面收到 5xx（Portal 换新代码时可能这样回）先读一次状态，切换已经生效就照常等新版本刷新，没生效才报错。
  - 面板：状态 `update.localSwitch`（字段同上，另有不能切换时的 `reason`），只有本地构建在跑、或留着一份本地构建时才有，普通 npm 用户看不到。版本弹层里一个按钮：本地构建在跑时是「切换到正式版」，否则是「切换到本地构建 <commit>」并写构建时间。点了显示「正在切换…」，`/api/local` 带 `{ to, confirm: true }`；切完页面等服务端换成新 build 就自动刷新，20 秒没等到（前台 `sideby ui`、启动后不再查包的 Portal）就提示并给「刷新页面」按钮。只读面板不显示按钮，`updates: false` 时 `/api/local` 返回 403。

设了 `SIDEBY_UPDATE_REGISTRY` 时，安装命令带同一个 `--registry`，装的就是检查看到的那个源。npm 的 `<prefix>/lib/node_modules` 或 `<prefix>/bin` 不可写时，也只给命令（多半要换 Node 版本管理器或 `sudo`，sideby 不替用户提权）。

**`sideby update [--yes] [--json]`**：查一次 registry（不看开关），列出当前版本、最新版本、安装方式、要执行的命令。已是最新：退出 0。能执行时不带 `--yes` 退出 10；带 `--yes` 执行，输出命令的 stdout/stderr 原样转给用户，然后重启后台 Panel（有的话）；装了桌面应用（`sideby app install`，主文件带标记）就从新代码按名字跑一次 `sideby app install --json` 并等它结束，让应用记录新的 Node 和入口、换上新图标，失败不影响 Update 成功（`--json` 的 `refreshedApp`，面板 `/api/update` 同名字段；2026-10-16 补充）；没装就不跑。提示前台 `sideby ui` 要重启、正在运行的会话下次启动才用新版本、已装的 sideby skill（`~/.agents/skills/sideby`、`~/.claude/skills/sideby`）版本不对时一起更新（2026-10-17 补充）：计划里列出 `skillUpdate`（`installed`、`outdated`、`command`、`canRun`、`reason`），CLI 装完后跑 `npx -y skills update sideby -g -y`（沿用安装时选的 agent），失败不影响 Update，结果写 `skillUpdated`；CLI 已是最新而 skill 旧时，`sideby update` 只更新 skill（同样先预览、退出码 10）；skill 所在目录在 git 仓库里（比如 dotfiles 克隆）、而 skills 工具的安装记录里没有它时不动它，写明原因和命令 `npx skills update sideby -g`，由那个仓库负责；安装记录见下文「skill 与 CLI 一起更新」。只能给命令的方式退出 1，说明原因和命令。

**同一时间只跑一个 Update**：`sideby update --yes`、面板按钮和自动更新共用 `update-install.lock`（内容是 pid 和时间）。持有者还在运行且锁不到一小时就算被占用，后来者立即失败并提示稍后再试；空锁一分钟内也算占用（对方可能正在写）。

**自动更新**：config `update.auto`，默认关。命令结束后，检查到期，或缓存里有还没装过的新版本（从没试过，或上次失败已过一天），就起后台检查。后台检查同时满足以下条件才执行 Update：安装方式是 npm/pnpm/bun 且可写；`$XDG_STATE_HOME/sideby/running/` 下没有还在运行的 pid（`run`、`next`、`resume` 运行时各写一个，退出时删，死掉的 pid 跳过并删除）；主版本号不变（`0.11` → `0.12` 可以，`0.x` → `1.0`、`1.x` → `2.0` 只提示）。被正在运行的会话挡住时记 `autoTriedAt`，一小时内不再起后台检查。用户不处理就不会消失的阻塞（这种安装方式不能自己更新、大版本）记成一次失败的 `auto`：提示一次原因，一天后再看。被手动 Update 占着锁时不算失败。结果记在 `update.json` 的 `auto`，下一次命令打一行 `sideby updated itself to 0.12.0` 或失败原因，只打一次；失败的版本一天后再试（镜像可能还没同步）。

**skill 与 CLI 一起更新**（2026-10-17 补充，ADR-0021 修订）：用户只认一个「sideby 版本」。agent 读的 sideby skill 是这个版本的一部分，CLI 和 skill 的 `metadata.version` 都等于当前版本才算「已是最新」。
- 谁能更新 skill：skill 真实目录上两级（`~/.agents/skills/sideby` → `~/.agents`）有 skills 工具的安装记录 `.skill-lock.json`，且其中 `skills.sideby.source` 是 `Adonis0123/sideby`，就由 sideby 跑 `npx -y skills update sideby -g -y`，即使目录在 git 仓库里（改动会出现在那个仓库的 `git status` 里，由用户决定提交）。只读这一个键。没有这条记录又在 git 仓库里时不动，给出 `npx skills update sideby -g`。Doctor 的 `skill.outdated` hint 用同一规则。
- 自动更新打开时：后台检查发现 CLI 已是最新（缓存里没有更新的版本）而 skill 落后、sideby 能更新它，就只更新 skill，不等 CLI 出新版本；结果记在 `update.json` 的 `skillAuto`（`to`、`at`、`ok`、`message`、`shown`），下一次命令打一行，只打一次；失败一天后再试。CLI 自动更新时同样带上 skill（之前后台计划漏了 skill）。CLI 有新版本却不能自动装时，不单独更新 skill：skills 工具拉的是仓库默认分支，会比 CLI 新。
- 终端提示：自动更新关闭、skill 落后时，命令结束后打一行 `the sideby skill agents read is for 0.13.1 (this sideby is 0.14.0) · run \`sideby update\``，同一 CLI 版本每天最多一次（`skillNotified`）；条件同 CLI 提示。
- 原因代码：安装方式和 skill 计划带 `reasonCode`（`local-build`、`npx`、`volta`、`not-writable`、`project`、`source`、`skill-in-git`），需要路径时另带 `reasonAt`；检查关闭带 `checksOffCode`（`local-build`、`env`、`config`、`ci`）。`reason` 英文原样保留，面板按语言显示代码对应的文字。
- `pnpm local --off` 切回 npm 版后跑一次 `sideby update --yes`，skill 落后就一起补上；`pnpm release` 收尾时经它同样补上。本地构建期间不提示 skill。
- 已知风险：skills 工具从 GitHub 默认分支拉取，两次发版之间可能教还没发布的命令；暂不按 tag 安装。

**面板**：

### 3.24 浏览器里登录过哪个账号（2026-10-16 补充，ADR-0023）

账号多了，用户会忘记在哪个 Chrome 用户（Browser Profile）里登录过哪个 claude.ai 或 chatgpt.com 账号。sideby 从本机浏览器数据里找出对应关系（Browser Sign-in），并能用那个浏览器用户直接打开官网。全部在本机完成：不联网、不上传、不解密。

**范围**：v1 只做 macOS 的 Google Chrome（`~/Library/Application Support/Google/Chrome`）。匹配：Claude、Codex。Grok、pi 不匹配，只能手选浏览器用户打开。其他 Chromium 浏览器以后只加目录。

**WSL**（2026-10-16 补充）：WSL 里的 sideby 读 Windows 那一侧的 Chrome，因为 WSL 用户的浏览器装在 Windows 上。判断是 WSL：`process.platform` 是 `linux`，且有 `WSL_DISTRO_NAME` 或 `/proc/sys/kernel/osrelease` 含 `microsoft`。
- 找目录：经 `DesktopDeps.exec` 跑 `/mnt/c/Windows/System32/cmd.exe /d /c echo %LOCALAPPDATA%^|%ProgramFiles%^|%ProgramFiles(x86)%`，把 `X:\...` 换成 `/mnt/x/...`，进程内记住。cmd.exe 失败时扫 `/mnt/c/Users/*/AppData/Local/Google/Chrome/User Data/Local State`，只有恰好一个时才用，多个不猜（进 `problems`）。Chrome 数据在 `<LOCALAPPDATA>/Google/Chrome/User Data`，读法与 macOS 完全相同。
- 找 Chrome：依次 `<ProgramFiles>`、`<ProgramFiles(x86)>`、`<LOCALAPPDATA>` 下的 `Google/Chrome/Application/chrome.exe`；都没有就给下载页。
- 打开：`cmd.exe /d /c start "" "<chrome.exe 的 Windows 路径>" --profile-directory=<dir> <url>`，`start` 立即返回，不等 Chrome 退出。Windows 路径含 `"%&|<>^` 时拒绝。
- 文字不标「Windows」：WSL 用户只有这一个 Chrome。
- 原生 Linux 的 Chrome 和 `sideby desktop` 不在此列。

**读浏览器**（`core/browser-profiles.ts`，只读）：
- `Local State`：只取 `profile.info_cache` 里每个 profile 的目录名（如 `Profile 7`）、显示名（`name`），和它在 Chrome 里登录的 Google 账号邮箱（`user_name`，是邮箱时才取；2026-10-16 补充：用户要的是"哪个 Google 账号"，显示名常常只是 adonis1 这样的昵称）。不取 `gaia_id`、头像或其他字段。面板显示这个邮箱（没有时显示名字），「隐藏邮箱」同样遮住它；`--profile` 也接受这个邮箱。
- `<profile>/Local Storage/leveldb`：解析 `.log` 和 `.ldb`（含 Snappy 解压，自写，不加依赖），只保留来源为 `https://claude.ai`、`https://chatgpt.com` 的键名。`.ldb` 的数据块整块 Snappy 压缩，键和值在一起，所以整块解压进内存，取完键名就丢掉；值的字节只是跳过，不转成文字。键格式是 `_<origin>\0` 后跟 `\x01`（Latin-1）或 `\x00`（UTF-16）编码的键名；值不解码、不保留、不比较。单个文件超过 64 MB 跳过，记一条问题。
- 不打开 `Cookies`、`Login Data`、IndexedDB、Keychain；不写、不锁、不复制任何 Chrome 文件；Chrome 运行时照样读（leveldb 文件只追加或整体替换，读到半截的记录丢掉）。
- 每个文件的解析结果按 mtime 和大小记住，文件不变不重读（`core/file-memo.ts`）。

**读 Host**（扩充 §3.7「账号身份」，只用于匹配）：
- Claude：`.claude.json` 的 `oauthAccount.accountUuid`。
- Codex：`tokens.id_token` 里 `https://api.openai.com/auth` 下的 `chatgpt_user_id`，没有时取 `user_id`。解码方式和取 email 相同，token 和其他 claim 丢掉。不用 `tokens.account_id`（它是工作区 ID，键名里没有）。
- 这个 ID 只在内存里比较，不进 `AccountIdentity`、任何输出、错误、日志或缓存。测试断言它不出现在 `--json` 和面板状态里。

**匹配**：Host 的完整 ID 作为键名里的一整段出现（以 `.`、`/`、`:`、`-` 或首尾为界；Codex 的 `user-<id>` 原样比较，不增删前缀），就算一次 Browser Sign-in。网站会给当前登录的账号存好几个 key，退出或切换账号后常留下一两个旧 key。所以只留最强的痕迹：一次匹配的 key 数，至少是同一个 ID 在所有浏览器用户里最多那次的一半，也至少是同一个浏览器用户里同一网站最多那个 ID 的一半，否则不算。剩下的全部列出，按该 profile 的 Local Storage 最后修改时间排序，最近的在前。Same Login 的账号 ID 相同，会一起对上，这是对的。

**措辞**：只说「浏览器用户 adonis2 登录过」/「Signed in from Chrome: adonis2」，不说「当前登录」。悬停说明：「根据本机 Chrome 的数据判断，退出登录后可能仍会显示。数据只在本机读取，不会上传。」

**开关**：config `browser.signIns`，默认 `false`。关闭时不读任何浏览器文件。打开前先显示会读什么（上面两类文件、只看键名、不碰 Cookie 和密码），确认后写 config，和其他 config 改动一样先预览。只读面板不能打开。

**打开**：macOS 用 `/usr/bin/open -na "Google Chrome" --args --profile-directory=<dir> <url>`（WSL 见上），网址 Claude `https://claude.ai`、Codex `https://chatgpt.com`、Grok `https://grok.com`。只启动 Chrome，不改任何 profile。`<dir>` 必须是 `Local State` 里列出的目录名，否则拒绝。所有程序经可替换的 `exec`（同 §3.20 的 `DesktopDeps.exec`），测试不启动真浏览器。没有装 Chrome 时说明并给出下载页。

**命令**：
- `sideby browser [--json]`：每个浏览器用户和它登录过的账号；关闭时提示 `sideby browser --enable`。
- `sideby browser --enable [--yes]` / `--disable [--yes]`：不带 `--yes` 显示计划，退出码 10。
- `sideby browser open <account> [--profile <dir|name>]`：只有一个对应时直接打开；多个或没有时列出可选的浏览器用户并退出 1，提示加 `--profile`。
- `--json` 带 `schemaVersion: 1`，profile 只有 `dir`、`name`、`signIns: string[]`（账号 ref）、`changedAt`；新 schema `schemas/browser.json`。

**面板**：
- Claude、Codex、Grok 的订阅账号，⋯ 菜单里有「在浏览器打开」。对上了浏览器用户的账号，邮箱后面还有一个链接「🌐 <浏览器用户名字>」（悬停说明是 Chrome），点了直接用它打开；空间不够时先截短邮箱，不截这个名字。没对上的账号行里不放按钮。只读面板不显示。
- 关闭时：按钮写「在浏览器打开」。点开的对话框说明会读什么、数据只在本机、不碰 Cookie 和密码，再给一个「开启」按钮；点了就写 config（对话框本身就是预览）。
- 开启后：只对上一个浏览器用户时，按钮写「Chrome：Work」，点一下直接打开；对上多个时写「Chrome：Work 等 2 个」，点开对话框选。对话框先列登录过的浏览器用户，再列其他浏览器用户，每个都有「打开」按钮，底部有「关闭查找」。没对上时说明原因，并列出所有浏览器用户；Grok 说明 grok.com 没有可比对的信息。
- 浏览器用户的名字跟着身份遮蔽开关一起遮住（名字本身可能是邮箱）。
- 读取出错（Chrome 没装、目录读不了、文件损坏）进 `problems`，不影响其他内容。

**已知限制**：键名是网站内部的，改版后会失效，失效时显示「没找到」，不报错；退出登录后留下的旧键仍算登录过；同一 Chrome 用户里切换过多个账号会都列出来；Grok 网页本地没有能对上的 ID。

**不做**：不解密 Cookie、不读 Keychain、不调网站接口、不用 DevTools 调试端口、不装浏览器扩展、不读键的值。

### 3.25 显示顺序（2026-10-17 补充）

- **CLI 补充**：`sideby pin|unpin <account|short command> [--json]` 按 Same Login 整组操作，每 Family 最多 3 组，新置顶排最后，重复操作不改变顺序；第四组报错并提示先 unpin。`sideby order [--json]` 显示每 Family 的实际顺序并标注置顶；`sideby order <family> <name>...`、`sideby order --families <id>...` 保存顺序，未知名字报错；`sideby order --reset` 清除 Family 和账号顺序，保留置顶。写入时去掉已不存在的名字，沿用原子配置写入。以下原有“没有 CLI”描述由本补充取代。

用户在面板里拖出来的 Family 和账号顺序（Display Order，见 `CONTEXT.md`），面板上叫「我的顺序」。它只管显示：Handoff Order、`sideby next` 和 Auto Handoff 的选号都不看它。

**配置**：`config.json` 新增可选的 `display`：

```json
{ "display": { "families": ["codex", "claude"], "accounts": { "claude": ["003", "main", "001"] }, "pinned": { "claude": ["work"] } } }
```

- `families`：Family id 的顺序。`accounts.<family>`：这个 Family 里账号名的顺序（名字，不是 ref，也不是短命令）。`pinned.<family>`：置顶的账号名（见下文「置顶」）。
- 没写进去的 Family 排在写了的后面，按原来的顺序（内置的 claude、codex、grok、pi，再按插件加载顺序）。没写进去的账号排在这个 Family 写了的账号后面，按原来的顺序（主账号在前，再按名字）。所以新建的账号、新装的插件排在最后，不打乱已有顺序。
- 写了但已经不存在的名字直接忽略，不报错，Doctor 也不报；下一次写入时去掉。
- 校验：每个值都必须是字符串数组，不能重复；写错时 config 报错，指出键名和修法。
- sideby 只在面板里写这个键：移动或置顶后整份替换 `display`；「恢复默认顺序」删掉 `families` 和 `accounts`，保留 `pinned`。写法同 §3.10 的其他键（保留其他键和顺序，原子写，读写之间文件被改过就拒绝）。没有 CLI 命令；手写 config 也可以。

**哪里用它**：

- `sideby list`（文本和 `--json`）按它排：先排 Family，再排每个 Family 里的账号。
- 面板的分组在任何排序模式下都按它排。排序下拉框新增「我的顺序」，选它时组内账号也按它排；「按额度」「按名称」「按最近使用」只重排组内账号，手动顺序保留不变。默认模式仍是「按额度」，没拖过的用户看到的和以前一样。
- `/api/state` 带 `display: { families, accounts, pinned }`（config 原样，没写时是空对象），页面用它排序。

**置顶**（Pinned，2026-10-17 补充）：`display.pinned.<family>` 是这个 Family 里置顶账号的名字，按显示的先后。
- 置顶的账号在任何排序模式下都排在本组最前，按 `pinned` 的先后；其余账号照常按当前排序。`sideby list` 同样把它们排在本组最前，`--json` 的账号带 `pinned: true`（只在置顶时出现）。
- 只管显示：`sideby next`、Auto Handoff、「下一个」标记都不看它。
- 每组最多 3 个（同一登录的一组算一个）。满了时菜单项变灰，写「每组最多置顶 3 个」。
- 同一登录（§3.21）一起置顶、一起取消。
- 入口（2026-10-18 改）：每行「…」菜单最上面的「置顶 / 取消置顶」，和「设置」里「账号顺序与置顶」（排序模式）每行的「置顶 / 取消置顶」文字按钮。行尾不放图钉按钮（列表、卡片、排序模式、只读面板都一样）：放在 `>_` 和「…」旁边，用户觉得突兀。置顶的行在名字前显示一个小的灰色描边图钉（12px，不是按钮，读屏读「已置顶」）。满 3 个时菜单项变灰并写「每组最多置顶 3 个」，排序模式里点按钮提示同一句话。
- 「恢复默认顺序」不清除置顶，按钮旁写「置顶会保留」。

**面板里怎么排**（2026-10-17 改：从常驻把手改为排序模式）：
- 平时不显示拖拽把手。两个入口进入排序模式：顶栏「设置」里的「账号顺序与置顶」（右边写「默认」或「已调整」），和排序下拉框最后一项「调整顺序…」；在还没排过顺序时选「我的顺序」也会进入。进入后排序切到「我的顺序」，页面滚到横栏。（2026-10-17 补充：只放在排序下拉框里时，用户找不到。）
- 排序模式里，列表上方一条横栏：「拖动或用 ↑ ↓ 调整顺序，改动立即保存」，右边「恢复默认顺序」和「完成」。分组变紧凑：每行只有把手、图标、名字和短命令（同一登录一行写「2 个目录」）、上移和下移按钮、「置顶 / 取消置顶」文字按钮；额度、邮箱、最近使用都收起。卡片视图在排序模式里也显示成这种紧凑列表。
- 分组标题有把手，拖它移动整个 Family。有自己窗口的桌面应用（Grok Bot，id `grok-bot`）也是一个分组：它在 `display.families` 里占一个位置（默认排在各工具后面），组内窗口按 `display.accounts.grok-bot` 排（默认主窗口在前），排序模式里同样能拖、能上下移动，没有置顶。`sideby order --families` 和 `sideby order grok-bot <name>...` 也认这个 id，`sideby list` 按它列出窗口。账号只能在本 Family 里移动，拖到别的 Family 上不生效，松手时提示「只能在 Claude Code 里调整」。置顶的账号只在置顶区里移动（改 `pinned` 的先后），其余账号只在置顶区下面移动。
- 键盘：把手是按钮，聚焦后 `↑` / `↓` 移动一位，`Home` / `End` 到区内最前或最后；上移、下移按钮在到头时变灰。读屏软件读出「claude:003，第 2 个，共 4 个」。
- 有筛选或搜索时，看不到的账号保持它们之间原来的相对位置。
- 每次移动立即写入。点「完成」退出，toast「已保存顺序」带「撤销」，撤销回到进入排序模式时的顺序（置顶也恢复）。退出时如果没有任何手动顺序，排序回到进入前的那一种（进入前就是「我的顺序」时回到「按额度」）。按 Esc 也是「完成」，但菜单、弹出面板或对话框先处理掉的 Esc 不算。
- 不在排序模式时拖不了，也不会因为别的操作悄悄切到「我的顺序」。
- 只读面板没有「调整顺序…」，也没有置顶菜单项。
- 写入一个接一个进行；失败时回到配置最后一次确认保存的样子，并提示原因。

**接口**：`POST /api/display-order { display: { families?, accounts?, pinned? } | null }`，写接口（token、Origin、串行队列同 §3.8，只读面板 403）。`null` 删掉整个键；「恢复默认顺序」发只含 `pinned` 的对象，所以置顶保留。返回写入后的 `display`。

### 3.26 联网查额度与 Grok 额度（2026-10-17 补充，ADR-0025）

- **CLI 补充**：`sideby quota check <family> on|off [--json]` 通过 Runtime 保存该 Family 的联网额度开关；只支持有 `fetchQuota` 的 Family，不影响本地额度读取，CI 仍不联网。

Grok 订阅有每周的 credit 额度。sideby 从 Grok 自己的 CLI 问额度，不读 token，也不自己发请求。

**插件约定**：`FamilyDef.fetchQuota?: { everyMinutes, summary, fetch(account, ctx) }`，和本地的 `readQuota` 并列。

- 由 sideby 决定什么时候调用 `fetch`：每个账号上一次的结果存在状态目录 `quota/<family>/<name>.fetched.json`，只有百分比、重置时间、套餐名和记录时间，原子写、权限 600。结果比 `everyMinutes` 旧，或者用户要求刷新，才再问一次。
- `fetch` 收到的 `ctx` 带 `signal`，20 秒后中止。超时或出错时保留上一份结果，同时记下这次的原因：没有上一份就显示原因；有上一份就照常显示，并标出数据时间。
- 同一时间每个账号最多一个 `fetch`；同一进程里，多个读取方共用同一个进行中的请求。
- 显示的是 `readQuota` 和 `fetch` 结果里较新的一份（按 `observedAt`）。
- 有 `fetchQuota` 的 Family 也算有额度来源（`next` 不再报 `no-quota-source`，`families` 输出 `quota: true`）。
- 不调用 `fetch` 的地方：`statusline-tap`、`handoff-hook`（只读存下的结果）、API 账号、`loginState` 为 `logged-out` 的账号。
- 关闭：config `quota.check.<family>` 为 `false`，或在 CI 里（`CI`、`CONTINUOUS_INTEGRATION`、`BUILD_NUMBER`）。关闭后不再调用 `fetch`，本地的 `readQuota` 照常读；两边都没有数据时显示「额度查询已关闭」，原因为 `not-enabled`。
- 谁会触发：
  - CLI（`list`、`quota`、`next`、Auto Handoff 选号）：结果过期就并行去问，等它回来（最多 20 秒）。
  - `sideby quota --refresh [acct|family]`：不管新旧都重新问。
  - 面板：读 `/api/state` 时，过期的账号在后台去问，这次先返回旧数据，下一次自动刷新（20 秒）就拿到新的。面板开着时，每个账号大约每 15 分钟问一次。顶栏「刷新」按钮调用 `POST /api/quota/refresh`（写接口，只读面板 403），不管新旧都重新问，等回来后再刷新页面。

**Grok 的 `fetch`**（`families/grok/quota.ts`，`everyMinutes: 15`）：

- 用和 Launch 一样的环境启动 `grok agent --no-leader stdio`：设该账号的 `GROK_HOME`（主账号不设），清掉 Hijack Variables，加 `GROK_DISABLE_AUTOUPDATER=1`，工作目录是系统临时目录。
- 发一行 JSON-RPC 请求 `{"jsonrpc":"2.0","id":1,"method":"_x.ai/billing","params":{}}`。不发 `initialize`，也不建会话。
- 读到 `id` 为 1 的应答后关闭 stdin；进程 10 秒内不退出就结束它。超时、提前退出、找不到 `grok` 都按失败处理。
- 换算方法：
  - 已用百分比取 `result.config.creditUsagePercent`（也接受顶层的同名字段）。
  - 重置时间取 `config.currentPeriod.end`，没有时取 `billingPeriodEnd`。
  - 窗口长度按 `currentPeriod.start` 到 `end` 计算，取整到分钟。每周（`USAGE_PERIOD_TYPE_WEEKLY`）是 `7d`；其他长度按天数写成 `<n>d`。
  - 没有百分比但 `currentPeriod` 是每周时，按 0%；有 `used.val` 和 `monthlyLimit.val` 时，按两者之比算。
  - 套餐名取 `subscription_tier`（或 `subscriptionTier`），例如 `SuperGrok Heavy`。
- 失败原因写清下一步：
  - `-32601`：这个 Grok 版本不会报额度，先更新 Grok。
  - 要求登录：运行 `sideby login grok:<name>`。
  - 用 API key 登录：没有订阅额度。
  - 超时、读不懂应答：写明原因，下次再试。
- 错误信息里只有错误码和 sideby 自己的说明，不带应答原文。

**Grok 的 `readQuota`**（本地，`families/grok/quota-log.ts`，叶子模块）：

- 读 `<账号目录>/logs/unified.jsonl` 里最新一条 `msg` 恰好等于 `billing: fetched credits config` 的行，取 `ctx.config` 里的额度字段和 `ctx.subscriptionTier`，`observedAt` 是这一行的 `ts`，换算同上。
- 从文件末尾往前读，一块 64KB：CLI 和面板最多读 8MB（Grok 自己在 5MB 时截掉一半），`handoff-hook` 最多读 512KB。
- 这个文件的其他行带用户 id 和 token 尾段：先按 `msg` 字符串整行筛，再解析；只保留上面这些字段，其余内容不进入输出、错误、日志或缓存，测试会断言。

**Grok 换号**：Grok 的 `handoff.starts` 改为 `['quota', 'limit']`。`handoff-hook` 的 Grok 读取器按 `GROK_HOME` 认出账号，取存下的 `fetch` 结果和日志末尾里较新的一份算 Quota Pressure，于是到 `prepareAt`、`threshold` 就会预备、交接；额度用完那一轮失败的兜底照旧。`sideby next grok` 按额度挑账号。

**带名字的窗口**：`QuotaWindow.name?` 是这一档额度只管哪一组模型，例如 Cursor 的「Other models」。

- 有名字的窗口不计入 Quota Pressure：用完它还能换别的模型。所以 `next`、Auto Handoff 和面板的提醒都不看它；面板照常显示它的用量条和提醒色。
- 面板的额度列按「名字，没有名字就用 `label`」分列；CLI 写成 `Other models 51%`。
- 内置家族目前都不设名字。

**面板**：

- 「设置」弹层新增「额度查询」一项，每个有 `fetchQuota` 的 Family 一个开关，旁边写上 `summary`（Grok：「让 Grok 每 15 分钟查一次各账号的额度」）。关掉时写 config `quota.check.<family>: false`，打开时删掉这个键。sideby 会写的 config 键见 §3.10。
- 账号的额度悬停说明写「Grok 自己查询，X 分钟前」或「读自 Grok 的本地记录，X 分钟前」。查询失败时，额度格旁边显示原因。

**不做**：读 `auth.json` 的 token、自己请求 `cli-chat-proxy.grok.com`、开会话、发 `initialize`、改 Grok 的配置。

### 3.28 让 AI 帮我（AI Task，2026-10-17 补充，ADR-0027）

目标：面板上能做、或者用户卡住的任何事，点一下就交给用户自己的 AI 去做。sideby 打开用户的终端，用用户自己的一个账号启动宿主，带上写好的提示词；AI 按 sideby skill 干活。术语见 `CONTEXT.md` 的「Asking AI」：AI Task、Task Prompt、Preferred Terminal。

**分期**：

- 第一期：本节全部内容，终端只做 macOS（Terminal、iTerm2、Ghostty、Orca、WezTerm、kitty、Alacritty）。
- 紧跟：Linux（`xdg-terminal-exec`，再依次试 gnome-terminal、konsole、xfce4-terminal、kitty、alacritty、ghostty）和 Windows（`wt`，没有就 `cmd`）。
- 第二期：插件给面板加内容的声明式扩展点（插件返回数据，面板按固定样式渲染，不注入 HTML 或脚本），另写 ADR。
- 暂不支持：Warp（URL 只能开目录，不能跑命令）、VS Code、Cursor（不装扩展就不能在内置终端跑命令）。

#### 入口

| 入口 | 位置 | 任务 |
|---|---|---|
| 通用输入框 | 顶栏「让 AI 帮我」按钮，以及「设置」里原「让 AI 帮你操作」一行 | 用户写什么都行 |
| 体检 | 不能自动修复的发现旁边，替换原「复制给 AI 修复」 | `fix`：带上这些发现 |
| 额度 | 额度格显示没有数据或出错时 | `quota`：带上账号和原因 |
| 新建账号 | 新建对话框第一屏底部「让 AI 帮我配」 | `account`：订阅账号，或「我有一个 API 地址或文档链接」 |
| 工具没列出 | 新建对话框的工具选择最后一项「其他工具……」 | `host`：加一个 sideby 还不支持的宿主 |
| 插件 | 「设置」里「让 AI 写插件」 | `plugin`：写插件或 hook |

确定性操作（全部修复、开启额度、调优「使用」、自动交接开关等）保留原来的按钮，不经过 AI。原「让 AI 帮你操作」说明面板里的示例句子改成点击后直接填进通用输入框。

#### 用哪个账号

- 默认按 `sideby next` 的排法，从所有家族里挑：已登录的订阅账号，Quota Pressure 最低的那个；没有额度数据时挑主账号。API 账号不参与默认挑选，但可以手选。
- 打开前的确认框写明「在 Orca 中打开，并在那里启动 claude:work」，主按钮「在 Orca 中打开」，账号和终端都能改。手选过的账号（API 账号也算）存进 config `ask.account`，手选过的终端存进 `terminal.preferred`（同 `sideby terminal --set`），下次默认用它；这个账号不存在或已登出时回到默认挑法。
- 没有可用的账号（都没登录、都用完、一个账号也没有）：按钮不变灰，确认框改成「复制提示词」，提示用户贴给任何 AI；一个账号也没登录时先引导「登录主账号」。

#### Task Prompt

- 用面板当前语言，短：要做的事、上下文、规则、结尾的贡献邀请。「怎么做」写在 skill 的 `references/ai-tasks.md`，提示词不重复。
- 上下文只放 sideby 已经能输出的事实：账号 ref、家族、发现的 code 和说明、额度原因、面板语言、sideby 版本。不放凭据值、身份信息以外的 Host 文件内容。
- 规则段固定三句：先用 `sideby` skill（没装就先问用户，同意后运行 `npx skills add Adonis0123/sideby -g`）；会改文件的命令先看预览，`--yes` 要用户同意；不要替用户登录，不要让用户把密钥发给你，密钥用 `sideby key`。
- 结尾一句：做好之后，问用户愿不愿意把这次的改进（新宿主、修好的问题、更好的提示）贡献给 sideby，同意后按仓库的 `CONTRIBUTING.md` 提 PR，提交前去掉用户自己的账号名、路径和邮箱。
- 用户在输入框写的话原样放进「要做的事」，但先检查：像密钥的串（`sk-`、`xai-` 等前缀的长串，或 32 个字符以上的无空格随机串）删掉，并在输入框下提示「密钥请用 sideby 的密钥输入，不要发给 AI」。
- 拼装在 `page-logic.ts` 的 `taskPrompt`，CLI 和面板共用，测试覆盖每种任务和密钥删除。

#### 每个入口的提示（2026-10-18 补充）

对话框按入口换标题、输入框提示语和示例；示例点一下填进输入框，用户可以改。从入口带进来的上下文（账号、发现、额度原因）照旧放进 Task Prompt，输入框可以不填。

| 任务 | 标题 | 提示语 | 示例 |
|---|---|---|---|
| `free` | 让 AI 帮我 | 你想让 AI 做什么？ | 现有的通用示例 |
| `account` | 让 AI 帮我配账号 | 比如：我有一个 DeepSeek 的 API key | 加一个 Claude 订阅账号；我有一个 API 地址或文档链接 |
| `fix` | 让 AI 修复 | 想补充什么？可以不填 | 帮我修好这些问题；先解释一下再修 |
| `quota` | 问 AI 为什么 | 想补充什么？可以不填 | 为什么看不到额度；帮我开启额度显示 |
| `host` | 让 AI 支持一个新工具 | 你想用哪个工具？ | 我想用 Gemini CLI；我想用 OpenCode |
| `plugin` | 让 AI 写插件 | 你想让插件做什么？ | 启动前自动切换代理；新建账号时复制我的配置 |
| `terminal` | 让 AI 帮我配终端 | 你用的是什么终端？ | 我用 Warp；我用的终端没被认出来 |

- 英文版同样一组，意思相同。提示语、示例和标题写在 i18n，按任务取；新任务没有自己的一组时用 `free` 的。
- **`terminal` 任务**（新增）：入口在「首选终端」对话框的自定义命令旁边（「不会写？让 AI 帮我配」），以及 `sideby ask --task terminal`。Task Prompt 让 AI：问清用户用的终端；只看这个终端的官方文档和 `--help`，找出「在指定目录新开窗口运行一条命令」的写法；写成带 `{cmd}`、`{cwd}` 的模板；用 `sideby terminal --custom '<模板>'` 保存（会改 config，先问用户）；让用户在面板点一次「让 AI 帮我」试一下。跑通后照例邀请把它做成内置终端提 PR（`src/core/terminal.ts` 的终端表加一行和测试）。

#### 附件（图片和视频，2026-10-17 补充）

用户卡住时常常只有一张截图。通用输入框和其他入口的对话框都能带附件。

- **怎么加**：在输入框里粘贴、把文件拖进对话框，或点「添加图片或视频」。缩略图显示在输入框下面，可以逐个删掉。
- **限制**：图片 png、jpeg、gif、webp，单个最大 20MB；视频 mp4、mov、webm，单个最大 200MB；一次最多 5 个。类型按文件开头的字节判断，不看扩展名和浏览器给的类型；不认识的类型拒绝，说明支持哪些。
- **暂存上限**：面板上传后、发出任务前，文件先放在暂存区，最多 20 个、共 400MB；超出时返回 507，提示先发出任务或删掉待发的文件。每次上传前清掉超过 1 天的暂存文件，没发出的不会一直留着。用户在对话框里删掉一个文件时，面板同时删掉它的暂存副本（`POST /api/ask/attach/remove`），配额马上空出来。
- **目录检查**：从状态目录往下的 `ai`、`ai/attachments`、暂存区和任务目录，每一级都必须是本人所有、别人不能写的真目录（不是链接），否则拒绝；清理只删 sideby 自己起名的文件和目录，删之前确认真实路径还在附件目录里。
- **存放**：`$XDG_STATE_HOME/sideby/ai/attachments/<task-id>/`（目录 700，文件 600），文件名由 sideby 起（`1.png`、`2.mp4`），不用原文件名。超过 7 天的附件目录在下一次写任务时清掉。附件不进任务文件，任务文件只记它们的路径。
- **交给 AI**：Task Prompt 多一段「Attached files」，每行一个绝对路径和类型；视频另加一句「需要看内容时用 ffmpeg 抽几帧再看」。家族可声明 `FamilyDef.imageArg`（Codex：`--image`），图片还会以 `--image=<path>` 逐个加在宿主参数里；其他家族靠提示词里的路径读图。
- **提醒**：对话框里有附件时写一句「图片会和你的话一起发给 AI，先确认里面没有密钥或密码」。密钥过滤只处理文字。
- **接口**：`POST /api/ask/attach`，请求体是文件本身（`Content-Type` 只作参考），单独的大小上限，写接口，token、Host、Origin 检查照旧；返回 `{ id, kind, bytes }`，`/api/ask` 带 `attachments: [id…]`。只读面板不能上传。
- **CLI**：`sideby ask "<text>" --attach <file>`，可写多次；文件被复制进附件目录，同样的类型和大小检查。`--print` 也列出附件路径。

#### 打开终端

- **选哪个终端**：config `terminal.preferred`（「设置」里的「首选终端」下拉框，只列本机装了的）。没设置时，看面板进程启动时的 `TERM_PROGRAM`（`Apple_Terminal`、`iTerm.app`、`ghostty`、`WezTerm`、`Orca`）和 `KITTY_WINDOW_ID`、`ALACRITTY_WINDOW_ID`；对不上就用 Terminal.app。后台面板（`ui --background`、桌面 app 打开）记下的是启动它的那个终端，可能为空。
- **终端里只跑一条固定命令**：`sideby ask --run <task-id> --state-dir <状态目录>`，写成当前 Node 和 sideby 入口文件的绝对路径，加上面板写任务的状态目录的绝对路径（三者都单引号转义；任一路径带反斜杠或控制字符就不放进命令，改为让用户粘贴），不靠新终端的 PATH 和环境变量：用 zsh、nvm 的用户在 `/bin/sh -l` 里找不到 `sideby` 和 `node`，新终端也可能没有面板用的 `XDG_STATE_HOME`。入口在 npx 缓存里时不打开，提示先 `npm i -g sideby`（同 `handoff setup`）。命令失败时窗口不立刻关闭，按回车再关。面板先把任务写进 `$XDG_STATE_HOME/sideby/ask/<task-id>.json`（原子写，权限 600，目录 700）：账号 ref、工作目录、Task Prompt，以及面板用的 HOME、配置目录和状态目录。`--run` 从 `--state-dir` 读任务（没给就用当前环境的状态目录）；这个目录和其中的 `ask` 必须是当前用户自己的真实目录、别人不能写（`ask` 是 700），否则拒绝。读出后删掉文件，用任务记下的 HOME、`XDG_CONFIG_HOME`、`XDG_STATE_HOME` 建 Runtime，然后像 `sideby run` 一样启动宿主，宿主看到的账号目录和配置与面板一致，Task Prompt 作为宿主的第一个位置参数（Claude Code、Codex、Grok Build 都会带着它开始交互会话）。任务文件 1 小时后失效，`--run` 拒绝并说明重新点一次。`task-id` 是 16 位随机十六进制。
- **启动方式**（全部经 `DesktopDeps.exec`，参数分开传；需要一整条命令字符串的地方只放上面那条固定命令，路径和 id 用单引号转义）：

| 终端 | 方式 |
|---|---|
| Terminal | `osascript`：已在运行就 `do script` 到新窗口，没在运行先 `launch` 再 `do script`，避免多出一个空窗口（照 cc-switch 的写法） |
| iTerm2 | `osascript`：`activate` 后一律 `create window with default profile`，往这个新窗口 `write text`。不用「当前窗口」：它可能是 iTerm2 的更新窗口或设置窗口（2026-10-18 实测 iTerm2 3.6.11 出现过），刚启动的 iTerm2 也可能没有窗口 |
| Ghostty | `open -na Ghostty --args --working-directory=<dir> -e /bin/sh -lc <cmd>`。不用 AppleScript：它要 Ghostty 1.3 以上，还会触发自动化授权；代价是每次多一个 Ghostty 进程 |
| Orca | `orca terminal create --worktree active --command <cmd> --title sideby --focus`。`path:<dir>` 只认 Orca 已加过的仓库，`sideby/ai/` 这类目录会报 `selector_not_found`（Orca 1.4.227，2026-10-17 实测），所以用 `active`，工作目录由 `ask --run` 自己切。`--command` 会被打进 Orca 的登录 shell，命令必须单引号转义 |
| WezTerm | `wezterm start --cwd <dir> -- <cmd>` |
| kitty | `kitty --single-instance --directory <dir> <cmd>` |
| Alacritty | `open -na Alacritty --args --working-directory <dir> -e <cmd>` |

- **工作目录**：`ask --run` 启动宿主前自己切到这个目录，不依赖终端的参数。配置类任务（`fix`、`quota`、`account`、通用输入框）用 `$XDG_STATE_HOME/sideby/ai/`（目录 700，不存在就建），AI 不会顺手读用户某个项目。`host`、`plugin` 也从这里开始，由 AI 在会话里问用户要把插件写在哪、要不要克隆 sideby 仓库（默认 `~/sideby`）。
- **打不开时**：终端不在列表里、`osascript` 被拒（macOS 的 Automation 权限）、命令退出码非 0：面板把 `sideby ask --run <task-id> --state-dir <状态目录>` 复制到剪贴板，提示「粘贴到你的终端回车」；Automation 被拒时再写一句去「系统设置 → 隐私与安全性 → 自动化」打开。「设置」里还有「自定义终端命令」：一个模板，`{cmd}` 和 `{cwd}` 由 sideby 按参数填入（不经过 shell）。
- **接口**：`POST /api/ask`（`{ task, text?, context?, account?, terminal? }`），返回 `{ opened, terminal, account, command }`；`POST /api/login`（`{ account }`）。两者都算写接口，走面板现有的 token、Host、Origin 检查；只读面板返回 403，前端改成复制命令。

#### 加 API 账号

- 不内置厂商、端点或模型名清单，事实只从厂商和宿主的官方文档、`--help` 来（ADR-0027）。skill 的「加 API 账号」一节写要找什么，以及常见错误：套餐端点和按量端点填混、key 放错变量（例如 `ANTHROPIC_AUTH_TOKEN` 写成 `ANTHROPIC_API_KEY` 会让 Claude Code 要求登录）、接口格式和地址对不上、拉模型列表被网站防火墙拦住却报成 key 无效、切回订阅后残留。
- AI 用 `sideby new <family> --next --api` 建账号，写 `proxy.env` 里除密钥外的变量。
- **`sideby key <acct> [--var <NAME>]`**：sideby 自己收密钥。在终端里不回显地读一行，写进该账号 `proxy.env` 的这个变量（默认用家族的密钥变量），其他行原样保留，原子写、权限 600。只用于 API 账号，以及 `secretFileMeansApi: false` 的家族（pi）。不打印、不返回值；`--json` 只回 `{ account, var, written }`。面板对应「填写密钥」对话框（`type=password`，`POST /api/key`，写接口）。
- **`sideby try <acct> [--yes]`**：让宿主自己发一次很短的非交互请求，确认账号能用。不加 `--yes` 先说明会花少量 token、运行哪条命令，退出码 10；这一步只算出命令，不运行 `launch.before` hook 和 account-script，也不读 Secret File。加 `--yes` 才准备一次 Launch（hook 只跑这一次），显示的命令就是实际运行的那条。sideby 只看退出码，以及宿主输出的前 2KB 交给用户和 AI 看（宿主自己不打印密钥；sideby 仍按 Secret File 里的值把输出中出现的值替换成 `***`）。家族通过 `FamilyDef.probe?: { args: string[] }` 声明这条命令（Claude Code `-p "Reply with OK"`、Codex `exec "Reply with OK"`、Grok Build `-p "Reply with OK"`（`--single`），pi `-p "Reply with OK"`；Claude Code 2.1.301、Codex 0.163.0、Grok Build 1.0.60、pi 1.3.0 的 `--help`，2026-10-17）；没有 `probe` 的家族报「这个工具不支持试一下」。这是公开插件契约的新增字段。

#### 加一个新宿主

- AI 先在本机写一个 Family Plugin，当天能用；跑通后再问要不要把它变成内置家族提 PR。
- **`sideby plugins new <id> [--json]`**：在第一个 `pluginDirs`（默认 `~/.config/sideby/plugins/`）下建 `<id>/`：`plugin.json`、`index.ts`（一个 `api.family(def)` 骨架，必填字段带 TODO 注释）、`index.test.ts`，目录 700、文件 600，能直接通过 loader 的信任检查。目录已存在时拒绝。
- **`sideby plugins check <id> [--json]`**：确定性校验，每条问题写明怎么修。查：FamilyDef 字段齐全、`selectVar` 存在、Shared Item 路径相对且不含 `..`、logo 合法、只 `import type` sideby；插件目录通过 loader 的信任检查（所有者、写权限）后，才在一个子进程里加载它，HOME 和 XDG 目录都指向临时的假 HOME，跑一遍发现账号、启动环境、doctor；子进程 20 秒不结束就整组结束，输出最多 64KB。信任检查不通过时只做静态检查，绝不加载。这只是让检查自己写的文件落在临时目录里，不是沙箱：插件仍是用户权限下运行的本地代码。再对插件目录跑 leak-check（真实 HOME 路径、邮箱、token 形状的串）。全部通过退出 0，有问题退出 1。CI 对每个内置家族跑同一套检查。
- AI 要查清并写明来源的事实：宿主二进制名、安装命令或链接、隔离配置目录的环境变量、主目录和账号目录的布局、Hijack Variables、登录命令、只看文件是否存在的登录状态规则、每个 Shared Item 和它的 Share Mode、是否拒绝链接、有没有本地额度或用量文件（没有就不写读取器）、logo 来源和许可证。证据写成「工具 X 版本，日期」。
- 提 PR 时按 AGENTS.md 的「Adding a family」，并遵守新增的 `CONTRIBUTING.md`：一个宿主一个 PR；写明测试用的宿主版本和日期；在自己机器上实测过；按「Write for every user」去掉个人信息。不要求先开 issue。仓库另加 issue 模板（「支持一个新工具」）和 PR 模板（上述清单）。

#### Portal 交来的任务（Task Spec，2026-10-18 补充，ADR-0030）

Portal 在它显示的每个页面都能发起 AI Task。别的 Tool 的 Task Prompt 由 Portal 按那个 Tool 的声明来写，sideby 只负责开始任务：挑账号、收附件、打开首选终端。sideby 自己的八种任务仍由 sideby 写提示词，逐字不变。术语见 `CONTEXT.md` 的 **Task Spec**。

- **`sideby ask --spec - [--print] --json`**：从 stdin 读一个 JSON 对象（Task Spec，最大 1MB，超过就停止读取并报错）。用户的文字只经过 stdin 和任务文件，不经过 shell。两种写法：
  - `{ specVersion: 1, prompt, cwd?, lang?, account?, terminal?, remember?, files? }`：别的 Tool 的任务。`prompt` 再过一次 `stripSecrets`（删过就 `removedSecrets: true`）；有 `files` 时照 `--attach` 复制进任务，在末尾追加附件段，写法与 sideby 自己的「Attached files / 附件」段相同（同一个 `attachedSection`），提示词里有 Markdown 标题（`## `）时附件段用同一级标题。`cwd` 必须是 HOME 里已存在的目录（按真实路径判断，链接到 HOME 外也算外面），宿主从这里开始；否则退出码 1，`code` 和 `reason` 都是 `bad-cwd`，不复制附件、不写任务。任务文件记下目录的真实路径（`cwdInHome: true`）。挑账号、探测终端要花时间，目录可能在这期间被换成指向 HOME 外的链接（本身或某一级上级目录），所以写任务文件前立刻再查一次：真实路径必须不变、仍在 HOME 里、仍是目录，否则同样报 `bad-cwd`，不写任务、不开终端。`ask --run` 切进这个目录后，按进程当前所在的真实位置再查一次，不对就拒绝、不启动宿主，提示目录在准备任务之后变了，检查后重新开始。不给 `cwd`（或为 `null`）时用 sideby 自己的任务目录 `ai/`，对应声明里的 `"cwd": "engine"`。
  - `{ specVersion: 1, native: { task, text?, context? }, lang?, account?, terminal?, remember?, files? }`：sideby 自己的任务，`task` 是八种之一，`context` 的字段和面板 `/api/ask` 一样（同一个校验）。走原来的 `startAiTask`，提示词与面板、`sideby ask --task` 逐字相同（快照测试 `src/core/fixtures/native-prompts.json`）。`native` 不带 `cwd`。
  - 其余字段：`lang` 为 `en` 或 `zh`（不给时按 locale）；`account`、`terminal` 是用户选的（同 `--account`、`--terminal`）；`remember: true` 把它们存成下次的默认（同面板手选）；`files` 最多 5 个绝对路径。不认识的字段、`prompt` 和 `native` 都给或都不给、JSON 不合法：退出码 1，`code` 为 `spec-invalid`。超过 1MB：`spec-too-large`。`specVersion` 不是 1 的数字：退出码 2，`code` 为 `spec-version`，提示 `sideby update`，Portal 据此提示升级 sideby。这些错误的 `--json` 是 `{ schemaVersion, error, code, reason }`，`reason` 与 `code` 相同。
  - 输出同 `sideby ask --json`（`startAiTask` 的结果）。`--print` 只返回 `{ schemaVersion, prompt, removedSecrets }`：不写任务、不复制附件（附件段列出原路径）、不开终端。
- **`sideby ask --choices --json`**：Portal 的对话框打开前要显示的选择。`{ schemaVersion, account, accounts, terminal, terminals, reason, detail }`：`account` 是现在会挑的账号（同 `pickTaskAccount`），挑不出时为 `null`，`reason` 是 `no-accounts` / `none-signed-in` / `all-full`，`detail` 是下一步；`accounts` 是 `{ ref, label, signedIn }`，已登录的订阅账号在前，再是 API 账号，最后是未登录的订阅账号，各按 ref 排，`label` 和面板下拉框一样（API 账号加「 · API」）；`terminals` 是本机装了的、sideby 支持的终端 `{ id, label }`，`terminal` 是任务会打开的那个（首选终端，没有就是猜的）。
- **面板的 `ask` 选项**：`createPanelHandler({ ask: { bridge: 'postMessage' } })`。给了这个选项、并且页面加载时确实在 iframe 里，面板脚本隐藏顶栏「让 AI 帮我」按钮（服务端返回的 HTML 不隐藏，单独打开的面板保留它）；每个 AI Task 入口（额度「问 AI 为什么」、体检「让 AI 修复」、配终端、新建账号、其他工具、写插件、自动接力、设置里的「让 AI 帮你操作」）不再打开面板自己的对话框，而是向 `window.parent` 发 `{ type: 'local-tools:ask', version: 1, preset: <任务>, native: { task, text, context }, text }`，`targetOrigin` 是面板自己的 `location.origin`。面板不在 iframe 里时照旧打开自己的对话框。不给选项时什么都不变。CSP（含 `frame-ancestors 'self'`）和 Host、Origin、token 检查一律不变。其他值在创建时抛 `TypeError`。
- **`ai-tasks.json`**：包根目录随包发布，供 Portal 读取。页面 `accounts`：`skill: "sideby"`、`skillInstall`（同规则里的安装命令）、`cwd: "engine"`（sideby 的任务目录跟着 `XDG_STATE_HOME` 走，写不成固定的 `~/…`，由 sideby 自己定）、`contribute`（仓库地址和 `CONTRIBUTING.md`），以及除 `free` 外每种任务一个 `native: true` 的预设，`title`、`placeholder`、`examples` 中英两套，照抄 `src/panel/i18n.ts`，测试保证两边一致。`free` 是 Portal 自己的全局按钮，不声明。

#### CLI

- **`sideby ask [<text>] [--task fix|quota|account|host|plugin] [--account <ref>] [--terminal <id>] [--print] [--json]`**：生成 Task Prompt、写任务文件、打开首选终端。`--print` 只打印提示词，不写文件、不开终端。`--json` 输出 `{ schemaVersion, task, account, terminal, opened, command }`；打不开终端时 `opened: false`，`command` 是要粘贴的命令。
- **`sideby ask --run <task-id> [--state-dir <dir>]`**：给终端用，见上。
- **`sideby ask --spec -`**、**`sideby ask --choices`**：给 Portal 用，见上一节。
- **`sideby terminal [--set <id>|--unset] [--json]`**：列出支持的终端、本机装了哪些、当前首选和猜测来源；`--set` 写 config `terminal.preferred`。
- `sideby key`、`sideby try`、`sideby plugins new|check` 见上。
- skill：`SKILL.md` 的路由表加「让 AI 做一件 sideby 的事」「加 API 账号」「加新工具」三行，指向新文件 `references/ai-tasks.md`（每种任务的步骤、加 API 账号的常见错误、加新宿主要查的事实、贡献清单）。`llms.txt` 补上这些命令。面板「让 AI 帮你操作」的示例句子加「帮我加一个 DeepSeek API 账号」「帮 sideby 支持一个新工具」。

#### 不做

- sideby 自己拿密钥调模型、拉模型列表或测端点（ADR-0001）。
- `sideby://` 一类的导入链接；URL 里带密钥会留在浏览器历史。
- 让 AI 自动 fork、提交或开 PR；都要用户先同意。
- 把用户写的文字、路径拼进 shell 或 AppleScript。
- 插件往面板注入 HTML 或脚本（ADR-0006 的 CSP 不放松）。

### 3.29 设置都能让 AI 改（2026-10-18 补充，ADR-0029）

对照 cc-switch 的设置（Claude、Grok Build、Cursor 里的 Codex 模型三方独立调研，2026-10-18），sideby 只借开机启动；代理、路由、云同步、供应商预设、改宿主登录状态都不做。目标是面板上的每一项设置，用户的 AI 也能用命令改。

**开机启动**（ADR-0029）：

- `sideby autostart [on|off] [--yes] [--json]`：不带参数报告状态（`off`、`on`、`stale`：记录的路径已不存在、`foreign`：同名文件不是 sideby 写的）。`on`、`off` 先列出要写或要删的文件和内容，退出码 10；加 `--yes` 才做。
- macOS：`~/Library/LaunchAgents/dev.sideby.panel.plist`，`RunAtLoad` 为 true，`KeepAlive` 为 false，`ProgramArguments` 是当前 Node 和 sideby 入口的绝对路径，加 `ui --background --no-open`；写完 `launchctl bootstrap gui/<uid> <plist>`，关闭时 `launchctl bootout gui/<uid>/dev.sideby.panel` 再删文件。文件里有 sideby 的标记注释，只替换、删除带标记的文件；没有标记的同名文件报告 `foreign`，不动。
- 拒绝（说明下一步）：入口在 npx 缓存或临时目录里（提示 `npm i -g sideby`）、路径含控制字符、非 macOS（「这个系统暂不支持，Linux 和 Windows 稍后」）。
- `sideby update` 和 `pnpm local` 发现已开启时重写 plist，让它指向正在用的 sideby。
- `--json`：`{ schemaVersion, state, path, programArguments? , changed? }`。

**通用配置命令**：

- `sideby config get [<key>] [--json]`：读 config 里的值；`<key>` 是点号路径（`handoff.threshold`、`panel.theme`）。没有 key 时列出所有能改的键、当前值和一句说明。
- `sideby config set <key> <value> [--yes] [--json]`、`sideby config unset <key> [--yes]`：值按 JSON 解析，解析不了就当字符串；改动后的整份 config 必须通过 `schemas/config.json`。先显示改动前后，退出码 10，加 `--yes` 才写；写法和其他会写 config 的命令一样（保留其他键和顺序，原子写，读写之间文件变了就拒绝）。`plugins.<name>` 下插件自己的配置不能用它改（插件配置可能含密钥）；`accounts.<ref>.args` 只接受模型和 effort 参数，同 `sideby model`。
- 专门命令（`handoff`、`quota check`、`terminal`、`model`、`order`）照旧保留，给新手和 skill 用；`config` 是兜底，保证每个键都有命令。

**主题和语言进 config**：新增 `panel.theme`（`system`、`light`、`dark`）和 `panel.language`（`auto`、`en`、`zh`）。面板读 config，设置里改了就写 config（以前只存在浏览器里）；CLI 用 `sideby config set panel.theme dark` 改，面板下次刷新就生效。浏览器里已有的选择在第一次打开新版本时写进 config 一次。

**设置菜单分组**（从上到下，组间分隔线）：

1. 外观：主题、语言（一键改）。
2. 启动：登录后在后台启动 sideby（开关，旁边小字「不打开窗口，打开面板时就是最新状态」；打开时先显示要写的文件，确认后生效）、首选终端。
3. 账号与额度：账号顺序与置顶、各工具额度开关、远程控制、自动接力。
4. 让 AI 帮我：通用说明、让 AI 写插件。

菜单超过一屏时，底部「更多设置…」打开整页设置，同样的分组。

**自动接力的 AI 任务**：任务种类 `handoff`。入口在「自动接力」设置里的「让 AI 帮我调」，上下文带 `sideby handoff status --json` 的事实（是否开启、阈值、顺序、各账号额度来源）。Task Prompt 让 AI 根据用户的账号推荐阈值和顺序，只用 `sideby handoff enable …` 或 `sideby config set handoff.*`，先预览、经用户同意再加 `--yes`。

## 4 从自制脚本迁移

已经用自制脚本管理多账号的用户，按下表迁移：

| 自制脚本里的做法 | sideby 里的对应 |
|---|---|
| 一个账号一个短命令（`cc004`） | config 的 `aliases`，由 `sideby shell-init` 生成 |
| 启动前先拉起本地网关的脚本 | 开启 `account-script`，脚本改名为 `<账号目录>/sideby-before-launch` |
| 自定义的体检或提醒 | 写成本地插件（`doctor.check`、`account.created`） |
| 定时跑的体检 | 定时任务改为调用 `sideby doctor --fix` |
| 额外共享的个人文件 | config 的 `extraSharedItems` |

建议先让新旧两套并存，确认行为一致后再删旧脚本。

## 5 验收

分两层：

- **确定性层**：`pnpm check` 全部通过。用假 HOME 加假宿主 bin 跑完下面 1–12 条。
- **真实层**：在维护者本机用真实宿主做补充验证。对真实 HOME **只读**，只跑 `list`、`doctor`（不加 `--fix`）、`quota`。

1. 只有 `~/.claude` 时运行 `sideby`：列出 `claude:main`，并提示怎么新建账号。
2. `new claude work` 之后，`run claude:work`：宿主拿到的 `CLAUDE_CONFIG_DIR` 指向新目录，劫持变量已被清除。同时 `run claude:main` 时，宿主拿到的环境里没有选择变量。两个账号用真实订阅同时登录，属于人工补充项。
3. `new claude deepseek --api`：生成权限 600 的 `proxy.env` 模板。填好后，宿主拿到注入的变量；父进程环境不变。权限改成 644 后拒绝启动，并给出修法。语法错误时报出行号。
4. Grok 的 `hooks` 是 symlink：doctor 报 fail，`--fix` 后变成真目录，内容和主目录一致。
5. `link` 位置上是真文件：`--fix` 不替换它，只给出处理命令。§3.3 的每个「绝不做」都有测试。
6. `json-key`：新增 server 能同步过去；会删除已有 server 时，不加 `--force` 拒绝；`.claude.json` 是 symlink 时，加 `--force` 也拒绝。
7. statusline：setup 之后用一段样例 stdin 跑 tap，缓存写入、原命令输出原样透传。用户改过文件后 teardown 拒绝；没改过时 teardown 恢复后，文件和原来逐字节一致。
8. Codex 额度：多个文件、乱序、截断、坏行的 fixture 都取到正确的最新值。维护者本机真实读取的结果，和 rollout 里最新一条一致。
9. 面板：空数据、单卡出错、慢加载、正常四种状态都截图存档；一键修复和新建账号走完真实流程。
10. 面板安全：错误的 Host、缺少 Origin、跨源 Origin、缺少或错误的 token、超大请求体，全部被拒绝。
11. 启动：子进程以 3 退出时 sideby 也返回 3；子进程被 SIGTERM 终止时返回 143；`launch.before` 插件抛错时宿主不启动，错误里有插件名；插件目录可被他人写时拒绝加载。
12. 首日错误路径：宿主未安装、端口被占、插件加载失败、账号名有歧义，每种都给出可执行的下一步。
13. Handoff（§3.13）：`next claude` 选中压力最低的订阅账号并启动它，宿主拿到的环境与 `run` 该账号相同；已重置的窗口按 0% 算；`full`、`logged-out` 不被选；API 账号只在 `--include-api` 时被选；全满时不启动并写出最早恢复时间；`next grok` 报 `no-quota-source` 并列出账号；`--dry-run`、`--json` 不启动宿主。面板在推荐账号上显示「下一个」。
14. 契约：`quota setup claude` 不加 `--yes`、有变更待确认时退出 10；带 `--json` 的命令出错时 stdout 是带 `code` 的错误 JSON。
15. skill：`metadata.version` 与 `package.json` 一致；已装的旧版本 skill 让 `doctor` 给出 `skill.outdated` warn，退出码仍为 0。
16. 上下文调优（§3.18）：应用与撤销（假 HOME）：计划里列出文件、改前改后值和共用账号；确认前不写；写后只有 `autoCompactWindow` 变了、其他键和值原样、软链未被改动；读到之后文件被改过就放弃；撤销只在键仍等于写入值时生效；错误和状态记录里没有 `settings.json` 的其他内容；

## 6 风险

| 风险 | 应对 |
|---|---|
| 宿主改目录布局或沙箱规则 | 家族知识集中在各自插件里；修复只做 §3.3 列出的动作；README 写明经过测试的版本 |
| Codex rollout 格式变化 | 解析失败显示「格式无法识别」；fixture 取自真实样例 |
| statusline 每次刷新都多一次 Node 冷启动 | tap 用单独的最小入口；验收时实测耗时并写进 verification |

| 条款变化 | ADR-0001、ADR-0003 的「不做」写进 README FAQ |
| 同类项目（aimux、agenv） | README 首屏突出额度面板、Grok 和 pi 支持、doctor、插件 |
