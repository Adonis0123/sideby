# Host directories and per-entry invariants

These continue the **Invariants** in `AGENTS.md`: breaking any of them is a bug, even if tests pass. The rule that sideby writes none of its own files into a Host account directory, and its first two exceptions (`quota setup claude --yes`, `handoff setup grok --yes`), are in `AGENTS.md`; the later exceptions and the rules for each hook entry and reader are here.

- `network-hook` (spec §3.35) runs before every prompt and tool call in a session sideby started with Network Guard on. It imports only Node built-ins, `core/egress.ts`, `core/prompt-origin.ts`, `core/fs-safe.ts` and `core/paths.ts` (`src/network/hook.test.ts` walks its imports), and reads the target and cache folder from the session's environment and config `network` fresh on every run: off (or no allowed country) lets everything through, on uses the list config holds now, no config file means the defaults (off), as for every other config reader, and only when the file exists but cannot be read or is not JSON does it fall back to the list the session started with. In CI it lets everything through without a request. Unlike `handoff-hook` it blocks: exit 2 with the reason when the country is not allowed or cannot be told, including when the check itself fails. Before a Claude prompt it also runs as `Held` in the background (`asyncRewake`, ADR-0053's second amendment): a prompt Claude Code made itself (it starts with `<task-notification>`) is not sent again once blocked, so `Held` keeps it in memory, asks again after 15 s, 30 s, then every 60 s (one request each), and exits 2 with the message only after a new answer inside the list, or once the check is turned off; it ends when its parent is gone or after 4 hours 58 minutes, and never lets anything through by itself. The checking hook tells it the decision through `<state>/network/held/<hash of the prompt id>` (folder 700, file 600, `ok` or `blocked` only, removed when read or after an hour); the prompt's text and id are never written to disk or a log. Of its input the hook reads only `prompt` and `prompt_id`, waits at most 5 seconds for it (then lets go of the stream and decides as if given none), and `Held` waits up to 65 seconds for the decision, also when the check is off by then. A typed prompt is never held, and Codex gets no such entry. It is injected only into sessions sideby starts (Claude `--settings`, merged with Auto Handoff's into one file; Codex `-c hooks.*`), by absolute path to this Node and this sideby (the path sideby was started by, such as the global `bin/sideby` link, when it leads to this sideby, so an update or a Local Build switch reaches running sessions; else the entry's real path; `core/session-hooks.ts`), and nothing of it is written into a Host directory.
- `unattended-hook` (spec §3.37, ADR-0058, ADR-0089, ADR-0090) runs before the ask tool (Claude `AskUserQuestion`, Codex `request_user_input`, Antigravity CLI `ask_question`), at every `Stop` (Claude, Codex and Antigravity CLI) and, in Claude, on every `PermissionRequest` and `Elicitation`, in the background (`asyncRewake`) on every Claude `StopFailure` (ADR-0067) and, as `StopWait`, on every Claude `Stop` (ADR-0077), and in the background (`async`) on every Claude `UserPromptSubmit` (ADR-0075), in a session sideby started once config has an `unattended` section (for Claude and Codex), or in every Antigravity CLI session once `sideby unattended setup agy --yes` added `"sideby-unattended"` to `~/.gemini/config/hooks.json`. It imports only Node built-ins, `core/unattended-state.ts`, `core/unattended-pending.ts`, `core/unattended-retry.ts`, `core/unattended-attended.ts`, `core/unattended-wait.ts`, `core/prompt-origin.ts`, `core/fs-safe.ts`, `core/lock.ts` and `core/paths.ts` (`src/unattended/hook.test.ts` walks its imports), reads only config `unattended.schedule` and `unattended.answerWait`, `<state>/unattended/override.json` and `<state>/unattended/attended/`, plus one line of the session's transcript (below) and, for Answer Wait, the session record of its parent process (below), and writes only Pending Decisions under `<state>/unattended/pending/`, Turn Retry streaks under `<state>/unattended/retries/` and Attended Sessions under `<state>/unattended/attended/` (one file per session, named by a hash of its id, read and written back under a `.lock` of the same name), each level a real folder of the user that nobody else can write to (`ownedFolder` in `core/fs-safe.ts`, as for `<state>/messages`). On a passing `StopFailure` while on, it waits 1, 2, then 4 minutes and exits 2 with a note to continue (which wakes the idle session), at most three times in a row per session; it wakes nothing when by then the mode is off, its parent is gone, or a later failure or a finished turn took over (every `Stop`, also while off, and every failure it does not retry clear the streak), and keeps a `deferred` Pending Decision instead of a fourth retry. A used-up Quota is never retried. It refuses only while Unattended Mode is on: a question with exit 2 and the reason (for `agy`, exit 0 with `{"decision":"deny","reason":…}` on stdout), a permission request with exit 0 and a `deny` decision as JSON on stdout (Claude Code does not honor exit 2 there), a stop whose last message ends on a question (`endingQuestion`, patterns in `QUESTION_PATTERNS`) with exit 0 and `{"decision":"block","reason":…}` (for `agy`, `{"decision":"continue","reason":…}`) only while `stop_hook_active` is `false` (for `agy`, `continuationActive !== true` and `terminationReason` absent or `"NO_TOOL_CALL"`), so a turn is kept going at most once, and an MCP form with exit 0 and an `Elicitation` `decline`. For `agy` `PreToolUse` and `Stop`, it handles only Antigravity CLI payloads (`transcriptPath` or `artifactDirectoryPath` under `antigravity-cli` or `antigravity-cli-<name>`, or CLI env markers) and allows Desktop App / IDE payloads unchanged. For `agy` `Stop`, when the payload carries no `lastAssistantMessage`, it reads at most the tail 2 MiB of `transcriptPath` only when it is a regular file (never a symlink, opened with `O_NOFOLLOW | O_NONBLOCK` and checked against `dev`/`ino`) whose resolved path stays inside a real non-symlink `<real HOME>/.gemini/antigravity-cli/` or `<real HOME>/.gemini/antigravity-cli-<name>/` directory and ends in `.jsonl`, taking only the final `PLANNER_RESPONSE` string `content` (including an empty string, so an earlier question cannot survive an empty final reply; never keeping any other transcript text). Off, or on any problem before it has decided, it exits 0 with no output (for `agy` `Stop`, `{"decision":""}` on stdout), and once it has decided to refuse it refuses even when keeping the Pending Decision fails. It never guesses which commands Claude Code would prompt for. Answer Wait (ADR-0077): a Claude `PermissionRequest` that is not refused at once (an Attended Session, or the mode off), without `agent_id`, and a `StopWait` after a turn that ended on a question while the session is not unattended, watch the Host's own record `<CLAUDE_CONFIG_DIR or ~/.claude>/sessions/<ppid>.json` (opened without following a link, at most 64 KB; only `sessionId`, `status` and `statusUpdatedAt` are read, never written): only when it names the session and shows `waiting` (or `idle` for `StopWait`) within 2 seconds, then every 3 seconds, letting the call be (exit 0, no output) as soon as the record changes, cannot be read, the parent changed or the wait is `false`. Once it waited `unattended.answerWait` minutes (10 when not set) and the mode is on, it answers as the mode does: a `deny` decision (never `allow`) or, for `StopWait`, exit 2 with the note on stderr, and keeps a Pending Decision with `waited`. Its `timeout` is 12 hours. An Attended Session (a session someone typed into within the last 30 minutes, ADR-0075) is answered as when the mode is off, and no Turn Retry wakes it; the first `Stop` or ask-tool `PreToolUse` of a stretch while the mode is on prints one `systemMessage` for the user, which is the only other output. Only the `UserPromptSubmit` entry writes an Attended Session, never another event, a command or the Panel, and only when the prompt does not start with `<task-notification>`, holds no `sideby message <8 hex>`, has no `agent_id`, is not one of the launch's command-line prompts (`SIDEBY_LAUNCH_PROMPTS`, which `spawnHost` fills from the final arguments, or sets to `?` past 64 of them; a value that is not a list of marks counts no prompt), and the transcript line with its `promptId` says `origin.kind` `human`, has a `timestamp` and text that passes the same checks. For that it opens the `transcript_path` Claude Code gave only when it is the session's own (`<CLAUDE_CONFIG_DIR or ~/.claude>/projects/<folder>/<session id>.jsonl`, compared after resolving links; `ownTranscript`), and not a link, a regular file; reads from the start of the line that holds the point 256 KB before its end (a line up to 8 MB) then what is added, every 50 ms for at most 10 seconds and 32 MB, parses only lines holding the prompt id, and looks only at `type`, `promptId`, `origin.kind`, `timestamp` and the message's text, which it never keeps. The stretch counts from the line's time, never later than now. The record keeps the session id, family, `SIDEBY_ACCOUNT`, `cwd` and three times; never the prompt's text or id. That entry exits 0 with no output whatever happens. Of a refused permission request it keeps only allow-listed fields (`permissionText` in `src/unattended/hook.ts`: for Bash only the program name (`commandProgram`) and the model's own description, never an argument, the file path of Read/Write/Edit/MultiEdit/NotebookEdit, WebFetch's host, the tool name for anything else, MCP tools included), never the whole tool input. For Claude and Codex it is injected like `network-hook` (merged into the same Claude `--settings` file; Codex `-c hooks.PreToolUse` and `-c hooks.Stop`, one value for every hook of an event, and no permission or Elicitation hook), and nothing of it is written into a Host directory.
- `sideby unattended setup agy --yes` / `teardown agy` and the Panel's Antigravity CLI setup action (spec §3.37, ADR-0089, `core/unattended-agy.ts`) are the ninth exception to "sideby writes nothing into a Host directory": `agy --settings` does not load lifecycle hooks, so setup adds one top-level key (`"sideby-unattended"`, with grouped `PreToolUse` matching `ask_question` and flat `Stop`) to `~/.gemini/config/hooks.json` only after a preview the user confirms (`--yes`, exit 10 without it; Panel confirm), under `<state>/settings-locks/<hash>.lock`, verifying every parent folder (`.gemini`, `config`) is a real directory under `HOME`, creating a new file exclusively (`O_CREAT | O_EXCL | O_NOFOLLOW`, mode `600`) and rewriting an existing one via `writeIfUnchanged` (keeping every other own key including `"__proto__"`, indentation, trailing newline and existing file mode). It refuses symlinks (on the file or parent directories), non-object/invalid JSON, an existing `"sideby-unattended"` not written by sideby, or a `sideby` missing from `PATH` / from the npx cache (even when already installed, so `coverage.agy` stays truthful while `teardown` remains available). `teardown` removes `"sideby-unattended"` only while it still matches what sideby wrote, re-verifying the file hash before unlinking when no other keys remain (never removing parent directories).
- `progress-hook` (spec §3.42, ADR-0076) runs in the background after every turn (`Stop`, `asyncRewake`, timeout 18000) and on every prompt (`UserPromptSubmit`, `async`, timeout 10) in a Claude session sideby started while config `progress.every` is set. It imports only Node built-ins, `core/progress-state.ts`, `core/prompt-origin.ts`, `core/handoff-chain.ts`, `core/unattended-attended.ts`, `core/unattended-state.ts`, `core/fs-safe.ts`, `core/lock.ts` and `core/paths.ts` (`src/progress/hook.test.ts` walks its imports). It reads config `progress` fresh on every check (no file means off; only a file that cannot be read or is not JSON falls back to `SIDEBY_PROGRESS_EVERY`, the interval at launch), the Unattended Mode state through `sessionUnattended()`, and, while Auto Handoff runs, the run's `ready.json` and run state. Of its input it reads only `session_id`, `prompt_id`, `prompt`, `agent_id` and `background_tasks` (each task's `type` and `description`, never its `command`), waiting at most 5 seconds for it. It writes only `<state>/progress/sessions/<hash of the session id>.json` (a random watch id and times; every write and removal of both records holds the session's `.lock` beside them, and nothing is written when it stays held; an older prompt never replaces a newer one, and a `Stop` whose hook began earlier never replaces a later `Stop`'s watch) and `.prompt.json` (a time, a hash of the latest prompt id, and whether that prompt was a reminder's wake-up), each level a real folder of the user that nobody else can write to (`ownedFolder`), files 600 through the atomic writer, removed a day after their last change; never a command, a description, a reply or a prompt's text or id. At a `Stop` with background work it waits and, every interval, exits 2 with a reminder on stderr (which wakes the idle session), after checking again under the session's lock that no newer prompt was noted; it ends with exit 0 and no output when a later `Stop` or a new prompt took over, its parent changed, the setting is off, Auto Handoff is handing over (`ready.json` or `thresholdSentAt`), or after 4 hours 55 minutes, and it skips a reminder while the session is unattended. Any problem: no output, exit 0. It is injected like `network-hook` (merged into the same Claude `--settings` file); Codex gets none, and nothing of it is written into a Host directory.
- `handoff-hook` (spec §3.17) runs on every tool call while Auto Handoff is on. Its imports follow the same rule as `statusline-tap`, and `src/handoff/hook.test.ts` walks its import graph to keep it so. It does nothing without `SIDEBY_HANDOFF_RUN` or for another Family's hook, never fails the Host (any problem: no output, exit 0), and a `StopFailure` counts only for a used-up Quota. It never speaks to a subagent (`PostToolUse` with `agent_id`). Its Claude `IdleWatch` entry (ADR-0056) runs in the background after a `Stop` with background work in flight, reads only the tap cache and the chain directory, and exits 2 (waking the session) only when a window reaches its hand-over level under a `pick` plan; it ends at the next `Stop`, when the run ends or its parent is gone. At `Stop` it also reads the session's Progress Reminder record (`progressReminderTurn` in `core/progress-state.ts`, ADR-0076) to tell a turn a reminder started: that turn does not join the recent turns behind the adaptive level, at the level it gets IdleWatch's message, and with the threshold already marked it is held once for the Brief like an ordinary turn; a missing or late record means an ordinary turn. Measured cold start (median of 21): about 40 ms from `dist`.
- `statusline-tap` runs on every status line refresh. It may import only Node built-ins and leaf modules: `families/claude/quota-cache.ts`, `families/claude/layout.ts`, `core/account-name.ts`, `core/fs-safe.ts`, `core/paths.ts`. Never import `runtime.ts`, a Family index or `core/accounts.ts` from it. It must never change what the original command receives, prints or returns. Measured cold start (median of 21): about 40 ms from `dist`, 71–79 ms from source.
- `agy-statusline` and `agy-title` (spec §3.32 step 5, ADR-0088, ADR-0090) run on Antigravity CLI status-line and title refreshes for interactive `sideby run agy` sessions (under config `agyMod`, default on). They import only Node built-ins and leaf modules (`core/fs-safe.ts`, `core/paths.ts`, `types.ts`; `src/agy/statusline.test.ts` walks their imports). `withAgyMod` reads `<account.dir>/settings.json` read-only (only `statusLine` and `title`, respecting `enabled: false`, `padding`, `stack_with_default`, and `accountTitle`), writes a session-scoped mode-600 JSON file under `<state>/agy-launch/` (`ownedFolder`, 700; cleaned up on normal exit and pruned on stale launch) and passes `--settings <file>`, writing nothing into `~/.gemini/antigravity-cli/` or any Account directory, and skipping when `--settings`, headless flags or non-interactive subcommands are passed. The helpers resolve the owning `agy` process via ancestor PID walk (or launch binding), write only non-credential fields (`pid`, `procStart`, `conversationId`, optional `account`, `title`, `agentState`, `cwd`, `updatedAt`) atomically to `<state>/agy-live/<pid>.json` (folder 700, file 600, no symlinks; never `email`, `plan_tier` or tokens), and wrap any user command at most once under recursion guard `SIDEBY_AGY_HELPER_ACTIVE=1` and bounded timeout, passing the payload strictly on stdin. Dead-PID cleanup runs only in write paths (`agy-statusline` and launch/exit); `agyLiveSessions` stays strictly read-only and matches each process to its owning Account by `--app_data_dir`/`--gemini_dir` and `live.account`. Orca Chat delivery (`families/agy/deliver.ts`) writes an ephemeral mode-600 transport file under `<state>/agy-send/` (removed in `finally`) and runs `orca orchestration send` without a shell only for verified non-guessed local `agy acp` Chats after a pre-send drift check and a verified Orca sender identity check.
- `sideby tune` and the Panel's context tuning (spec §3.18, ADR-0011) analyse read-only. The only Host config value they read is the auto-compact size: `autoCompactWindow` in Claude's `settings.json` (top level, and the numbers under `modelSettings`, where `/autocompact` saves a size per model) and `model_auto_compact_token_limit` in Codex's `config.toml`. No other value of those files may reach an output, an error or a cache, and the tests assert it. Codex gets observations only until its default threshold has a first-hand source.
- Auto Handoff's wait rule (ADR-0018) reads only `autoContinueAtUsageLimit` of Claude's `settings.json`, to tell whether a session continues by itself at the reset; nothing else of the file reaches an output.
- The model and effort shown per Account (spec §3.19, ADR-0014) read only `model`, `effortLevel` and `modelSettings.<model>.effortLevel` of Claude's `settings.json`, the top-level `model` and `model_reasoning_effort` of Codex's `config.toml`, and the `model` and `effort` of the newest session record. Changing them (`sideby model`, the Panel dialog) edits only the model and effort arguments in sideby's config `accounts.<ref>.args`, after a preview; it never writes a Host file.
- `sideby tune apply` / `undo` and the Panel's "Use" button (ADR-0012) are the third exception to "sideby writes nothing into a Host directory": they write only the top-level `autoCompactWindow` (100000 to 1000000, the range Claude Code accepts) of an Account's `settings.json`, only after a preview the user confirms, through `writeIfUnchanged`, keeping every other key; a symlinked file is written at its real target with the affected Accounts named, never replaced or retargeted. `undo` restores the old value only while the key still holds what was written.
- `sideby remote-control off` / `on` / `undo`, the Panel's "Turn all off" banner and its Remote Control switch (spec §3.22, ADR-0017) are the fourth exception: they write only the top-level `remoteControlAtStartup`, to `false` (`off`) where it is `true` or not set, or to `true` (`on`) where it is `false` or not set, of each Claude settings file, under the same rules as `tune apply` (preview first, `writeIfUnchanged`, every other key kept, links written at their real target and never created or retargeted). They never create a `settings.json`, never write `disableRemoteControl`, never touch `~/.claude.json`, and never turn it on unless the user asks; `undo` restores the old value only while the key still holds what sideby wrote.
- `sideby messages inbound accept` / `undo` (spec §3.32 step 2, ADR-0040) are the fifth exception: they write only the top-level `crossSessionInbound`, to `"accept"` where it is not set or `"hold"`, of each Claude settings file, under the same rules as `remote-control off` (preview first, `writeIfUnchanged`, every other key kept, links written at their real target and never created or retargeted, no `settings.json` created). They never change `"refuse"` or any other value: each is reported with its reason, and a run that changes nothing says so and exits 1. Undo records whether the key was there and its exact old value, and restores it only while the key still holds what sideby wrote. Doctor's `messages.inbound-held` warning reads only `crossSessionInbound` and `permissions.defaultMode` and is never fixed by `--fix`.
- `sideby advisor <fable|opus|sonnet>` / `off` / `undo` and the Panel's Advisor dialog (spec §3.41, ADR-0074) are the sixth exception: they write the top-level `advisorModel` of each Claude Subscription Account's settings file, to the chosen alias, or remove the key for `off`, under the same rules as `remote-control off` (preview first, `writeIfUnchanged`, every other key kept, links written at their real target and never created or retargeted, no `settings.json` created, a blocked file skipped). They also read whether `env.CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS` is true by Claude Code's reading (`1`, `true`, `yes`, `on`, any case, trimmed; reported as `betasOff` and `betasValue`), and only with a confirmed model choice (never `off`) remove that one entry, listed in the same preview with the note that it turns Claude Code's other experimental features back on, in the same single write as `advisorModel`; a false-like value is not touched, every other `env` entry is kept, and an `env` emptied by the removal stays `{}`. An `env` that is not a JSON object makes the file `blocked`. They never read another key or `env` entry of the file into an output, an error or the undo record, never write any other key or `env` entry, never override the variable in the shell environment, and never touch an API Account's settings: a file used only by API Accounts is never listed or offered a removal. When a file that sets the variable is also used by API Accounts, the same confirmed change turns config `claude.apiBetasOff` on, written before the settings file (and turned back if no file the API Accounts use lost the variable after all); `undo` turns it back to its earlier value only while it still holds `true` and every file it was turned on for got the variable back. The Advisor writes through `writeSettingsKey` / `writeKeyRecord` of `core/claude-settings-file.ts`, not the shared `settingsKey`. Undo records whether `advisorModel` was there, its old value, its position among top-level keys when `off` removed it, what sideby wrote, and for a removed env entry its old value and position in `env`; it puts each back at its old place, `advisorModel` only while it still holds what sideby wrote (or is still absent after `off`), the env entry only while it is still absent. Unlocking is not a write: while config `advisor.unlock` is on, every Launch sideby prepares for a Claude Subscription Account (not `login`) gets `CLAUDE_CODE_ENABLE_EXPERIMENTAL_ADVISOR_TOOL=1`, set before Plugins' `launch.before`, and never when the environment already sets `CLAUDE_CODE_DISABLE_ADVISOR_TOOL`, `CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS` or the variable itself. Neither is a write: while config `claude.apiBetasOff` is on, every Launch sideby prepares for a Claude API Account (never a Subscription Account or another Family) gets `CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS=1`, set before the Account's `proxy.env` is read, so a value there wins, and never when the environment already sets it.
- Carried trust (spec §3.43, ADR-0078, `core/claude-trust.ts`) is the seventh exception. Only while config `claude.carryTrust` is on, and only for an interactive Claude Launch `rt.prepareLaunch` prepares (`command === 'run'`, no `-p` or `--print` in the final arguments; never `login`), after `sessionReady` and every `launch.before` let it through and before the Host starts. When the target does not trust the launch folder F (`process.cwd()`) and another Claude Account sideby knows does, it copies that Account's matching key into the target's `.claude.json` (`claudeJsonOf`: `~/.claude.json` for the Main Account). "Trusts F", from files only and never by running `git` in F: walking up from F's real path, the first `.git` decides. A `.git` folder makes its folder the root M; a `.git` file counts only as a linked worktree whose `gitdir` is `<common>/worktrees/<name>`, whose `<dir>/gitdir` points back at it (real paths), whose `commondir` or layout leads to `<common>`, and whose `<common>` is the `.git` folder of the checkout M above it. Anything else is unclear and nothing is written. In a checkout only a key equal to M counts, never a parent's; outside any checkout a key equal to F or a parent counts. Keys equal to HOME or a filesystem root never count. Keys compare as written against real paths, the narrowest match first, then the first Account. Of any `.claude.json` it reads only `projects.*.hasTrustDialogAccepted`, opened with `O_NOFOLLOW`, at most 64 MB; the target first, the others only when it lacks trust; errors name the path only and never quote the file. The write refuses a link, a missing file (never created), a file that is not a JSON object, a `projects` or entry that is not an object, and a field that is neither absent nor `false`. It sets only that field (a new entry is `{ "hasTrustDialogAccepted": true }`), keeps every other key, their order, the indentation and the final newline, and writes under `<state>/settings-locks/<hash>.lock` (2 s wait) through `writeIfUnchanged` (mode 600), skipping when the hash changed. A failed or skipped carry never stops the Launch and prints one stderr line saying why; every carry prints one line at once. Each carry is recorded after the write in `<state>/trust/carried/<hash of file and key>.json` (`ownedFolder`, folder 700, file 600): Account ref, file, key, `before` (`no-entry`, `no-field`, `false`), time, source ref; never another value of the file. `sideby trust undo` (exit 10 without `--yes`) reverts a record only while the field still holds `true`: `false` back to `false`; an absent field removed, with the entry when sideby made it and it holds nothing else; it keeps every field Claude Code added. Under the lock a carry reads the target again, does not carry (and keeps every record) when it cannot read it, and does nothing (keeping its record) when it is trusted by then, and does not carry when sideby's record folder cannot be checked. A carry first removes an earlier record of the same file and folder (it is stale, or the carry would not run) and does not carry when it cannot; carry and undo read and write only the path resolved under the lock (every folder above resolved, the file name itself not, so a linked file is still refused). A record also keeps the file's real path when written; an undo leaves the file alone (`blocked`) once that path leads elsewhere, re-reads the record under the file's lock (the carry writes it under the same lock), sets it aside as `<id>.json.undoing` before changing the field (no change when that fails), and never undoes with a record left set aside: it is listed as `blocked`. The Panel's confirmation names the records it showed (`items: [{ id, at }]`) and nothing else is taken back. A changed field or a gone file drops the record untouched; a blocked or busy file keeps it. Turning the setting off undoes nothing. `sideby trust` reads no `.claude.json` while the setting is off, and while on gives only booleans for the asked folder, never another `projects` key. The Panel's polled state reads only the records.
- Shared Project Memory (spec §3.44, ADR-0081, `core/claude-memory.ts`) is the eighth exception. Only while config `claude.shareMemory` is on. At Launch, only for an interactive Claude Launch `rt.prepareLaunch` prepares (`command === 'run'`, no `-p`/`--print` in the final arguments, never `login`) of an Account that is not the Main Account, and only when the arguments hold no `--settings` yet (otherwise one notice line and nothing passed): the Project key comes from `trustRoot` (files only, never `git`; `unclear` passes nothing and says so), its folder name from `claudeProjectDirName` (Claude Code 2.1.328's rule, a hash past 200 characters), and `<real Main dir>/projects/<name>/memory` goes as `autoMemoryDirectory` into sideby's own session settings file (`sessionHookArgs`, named with a hash of that path, carried into Auto Handoff's merged file). Nothing is passed when `projects`, the Project folder or `memory` under the Main Account is a link or not a folder, or the Main Account's folder is missing. Nothing is written into a Host directory at Launch. Doctor (only while on, and only when the run includes Claude) gives each non-main Claude Account with files in `projects/*/memory` one `warn` `memory.unfolded` (the check reads Live Sessions too: Projects a session of that Account works in are named with its Session Label, and the finding is not fixable when every Project waits or sideby cannot tell; its `params` carry names and counts for the Panel's translated sentence), whose Fix (reading Live Sessions again, never the check's list): reads Live Sessions (`sessions/<pid>.json` and `ps`) first and moves nothing of that Account when it cannot tell (a running process's record it cannot read, such as one being rewritten, one without its session id, working folder or start time, or a process list it cannot read; only a gone process or a reused pid counts as ended), and skips a Project a Live Session's working folder, real path or Project names; refuses (and reports) a link anywhere on the way in the Account (`projects`, the Project folder, `memory`, a file inside) or in the Main Account, and a memory folder holding anything but plain files; - `sideby send` (spec §3.32 step 2, ADR-0040) keeps every Message in sideby's state folder before any delivery, in folders under `<state>/messages` it checks one at a time (a real folder of the user, not a link, not writable by others; never `.`, `..` or a name with a separator), copies each screenshot from the file it checked (opened without following a link, read up to the 20 MB limit, its type told again from the copied bytes), and once the Message is kept turns any failure into a paste, except a `codex queue` that started and timed out and a Claude write that got no flush callback, which are `unknown` (ADR-0065) because the Message may already be there; a Claude write that failed before anything was written for a reason that may pass (`PassingWriteError`) is tried again, three tries in all, 2 s and 4 s apart, every check redone, never once anything was written or the target's process is gone; and writes into a Host only through a Claude Code message socket: the path named by the session's own `sessions/<pid>.json` whose `sessionId` and `procStart` match the running process, in a `cc-socks` folder right inside a system temp folder, that folder a real folder of the current user others cannot enter, the socket a socket of the current user and not a link. - Using a Limit Reset (spec §3.40, ADR-0072, `core/limit-reset.ts`) writes nothing into a Host directory. Each operation is one file, `<state>/quota/limit-reset/<operation>.json` (folder 700, file 600, atomic writer), written before the request leaves; its locks are under `<state>/quota/limit-reset/locks/`. A record holds a version, the operation id, the Account refs of the Same Login, the idempotency key, the state and the attempt times: never a Login Key, an Identity, a credit id or a credential. It also holds a salted digest of the login's comparison key, usable only to tell that this operation's login is unchanged; never the Login Key or the Identity (`login: { salt, digest }`; `loginComparisonKey` in `core/same-login.ts` stays in the Runtime). `limitResetUse` compares it when a plan is confirmed and again under the lock right before the request: a plan whose login changed is out of date (`plan-outdated`), and an unresolved operation is not sent from another login and stays `pending` (`login-changed`). Only the Host's final answer to its own key ends a `pending` operation: Accounts leaving or joining its Same Login never do, and `unresolvedFor` finds it by the digest as well as by the Accounts it names, so no second key is made for a login that has one unresolved.
