# Host directories and per-entry invariants

These continue the **Invariants** in `AGENTS.md`: breaking any of them is a bug, even if tests pass. The rule that sideby writes none of its own files into a Host account directory, and its first two exceptions (`quota setup claude --yes`, `handoff setup grok --yes`), are in `AGENTS.md`; the later exceptions and the rules for each hook entry and reader are here.

- `network-hook` (spec §3.35) runs before every prompt and tool call in a session sideby started with Network Guard on. It imports only Node built-ins, `core/egress.ts`, `core/fs-safe.ts` and `core/paths.ts` (`src/network/hook.test.ts` walks its imports), and reads the target and cache folder from the session's environment and config `network` fresh on every run: off (or no allowed country) lets everything through, on uses the list config holds now, no config file means the defaults (off), as for every other config reader, and only when the file exists but cannot be read or is not JSON does it fall back to the list the session started with. In CI it lets everything through without a request. Unlike `handoff-hook` it blocks: exit 2 with the reason when the country is not allowed or cannot be told, including when the check itself fails. It is injected only into sessions sideby starts (Claude `--settings`, merged with Auto Handoff's into one file; Codex `-c hooks.*`), by absolute path to this Node and this sideby (the path sideby was started by, such as the global `bin/sideby` link, when it leads to this sideby, so an update or a Local Build switch reaches running sessions; else the entry's real path; `core/session-hooks.ts`), and nothing of it is written into a Host directory.
- `unattended-hook` (spec §3.37, ADR-0058) runs before the ask tool (Claude `AskUserQuestion`, Codex `request_user_input`), at every `Stop` (Claude and Codex) and, in Claude, on every `PermissionRequest` and `Elicitation`, and in the background (`asyncRewake`) on every Claude `StopFailure` (ADR-0067), in a session sideby started once config has an `unattended` section. It imports only Node built-ins, `core/unattended-state.ts`, `core/unattended-pending.ts`, `core/unattended-retry.ts`, `core/fs-safe.ts` and `core/paths.ts` (`src/unattended/hook.test.ts` walks its imports), reads only config `unattended.schedule` and `<state>/unattended/override.json`, and writes only Pending Decisions under `<state>/unattended/pending/` and Turn Retry streaks under `<state>/unattended/retries/` (one file per session, named by a hash of its id), each level a real folder of the user that nobody else can write to (`ownedFolder` in `core/fs-safe.ts`, as for `<state>/messages`). On a passing `StopFailure` while on, it waits 1, 2, then 4 minutes and exits 2 with a note to continue (which wakes the idle session), at most three times in a row per session; it wakes nothing when by then the mode is off, its parent is gone, or a later failure or a finished turn took over (every `Stop`, also while off, and every failure it does not retry clear the streak), and keeps a `deferred` Pending Decision instead of a fourth retry. A used-up Quota is never retried. It refuses only while Unattended Mode is on: a question with exit 2 and the reason, a permission request with exit 0 and a `deny` decision as JSON on stdout (Claude Code does not honor exit 2 there), a stop whose last message ends on a question (`endingQuestion`, patterns in `QUESTION_PATTERNS`) with exit 0 and `{"decision":"block","reason":…}` only while `stop_hook_active` is `false`, so a turn is kept going at most once, and an MCP form with exit 0 and an `Elicitation` `decline`. Off, or on any problem before it has decided, it exits 0 with no output (Claude Code then prompts as usual), and once it has decided to refuse it refuses even when keeping the Pending Decision fails. It never guesses which commands Claude Code would prompt for. Of a refused permission request it keeps only allow-listed fields (`permissionText` in `src/unattended/hook.ts`: for Bash only the program name (`commandProgram`) and the model's own description, never an argument, the file path of Read/Write/Edit/MultiEdit/NotebookEdit, WebFetch's host, the tool name for anything else, MCP tools included), never the whole tool input. It is injected like `network-hook` (merged into the same Claude `--settings` file; Codex `-c hooks.PreToolUse` and `-c hooks.Stop`, one value for every hook of an event, and no permission or Elicitation hook), and nothing of it is written into a Host directory.
- `handoff-hook` (spec §3.17) runs on every tool call while Auto Handoff is on. Its imports follow the same rule as `statusline-tap`, and `src/handoff/hook.test.ts` walks its import graph to keep it so. It does nothing without `SIDEBY_HANDOFF_RUN` or for another Family's hook, never fails the Host (any problem: no output, exit 0), and a `StopFailure` counts only for a used-up Quota. It never speaks to a subagent (`PostToolUse` with `agent_id`). Its Claude `IdleWatch` entry (ADR-0056) runs in the background after a `Stop` with background work in flight, reads only the tap cache and the chain directory, and exits 2 (waking the session) only when a window reaches its hand-over level under a `pick` plan; it ends at the next `Stop`, when the run ends or its parent is gone. Measured cold start (median of 21): about 40 ms from `dist`.
- `statusline-tap` runs on every status line refresh. It may import only Node built-ins and leaf modules: `families/claude/quota-cache.ts`, `families/claude/layout.ts`, `core/account-name.ts`, `core/fs-safe.ts`, `core/paths.ts`. Never import `runtime.ts`, a Family index or `core/accounts.ts` from it. It must never change what the original command receives, prints or returns. Measured cold start (median of 21): about 40 ms from `dist`, 71–79 ms from source.
- `sideby tune` and the Panel's context tuning (spec §3.18, ADR-0011) analyse read-only. The only Host config value they read is the auto-compact size: `autoCompactWindow` in Claude's `settings.json` (top level, and the numbers under `modelSettings`, where `/autocompact` saves a size per model) and `model_auto_compact_token_limit` in Codex's `config.toml`. No other value of those files may reach an output, an error or a cache, and the tests assert it. Codex gets observations only until its default threshold has a first-hand source.
- Auto Handoff's wait rule (ADR-0018) reads only `autoContinueAtUsageLimit` of Claude's `settings.json`, to tell whether a session continues by itself at the reset; nothing else of the file reaches an output.
- The model and effort shown per Account (spec §3.19, ADR-0014) read only `model`, `effortLevel` and `modelSettings.<model>.effortLevel` of Claude's `settings.json`, the top-level `model` and `model_reasoning_effort` of Codex's `config.toml`, and the `model` and `effort` of the newest session record. Changing them (`sideby model`, the Panel dialog) edits only the model and effort arguments in sideby's config `accounts.<ref>.args`, after a preview; it never writes a Host file.
- `sideby tune apply` / `undo` and the Panel's "Use" button (ADR-0012) are the third exception to "sideby writes nothing into a Host directory": they write only the top-level `autoCompactWindow` (100000 to 1000000, the range Claude Code accepts) of an Account's `settings.json`, only after a preview the user confirms, through `writeIfUnchanged`, keeping every other key; a symlinked file is written at its real target with the affected Accounts named, never replaced or retargeted. `undo` restores the old value only while the key still holds what was written.
- `sideby remote-control off` / `on` / `undo`, the Panel's "Turn all off" banner and its Remote Control switch (spec §3.22, ADR-0017) are the fourth exception: they write only the top-level `remoteControlAtStartup`, to `false` (`off`) where it is `true` or not set, or to `true` (`on`) where it is `false` or not set, of each Claude settings file, under the same rules as `tune apply` (preview first, `writeIfUnchanged`, every other key kept, links written at their real target and never created or retargeted). They never create a `settings.json`, never write `disableRemoteControl`, never touch `~/.claude.json`, and never turn it on unless the user asks; `undo` restores the old value only while the key still holds what sideby wrote.
- `sideby messages inbound accept` / `undo` (spec §3.32 step 2, ADR-0040) are the fifth exception: they write only the top-level `crossSessionInbound`, to `"accept"` where it is not set or `"hold"`, of each Claude settings file, under the same rules as `remote-control off` (preview first, `writeIfUnchanged`, every other key kept, links written at their real target and never created or retargeted, no `settings.json` created). They never change `"refuse"` or any other value: each is reported with its reason, and a run that changes nothing says so and exits 1. Undo records whether the key was there and its exact old value, and restores it only while the key still holds what sideby wrote. Doctor's `messages.inbound-held` warning reads only `crossSessionInbound` and `permissions.defaultMode` and is never fixed by `--fix`.
- `sideby send` (spec §3.32 step 2, ADR-0040) keeps every Message in sideby's state folder before any delivery, in folders under `<state>/messages` it checks one at a time (a real folder of the user, not a link, not writable by others; never `.`, `..` or a name with a separator), copies each screenshot from the file it checked (opened without following a link, read up to the 20 MB limit, its type told again from the copied bytes), and once the Message is kept turns any failure into a paste, except a `codex queue` that started and timed out and a Claude write that got no flush callback, which are `unknown` (ADR-0065) because the Message may already be there; a Claude write that failed before anything was written for a reason that may pass (`PassingWriteError`) is tried again, three tries in all, 2 s and 4 s apart, every check redone, never once anything was written or the target's process is gone; and writes into a Host only through a Claude Code message socket: the path named by the session's own `sessions/<pid>.json` whose `sessionId` and `procStart` match the running process, in a `cc-socks` folder right inside a system temp folder, that folder a real folder of the current user others cannot enter, the socket a socket of the current user and not a link. Right before connecting it reads the session record and the processes again; after connecting and before writing it checks that the socket and its folder are still the same files (device, inode, owner). It writes one line and closes the connection once it is flushed, sends no token, and never opens a `<pid>.<hash>.key` file or reads `CLAUDE_CODE_MESSAGING_TOKEN`. Of a transcript it reads only the last 256 KB, and of that only the lines with a Message id or a `permission-mode` record. It never resumes, copies or starts a session to deliver. To a Codex session (step 4) it only runs `codex queue --thread <session id> --message <paste line>` with that Account's launch environment, never the Message text on the command line, ends only that process on its 20 s timeout and reads none of its output.
- `sideby desktop` and the Panel's "Open desktop app" (spec §3.20, ADR-0015) start the unchanged app with `/usr/bin/open` only: never copy, modify or re-sign the `.app`, never end a process (an Account's running window is only brought to the front), and never write into a Host account directory. They write only the Account's App Data under `~/Library/Application Support/sideby/<family>/<name>/` (mode 700) and, in a new one, a link to the Main Account's `claude_desktop_config.json` where nothing is. Every program they run goes through `DesktopDeps.exec` in `core/desktop-app.ts`; tests replace it through `createRuntime`'s internal `desktop` option and never start a real app.
- The Run Link (spec §3.32 step 2b, ADR-0041, `core/run-link.ts`) reads an orchestrator's Session Index (`<state>/session-index.json`, at most 256 KB, not a link, `schemaVersion` 1) and makes no request. It shows or opens a Run Board only when the board is a regular `.html` file of the current user, not a link, right inside `<state>/boards` (itself a real folder of the user), and the entry's `url` is exactly `file://<board>` with an optional `#lane-<id>`. Opening runs `/usr/bin/open <board>` (xdg-open on Linux) through `DesktopDeps.exec`, with the path found again from the index for the Session id the page sends, never a path from the page, after checking the board and its folder once more (not links, owner, device and inode unchanged) right before the program starts; a read-only Panel refuses it.
- Session History (spec §3.33, ADR-0042, `core/history*.ts`, `families/<id>/history.ts`) reads the Hosts' session records read-only and never a credential file. The History Index (`<state>/history/index.sqlite`, folder 700, file 600) keeps only the fields §3.33 lists and the text of typed prompts and model replies: never tool calls or output, injected context, reasoning, or Codex's `session_meta` account ids and instructions; tests assert it. Config `history.index: false` stops it and deletes the file. Searching tool output reads the records at that moment and keeps nothing.
- `sideby browser` and the Panel's "Open in browser" (spec §3.24, ADR-0023) read nothing of a browser until config `browser.signIns` is true. Then they read only Chrome's `Local State` (each profile's folder, `name`, and `user_name` when it is an email: the Google account the profile uses in Chrome) and the Local Storage key names of claude.ai and chatgpt.com: a value is never decoded, kept or compared, and `Cookies`, `Login Data`, IndexedDB and the Keychain are never opened. Nothing of Chrome is written, locked or copied, and no request is made. The Host-side ids they compare (Claude's `oauthAccount.accountUuid`, Codex's `id_token` claim `chatgpt_user_id` or `user_id`, Grok's `auth.json` `user_id`, and the id a plugin Family's `website.match.signInId` returns) never reach an output, an error, a log or a cache; tests assert it. Opening runs `/usr/bin/open -na <Chrome.app> --args --profile-directory=<dir> <url>` through `DesktopDeps.exec`, only for a folder `Local State` lists.
- `sideby shell-init setup --yes` and the Panel's "Add the line" (ADR-0036) are the only writes to a shell rc file: they append one marked block (`eval "$(sideby shell-init <shell>)"`) to `~/.zshrc` or `~/.bashrc` after showing it, only when no line there names `sideby shell-init` and no `shellInitFile` is set; a linked file is written at its real target; `--undo` removes only that exact block.
- Using a Limit Reset (spec §3.40, ADR-0072, `core/limit-reset.ts`) writes nothing into a Host directory. Each operation is one file, `<state>/quota/limit-reset/<operation>.json` (folder 700, file 600, atomic writer), written before the request leaves; its locks are under `<state>/quota/limit-reset/locks/`. A record holds a version, the operation id, the Account refs of the Same Login, the idempotency key, the state and the attempt times: never a Login Key, an Identity, a credit id or a credential. It also holds a salted digest of the login's comparison key, usable only to tell that this operation's login is unchanged; never the Login Key or the Identity (`login: { salt, digest }`; `loginComparisonKey` in `core/same-login.ts` stays in the Runtime). `limitResetUse` compares it when a plan is confirmed and again under the lock right before the request: a plan whose login changed is out of date (`plan-outdated`), and an unresolved operation is not sent from another login and stays `pending` (`login-changed`). Only the Host's final answer to its own key ends a `pending` operation: Accounts leaving or joining its Same Login never do, and `unresolvedFor` finds it by the digest as well as by the Accounts it names, so no second key is made for a login that has one unresolved. An operation file that is there but cannot be read or is not a record, or a folder that cannot be listed (`scanLimitResetRecords`), blocks every new operation and every send (`records-unreadable`); pruning never removes it. A finished record (an outcome, `not-sent`, or `stopped`, which only an older sideby wrote) and a plan nobody confirmed go 24 hours later, with the next `sideby quota` command or plan; an unresolved one (`pending`) is never aged out, because only its key may ask the Host again. `pruneLimitResetRecords` removes a record only while it holds the spend lock of that record's Accounts (not waited for) and after reading it again there, and `limitResetUse` refuses a plan older than 24 hours under that lock before it writes `pending` (`plan-outdated`), so a plan being confirmed is never removed. `Runtime.limitResetUse` is the only caller of a Family's `limitReset.use`, and only `sideby quota reset --yes` and the Panel's `/api/quota/reset` with `confirm` call it (`src/core/limit-reset.test.ts` reads the source for this); it refuses in CI and in a session sideby started under Unattended Mode. `sideby menubar reset` and the Panel's `#reset=<account>` only open a page. For Claude Code, `openVendorPage` starts the browser on `https://claude.ai/settings/usage` (the Account's Browser Profile when one is known, under the rules of `sideby browser`) and reads nothing of it.
